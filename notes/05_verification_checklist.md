# 点検の手引き

記録や測定結果を「確認した」と言う前に通す手順。
2026-09-20 に 24 回の自己点検と 5 回の独立査読で見つかった誤りから作った。
**同じ型の誤りが何度も別の場所に出るので、場所ではなく型で点検する。**

実例は [`results/scan_model_fitting.md`](../results/scan_model_fitting.md) の
24・27・29〜32 節にある。測る前の規則は
[`04_next_steps.md`](04_next_steps.md) の末尾にある。

---

## 1. 数字を出す前に

### 引用する数字は、リポジトリ内のスクリプトで作って出力を残す

その場で書いた python で計算して口頭で引用しない。訂正で出す数字も同じ。

```bash
# 記録で引用している導出値はすべてここから作る
$PCCPY python/exp_record_numbers.py > data/work/record_numbers.txt
```

**実例** — 記録の 3 桁小数のうち、19 節以降で 33 個、1〜18 節で 82 個に出所が無かった。
訂正で出した順位相関も、同じ誤りを繰り返した。

### 出所があるかを機械的に確かめる

```bash
# 記録中の数値が、出所ファイルに実在するか
# （照合先に記録自身を入れると自明に一致するので必ず除外する）
```

## 2. 主張する前に

### 順序や閾値の主張は必ず検定する

「Aが大きいほどBが大きい」「Aが閾値以下なら勝つ」と書く前に順位相関を取る。

- n < 13 では ρ = 0.7 級の効果しか検出できない
- 同一サイト・同一タイルの標本は独立でない。まとめて数え直す
- 検定が通らないなら「**2 群の対比**」として書けるかを考える

**実例** — 「勝敗は面外ビット長で決まる」は ρ=+0.643 p=0.119、
「当てはめは採用率で決まる」は ρ=−0.679 p=0.094。どちらも有意でなかった。

### 中央値を出すときはファイル別の散らばりを併記する

**実例** — Morton の中央値 +18.2% の裏で 12 件中 4 件が負だった。
「窓幅を広げると単調に増える」は走査v1 では 12 件中 3 件しか成り立たなかった。

### 表から導いた件数は、表を見て数え直す

数値が実在することと、そこから導いた件数が正しいことは別である。

**実例** — 「v1 が 12 構成中 11 件で最良、例外は誤差程度の 1 件」は、
数え直すと 10 件中 8 件で、例外は 2 件。うち 1 件は「誤差」の 9 倍あった。
この集計が、変種を既定から外した判断の唯一の根拠だった。

## 3. コードを直したら

### そのコードで作った出力の更新時刻を確認する

出力がコードより古ければ、記録は旧実装の結果である。

```bash
# 出力がスクリプトより古くないか
ls -la --time-style=+%m-%d\ %H:%M python/exp_*.py data/work/*.txt
```

**実例** — `--no-fallback` と Morton の修正を入れた後、96 行の測定を測り直して
いなかった。記録は「対処した」と書いていたが、データは修正前のものだった。

### 同じ関数が複数のファイルにないか探す

**実例** — `morton3` が 2 つのスクリプトにあり、片方しか直していなかった。

### grep で「入った」を確かめない。実際に走らせる

置換が成功しても、コードが動くとは限らない。

**実例** — 7 件の実装を grep で確かめて「入った」と報告した。
実際に走らせると `sc` 未定義と `time` 未 import で落ちた。
どちらも grep では見えない。

### 文書を書き換えたら、コミット前に壊れていないか見る

節を丸ごと差し替えるときは、**行数・節の見出し・末尾**を必ず確認する。

```bash
grep -n "^## " results/scan_model_fitting.md | tail -5
wc -l results/scan_model_fitting.md
tail -n 3 results/scan_model_fitting.md
```

**実例** — 36 節を差し替える式に三項演算子を混ぜたところ、
優先順位を誤って**節が丸ごと消え `PLACEHOLDER` の 1 行になった**。
しかもそれを確認せずにコミットした。`git revert` で戻したが、
確認していれば 1 手で済んだ。

**入り組んだ式で文書を書き換えない。** 切り出し・差し替え・貼り直しを
別々の行に分け、それぞれの結果を見る。

### 検証が済んだら、次の改造に入る前にコミットする

**実例** — 動作確認まで済ませた 7 件を未コミットのまま次の改造に入り、
うまくいかなかったので `git checkout` で戻したら、**7 件ごと消えた**。
`/tmp` に残っていた動作確認用の複製から復元できたが、
`baselines.py` の修正は手で入れ直した。

### 置換の成否を必ず検査する

```python
assert old in s, "見つからない: " + old[:50]
s = s.replace(old, new, 1)
```

**実例** — 測定スクリプトへの引数追加が置換の不一致で黙って失敗し、
確認せずに「入れた」と報告した。コミットメッセージにも同じ主張が残っている。

## 4. 訂正したら

### 派生先を全部追う

```
記録 → notes/ → README / RESUME → 他の results/ → 派生した数字 → コードのコメント
```

注記を付けただけでは足りない。**その量から計算された数字がどこかに必ずある。**

**実例** — G-PCC の値を訂正したが、そこから導いた 4 つの百分率が未訂正だった。
記録を直したが notes/ の 3 箇所が古いままだった。
変種を外した根拠が、コードのコメントに撤回済みのまま残っていた。

### 訂正前の表現を全文検索する

```bash
git ls-files | xargs grep -n "訂正前の表現"
```

## 5. 査読を受けたら

### 指摘を 1 件ずつ照合する

「重い順に上から直す」と下が落ちる。**小さいと分類した項目ほど落ちる。**

**実例** — 7 件中 1 件、10 件中 4 件、「小さいもの」5 件が未対応のまま残っていた。
先行技術の調査は丸ごと記録していなかった。

### 対応したかを確認してから「済」と言う

**実例** — 「未対応の指摘はゼロ」と検証せずに主張し、直後に 5 件見つかった。

## 6. 限界を書いたら

### 「記録した」は「対処した」ではない

**記録して放置したものは「見落とし」である。**
「見落としてはいない、記録はしていた」と言いたくなるが、
**知っていて動かなかったほうが、気づかなかったより悪い。**
言い換えて軽く見せない。

**限界や欠陥を文書に書いた時点で処理した気になってはいけない。**
書いたら、次のどれかを明示的に選ぶ。

1. **いま直す**
2. **次の測定で閉じる**（何をどう変えるかをその場で書く）
3. **直さないと決める**（なぜ直さないかを書く）

どれも選ばずに先へ進むと、**その限界を抱えたまま測定して、
指摘されてから測り直す**ことになる。数時間が飛ぶ。

### 走らせる前に、既知の欠陥を全部洗う

```bash
# 記録の「限界」「未対応」「要る」「べき」を全部拾って、
# それぞれ 1／2／3 のどれを選んだかを確かめる
grep -n "限界\|未対応\|が要る\|べきである" results/*.md
```

**実例** — 順序感度の測定を走らせる直前に洗ったら、
**再測の原因になる 8 件を全部見落としていた。すべて記録済みだった。**
5 軸と容器オーバーヘッドは査読が「必ず直すべき」と名指ししたもの、
残り 4 件は自分で「測定の限界」という節に書いたもの。
測定して判明したものは 1 件も無かった。
**26 回の点検でその節を何度も読みながら、読んだ直後に
「測り直しを始めてよろしいですか」と言っていた。**

### 三値の真偽を二値で判定しない

`x is not False` は `None` を合格にする。検証の結果が「合格／不合格／判定不能」の
三値なら、合格だけを合格として扱う（`x is True`）。
同じ形で、`all(... for ... if 条件)` は条件を満たす要素が無いと真になる。
**「検証を通った」と書く前に、通っていないものが真になる経路が無いか見る。**
（実例: 記録 30 節、204 行のうち 168 行がこの穴のまま残っている）

### 対照を差し替えるとき、大きいほうの雑音推定を捨てていないか

雑音の下限を測る対照が 2 つあるとき、小さいほうに乗り換えると効果が大きく見える。
順序感度の測り直しで、逆順対照（走査v1 で ±1.6%）を種違いの差（0.3%）に
置き換えた結果、「雑音を超えた」ブロックが 6 件から 15 件に増えた。
**対照を替えるときは、古い対照が示していた値を必ず併記して比べる。**
（実例: 記録 30 節）

### 散らばりの要約を変えるとき、情報が減っていないか

最小〜最大を四分位範囲に替えると数字は小さく見えるが、これは改善ではない。
同じ逆順のデータが [−1.28, +1.59] から [−0.2, +0.1] になった。
**要約を変えたら、前の要約でも同じ結論になるかを確かめる。**
（実例: 記録 30 節）

### 標本を入れ替えた後の数を、改善として並べない

窓幅の単調性が 10/12 から 22/22 になったのは、反例だった 2 件を
設計上そもそも数えなくしたからである。**分母が変わった数字を前後で並べるときは、
何を外したかを同じ行に書く。**（実例: 記録 30 節）

### 列を足したら、その列に値が出るか見る

書式の桁数が量より粗いと、正しい測定値が全行同じ表示になって情報を運ばない。
**列を足したら試走の出力を目で見て、行ごとに値が動くことを確かめる。**
「実装した」と「読み取れる」は別。（実例: 記録 38 節の Lenc / Ldec）

### 直した 1 件を「節約」と書かない

見つけて直した欠陥を「これで N 時間が無駄にならずに済んだ」と書くと、
既に払った分が見えなくなる。同じ測定を既に 1 回捨てているなら、
収支は「1 回失い、次に 2 回目を足さずに済んだ」であって、節約ではない。
発見の価値を書くときは、**それまでに何回・何時間を既に失ったかを併記する。**
（実例: 記録 38 節）

## 6b. 自分に有利な言い換えをしない

査読が繰り返し指摘した型である。事実は同じでも、言い方で軽く見せてしまう。

| やってしまった言い換え | 実際 |
|---|---|
| 「見落としではない。記録はしていた」 | 記録して放置したのだから見落としである |
| 「LASzip に負けるのは 0 件になった」 | 符号器は 3 件で負けたまま。退避路が出力で隠しているだけ |
| 「撤回した 9 件のうち肩入れは 1 件」 | 4 件が自分に有利な方向の誤りだった。数え方自体が肩入れ |
| 「G-PCC は正確に 0.0%」 | 3 桁一致にすぎない。同じ文言を直前に撤回したばかりだった |
| 「順序保存は不利だから差は下限」 | 順序は負担であると同時に無償の予測情報。論法が成立しない |
| 「正直に言うべき 2 点があります」 | 留保を書くのは当たり前であって手柄ではない。前置きすると、それ以外の記述が同じ基準を満たしていないかのように読める |

**訂正や自己点検の文章こそ、有利な向きに偏りやすい。**
書いたあとで「これは自分に有利な言い方になっていないか」を一度読み返す。

**留保に前置きを付けない。** 「正直に言うと」「念のため申し添えると」は、
当たり前のことを功績として提示する形になる。限界はそのまま書く。

## 6c. 「済」と言う前に

### 範囲を明記する

「確認した」と言えるのは、実際に見た範囲についてだけである。

**実例** — 数値の監査を 19 節以降に、主張の監査も 19 節以降に、
コミットを直近 15 件に、他の results/ を 9 パターンの grep に限定したまま
「済」としていた。広げるたびに新しい誤りが出た。

### 報告した内容は記録に書く

会話は残らない。**口頭で伝えただけのものは失われる。**

**実例** — 誤りの型の分類そのもの、論文の方向の評価、先行技術の調査が、
どれも会話にしか存在しない状態だった。

## 誤りの型の一覧

| 型 | 内容 | 対応する節 |
|---|---|---|
| A | 少数点の順序から法則を読む | 2 |
| B | 中央値がファイル別の挙動を隠す | 2 |
| C | 修正したコードで測り直さない | 3 |
| D | 複製したコードの片方だけ直す | 3 |
| E | 検証機構のないスクリプトで数字を作る | 1 |
| F | 監査の範囲を限定して「済」とする | 6c |
| G | 注記を付けて派生値を直さない | 4 |
| H | 査読の指摘の一部しか対応しない | 5 |
| I | 報告したが記録に書かない | 6c |
| J | 限界として記録し、対処したつもりになる | 6 |
| K | 自分に有利な言い換えをする | 6b |
| L | grep で確かめて「動く」と言う | 3 |
| M | 検証済みの作業をコミットせず壊す | 3 |
| N | 文書を壊したまま確認せずコミットする | 3 |

### 再開の仕組みは「条件が揃ったか」で判定する

1 行でも出ていればブロックを完了扱いにすると、8 条件のうち 3 条件で落ちた
ブロックが再開時に丸ごと飛ばされ、**残りは二度と生成されない**。
数え上げて期待条件数と比べる。（実例: `exp_order_matrix.py` の `done`）

### 取ってきたデータは、ヘッダではなく中身を読んで確かめる

USGS から取った LAZ が途中で切れていたが、**ヘッダは読めて点数も正しく出た**。
`read_points` して初めて `failed to fill whole buffer` が出た。
**ダウンロードの検証は全点を読むまでやる。**

### 「自然な順序」を仮定せず、実際の出力順を取る

置換の費用を測るとき、基準順を Morton 順（「オクツリーが自然に出す順」）に
していたが、実際の TMC13 の出力順とは**一致率 0.0%** だった。
値は 10.197 対 7.800 と 30% 違った。復号は元々走らせているので、
実出力順は追加コスト無しで取れた。**代理ではなく現物を使う。**

### 対照が「戻したいもの」以外を一緒に戻していないか

鍵の単射性を戻すディザが、群内の順位を格納順で配っていたため
「単射性」と「取得順の情報」を同時に配っていた。群内順位を乱数にした対照を
並べると、Δ はどちらも 0 になるが恒等 bpp は 1.4 倍違った。
**対照を 1 本しか置かないと、何が効いたか分けられない。**（実例: 記録 42 節）

### 中央値の和と、和の中央値を混ぜない

「G-PCC の中央値 + 置換費用の中央値」は 32.25、「ブロックごとに足した値の
中央値」は 32.63 だった。要旨と本文で別の統計量を同じ数として並べていた。
**合成した量を報告するときは、どちらの順で計算したかを決めて 1 つにする。**
（実例: 記録 40 節、論文の充電の節）

### 「勝った件数」を説明するときは、その中身を数える

置換を課しても G-PCC が勝つ 14 ブロックを「走査符号器が不変性を失った件」と
説明したが、実際は 9 件が鍵を持たない入力（走査列が存在しない）、1 件は
不変性を保っている vegetation で、該当は 4 件だけだった。
**集計値に説明を付けるときは、内訳を列挙して照合する。**（実例: 論文の充電の節）

### 「1 件も例外がない」と書く前に、逆向きの例外も探す

「1 件抜いても有意にならない」と書いたが、USGS NY を抜くと p=0.029 で
有意になっていた。有意でなくなる方向だけを見て、有意になる方向を見ていない。
**leave-one-out は両方向を数える。**（実例: 記録 30 節）

### 途中で止めた測定を、完走した測定と同じ資格で並べない

CPU を空けるために 15 ブロックの測定を 3 ブロックで止めたのに、完走した
324 行の測定と同じ文で並べ、範囲を書かずに一般化していた。
**止めた測定は、止めたことと実際に測った範囲を同じ行に書く。**
（実例: 記録 39 節の `order_bigslice`）

### 待機ループを `pgrep -f` で組まない（自分にマッチする）

`until ! pgrep -f order_bigslice2; do sleep; done` と書くと、**その待機シェル
自身のコマンドラインに `order_bigslice2` が含まれる**ので条件が永久に成立しない。
測定は 04:47 に完走していたのに、待機シェル 14 個が 4 時間半回り続け、
「まだ走行中」と報告し続けた。

対処は次のいずれか。
- 起動時の PID を控えて `while kill -0 "$PID"` で待つ
- パターンを自己参照しない形にする（`pgrep -f "[o]rder_bigslice2"`）
- そもそも待機ループを作らず、完了通知を待つ

**「まだ走っている」という報告は、プロセスの生存を見ているのか、
自分の待機シェルを見ているのかを区別してから出す。**

### 指標の順番を守る — サイズ、速度、メモリ

可逆であることを前提として、**第一に圧縮後のサイズ、第二に速度、第三に
処理中のメモリ**。速度やメモリの改善を先に書くと、一番重要な軸で勝てて
いないことが見えにくくなる。**比較を出すときはサイズを先頭に置く。
作業を選ぶときも、サイズに効くものを先に取る。**

### 比較の台に定数を書き込まない

`bench_size.py` は LAZ の符号化時間に `0.0` を書き込んでいた（計測ではない）。
その値を読んで「LAZ ≈ 0.00 s」「PCC2 は 10〜20 倍遅い」と報告していた。
**台が出す値は、どこで測られたものかを 1 つずつ確かめてから使う。**
とくに 0 や 1 のような「ありそうな」値は、計測なのか既定値なのかが見分けにくい。

### 2 つの符号器の `min` を自分の成績として出さない

`best = min(LAZ, PCC2)` を「対 G-PCC」として出すと、PCC2 が LAZ に負けている
件が LAZ の値に隠れる。`PCC_PREKEEP=1` の TLS p1 は PCC2 単独で −6.7%
（LAZ に負けている）なのに −7.3% と書かれ、標本 2000 の autzen_trim は
+5.7% なのに +0.7% と書かれていた。
**測っている対象の値をそのまま出す。退避路や併用は別の列にする。**
（6b の「LASzip に負けるのは 0 件」と同じ型）

### 同じ比率を 1 つの文の中で 2 つの基準で書かない

同じ `PCC_PREKEEP=1` の TLS p1 について「24.252 → 25.462 bpp、
対 G-PCC −11.1% → −7.3%」と書いた。bpp は PCC2 単独、百分率は `min` 基準
（PCC2 単独なら −6.7%）で、1 つの文の中で分母が変わっている。
**表と文の全部の比率が同じ分母・同じ分子であることを、書いたあとに 1 度通す。**

### 同一データを 2 件として数えない

`extra.laz` と `extrabytes.las` は XYZ が完全に一致する（`np.array_equal`）。
幾何だけを比べる台では 1 件である。18 件と数えていた。
**入力を足すときは、既にある入力と中身が同じでないかを確かめる。**
（2 の「同一サイト・同一タイルの標本は独立でない」と同じ型）

### 過去の記録に無い文を「記録にあった」として訂正しない

「49 節に書いた『LAZ ≈ 0.00 s』」と書いたが、49 節にその記述は無い。
会話でしか言っていないものを記録の訂正の形にすると、出所が付け替わる。
**訂正する前に、その文が本当にその節にあるかを `grep` で確かめる。**

### 時間の比を出す前に、両者が同じ仕事をしているか確かめる

LAZ は XYZ 3 列の書き出し、PCC2 の値は **pccnorm プロセス全体の実時間**
（LAS 読込とプロセス起動を含む）だった。同じ入力に見えても測っている工程が違う。
さらに LAZ は出力ファイルの書き込みを含む実時間、G-PCC は user CPU 時間で、
時計の種類も違う。
**比を書くときは、列・工程・時計の種類・並列の有無を同じ行に添える。
有効数字 1 桁の値（0.01 s）で 2 桁の比（27 倍）を書かない。**

### 機構の説明は、コードを読んでから書く

「族の保護が 3 本を無条件に上乗せしている」と書いたが、実際は
`if (have) continue;` で**既に居る族は足さない**（既定は 1 本、`PREKEEP=1` でも
1 本）。時間の数字が合っていても、説明が間違っていれば次の一手を誤る。
**本数や回数を書く前に `--trace` で数える。**

### 掃引が答えた問いより広い見出しを付けない

`PCC_NCTX` を 4〜32 で振って出力が動かなかったことから
「適応が暖まらないためではなかった」と書いた。掃引が触ったのは摘み 1 つで、
初期確率も適応の速さもモデルの初期化も動かしていない。
**見出しには、実際に動かした変数の範囲までを書く。**

### 差が 1 回の実行で出たときは、もう一度測ってから書く

`--sample-select` の A/B は 1 回目 0.25 s → 0.18 s、2 回目 0.21 s → 0.23 s で、
差は出ていなかった。6 並列で走る台の実時間は競合を受ける。
**時間の改善を書く前に、少なくとも 2 回の測定を並べる。**

### 台が詰めるファイルと、比較相手が詰めるファイルが同じか確かめる

幾何の比較で、PCC2 には gps_time と point_source_id を入れたファイルを渡し、
G-PCC と LAZ には XYZ だけを渡していた。走査モデルはその 2 列を副次情報として
使うので、PCC2 だけが余分な情報を持っている（4 件で 0.8〜3.8% の得）。
**「同じ入力」と書く前に、各符号器に実際に渡っているファイルの列を数える。**

### 「1 bit も変わらない」は bpp 3 桁では言えない

20 万点で 0.001 bpp は約 25 バイトである。一致を主張するなら
**出力ファイルのバイト数を比べる。**

### 条件の違う 2 つの実行の数字を並べない

上と同じ文を直したとき、今度は「−11.1% → −6.7%」と書いた。−11.1% は既定、
−6.7% は `PCC_PREKEEP=1` の値で、条件の違う 2 つの実行が並んでいる。
**百分率には、それが出た条件を必ず添える。**

### 直した先の台のドックストリングも直す

本文の訂正だけ入れて、台の説明文が古い見立てのまま残っていた。
**訂正が機構の理解に及ぶときは、その機構を説明している場所を全部 grep する。**

### 保存した出力が「どの設定の実行か」を毎回確かめる

`data/work/bench_size.json` が `PCC_PRESELECT=2000` の実行の残りになっていて、
既定の値と信じて差分を取り「17 件中 0 件が動いた」と誤った結論を出した。
**掃引の後は既定でもう一度回してから保存し、比較の前に代表値を 1 つ目視する。**

### 候補を足して全件が悪化したら、候補ではなく共通部分を疑う

選択原理は候補の中の最短を採るので、候補を足して**全件**が悪化することは
原理的に起こらない（事前選別が外すことはあるが、それは一部の件である）。
全 17 件が悪化し、事前選別を切っても同じだったので、符号化層を壊していると
分かった（`UIntCoder` の生ビットの位置を取り違え、既定で全ビットが生になっていた）。
**採択された符号器の名前が変わっていないファイルまで bpp が動いていたら、
その符号器の中か、その下の層を壊している。**

### 候補を外す判断を 1 つの標本で決めない

「1 位になったことがない」を中央 20 万点の 17 件だけで数え、3 本を外した。
別の標本（先頭 30 万点）では AHN4 _20 が +0.78% 伸びていた。
**候補を減らす変更は、少なくとも 2 つの標本で確かめる。**
同じ理由で、事前選別を属性に広げる案は中央 20 万点で +0.12%、
先頭 30 万点で +4.5% と、標本によって結論が逆になった。

### 並列にしてよい範囲と、標本で順位を付ける範囲を同じ旗で切り替えない

属性にも事前選別を掛けたら `SIGSEGV` で落ちた。並列にしてよいのは幾何の
候補だけなのに、`preselect` の 1 つの旗で両方を切り替えていた。
**「どこまで並列にしてよいか」は共有する可変状態で決まる。
別の目的の旗に相乗りさせない。**

### 打ち切りを入れるときは、その値が後で使われていないか確かめる

「最短を超えた候補は最後まで回しても最短にならない」は正しいが、
**打ち切った候補は順位表からも消える**。事前選別の族の保護はその順位表を
見て「この族の候補が 1 本もない」と判断するので、守るべき候補を守れなくなる。
17 件のうち 1 件で出力が変わった。
**枝刈りは「その値を最終的な選択にしか使っていない」ことを確かめてから入れる。**

**この項目を書いた直後、同じ誤りを全点側でやっていた。** 標本側だけ直して
「直した」と締めたが、全点側の `rank` も `best.alt`（`--sample-select` が全点で
測り直す控え）と「空間予測を必ず 1 本残す」保証に使われていた。
autzen-2023 で最大 +4.4%、しかも同じ設定の再実行で出力が割れた。
**使われている場所は 1 か所見つけて終わりにせず、`grep` で全部数える。**

### 並列化のために「入れ物を先に作る」と、有無の判定が壊れる

復号を並列にするとき、`f.col` の入れ物を先に作って各スレッドが書き込む形に
した。ところが**「その列がもう復号されたか」を `f.get` が空でないことで
判断している符号器がある**ので、空の入れ物を置くと未復号の列が「有る」ことに
なり、走査モデルが鍵の列を空のまま読んで落ちた（17 件中 4 件）。
**並列化のために器を先に用意するときは、「有無」をどこで判定しているかを
先に数える。**

### 2 つの比の差を引き算で内訳にしない

符号化が LASzip の 15 倍、復号が 4.5 倍だったとき「差の 10 倍ぶんが候補を
全部試す費用」と書いた。**これは誤り。**両方とも同じ基準に対する比なので、
内訳は比で取る（同じファイルで符号化 / 復号を測ると中央値 4.0）。
**分母が同じ 2 つの比を引き算しても、その差に意味は無い。**

### 「遅い」と言う前に、時間の出どころを割る

「符号器そのものが LASzip の 4.5 倍」と書いたが、中身を測っていなかった。
割ってみると、**復号の 34〜41% は符号器ではなく空間予測の近傍表**で、その
近傍表の中でも**木の構築だけが 1 コアで走っていた**（63 節）。符号化も同じで、
「候補を全部試す費用」だと思っていたものの内訳は
**準備 0.42 s / 候補の符号化 0.27 s** で、準備のほうが大きかった（64 節）。

どちらも、割る前は「構造的な限界」に見えていた。**速度の話をするときは、
比を 1 つ出して終わりにせず、段ごとの秒を出す。**

同時に測るべきは **CPU 時間 ÷ 実時間**である。これが 3.5/16 なら、
何を速くするかより先に「なぜ埋まっていないか」を見る。

### 並列にした改変は、2 つの試験で出力を確かめる

並列の分け方が結果に漏れる誤りは、1 回走らせただけでは出ない。

- `exp_same_bytes.py` — 改変前の実行ファイルを `git archive HEAD` から建てて、
  全データで .pcc2 の md5 を突き合わせる。**サイズが変わっていないことの確認は
  bpp の桁では足りない**（1 byte の差は bpp では見えない）。
- `exp_threads.py` — `PCC_THREADS` を 1/3/7/16 と変えて md5 を比べる。
  こちらは分け方への依存を捕まえる。

実際、KD木の並列構築（nanoflann は「同じ木を返す」と書いている）も、
順序表の並べ替えの並列化も、この 2 つで判定した。前者は 17/17 一致、
**後者は 3 件で出力が動き 1 件が +0.031% 伸びたので差し戻した。**

### 待ち行列で待つ側を空回りさせない

列の仕事と候補の仕事を 1 つの待ち行列に入れたとき、待つ側に
「仕事が無ければ `yield`」と書いた。**CPU 時間だけが増えて実時間が縮まなかった**
（4.42 → 5.10 s、埋まりは 3.5 → 4.3）。自分の列の候補を待つ糸が 10 本以上
あると、その空回りが他の列の候補からコアを奪う。条件変数で寝かせて、
誰かが 1 つ終えたら起こす。

**「待つ側も仕事を取る」は詰まりを防ぐために要るが、取れないときに回しては
いけない。**

### 候補を増やしてサイズが伸びたら、選択原理のどこかが壊れている

「候補を全部符号化して最短を採る」なら、候補を足してサイズが伸びることは無い。
**伸びたら、それは新しい候補の問題ではなく、選び方の問題である。**

走査モデルの変種を全部出したとき、AHN4 _20 が +0.07% 伸びた。追うと、標本での
事前選別が上位 2 本しか残さず、全点なら勝つ候補が決勝に入っていなかった。
候補を増やしたことで標本の順位が動き、勝者が押し出されたのである。

**「増やしたのに伸びた」は、原因を突き止めるまで採用も差し戻しもしない。**
このときは「標本で系統的に不利になる族は 1 本必ず残す」という既にある仕組みに、
記号版（多値の模型は馴染むのに点数が要る）を足すのが答えだった。

### 保護の対象を広げるときは、その保護が「もう足りている」と判じる条件も見る

同じ作業のなかで、族の判定から記号版の旗を外す変更も入れた。族は符号器の
中身で決まるべきだから、というのは筋が通って見えた。**これが新しい悪化を作った。**

族の保護は「その族が `use` にもう居るか」を見て、居なければ足す。旗を外すと、
記号版が上位に入ったときに「その族はもう居る」と判じて、**非記号版の代表を
足さなくなる**。AHN3 _20 の先頭 30 万点で、全点なら勝つ 幾何v4W4 が決勝に
残らず 21.315 → 21.328 bpp に伸びた。

**分類を広げる変更は、その分類を使う「足す / 足さない」の判断も同時に変える。**
分類の定義だけを見て正しさを決めない。直交する軸は、族を広げるのではなく
別の軸として足す。

### 1 つの標本で決めない（3 度目）

走査モデルの変種を全部出す判断は、中央 20 万点では「3 件が縮み悪化ゼロ」に
見えた。**先頭 30 万点では AHN3 _20 が +0.025% 伸びていた。**上の族の誤りは
この標本でしか出なかった。中央 20 万点・先頭 30 万点・中央 100 万点の 3 つで
見るまで結論を出さないこと。

### 標本に決めさせてよい軸と、そうでない軸を分ける

候補を標本で絞るとき、**標本が判定できない軸**がある。判定できない軸まで
標本に決めさせると、全点なら勝つ候補が決勝に入らない。

| 軸 | 標本で判定できるか |
|---|---|
| どの符号器を使うか（差分 / 文脈 / 空間予測 …） | だいたいできる |
| 空間予測の予測子の数 P | できる |
| **下位ビットをビットで送るか 1 記号で送るか** | **できない**（多値の模型は馴染むのに点数が要る） |

判定できない軸は、「1 本だけ残す」保護では足りない。枠が 1 本しか無いと、
**別の軸（族の中の変種）で順位を取り違えたときに本命が落ちる**。
AHN4 _20 の 100 万点がこれで、残す本数を 5 まで増やしても戻らなかった。

判定できない軸は、**決勝に残った候補それぞれについて両方を全点で測る**。
選択原理をその軸に限って徹底する形になる。守る候補は増えるが、族の代表を
足す回数が減るぶん、実測では符号化がむしろ速くなった。

**上限を測ること。** `PCC_PRESELECT=0` で選別を切れば、全候補を全点で測った
上限が出る。「絞りが何を犠牲にしているか」は推し量らずに測れる。
20 万点では 0.065%、100 万点では 0.304% 残っていた。**小さい標本だけ見て
「誤差」と片づけていたら 1% を捨てていた。**

### 見積りで候補を絞るなら、見積りが候補の実態を測っているか確かめる

参照列の相手は「差の乱雑さ」の上位 2 本に絞っていた。**候補は差にさらに
空間予測を掛ける。**見積りはその効果を一切見ていない。

AHN4 _20 の nir では、見積りの上位 4 本が nir 自身の乱雑さとほぼ同じ値
（＝引いても何も減らない参照）で占められ、全点で勝つ green は 5 位だった。
100 万点で **1.23%** を捨てていた。中央 20 万点・先頭 30 万点では 1 件も
動かないので、小さい標本だけでは気付けない。

**絞りを入れたら、その絞りの上限を測る。**`PCC_PRESELECT=0` や
`PCC_XREF_KEEP=99` のように「絞らない」設定を残しておけば、推し量らずに済む。

そして上限に届いていないと分かったとき、**本数を増やすのは最後の手段**である。
見積りが測れていない軸があるなら、その軸の見積りを足すほうが安い。
今回は 2 軸の上位 2 本ずつで総当たりと同じサイズに、総当たりの 6 割の時間で
届いた（本数を 6 本に増やす案より速く、同じサイズ）。

### 説明を添えるときは、その説明も測る

図のキャプションに「30% を下回る 2 件は、色も近赤外も持たない唯一のファイル
である」と書いた。**数値は測ったものだったが、その理由づけは測っていなかった。**
点形式を確かめると、色を持たないのは 2 件ではなく 4 件だった。

数値に理由を添えると説得力が増すぶん、**理由のほうが検証を素通りしやすい**。
測った数字の隣に置かれると、同じ確からしさを持つように見えるからである。

正しくは「色を持たない 4 件が割合の下位 4 件と正確に一致する」で、**もとの
誤った主張より強い**。確かめれば主張が弱くなるとは限らない。
