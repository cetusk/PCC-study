## 1. 比較が我々に有利に傾いていた（幾何の基準）

`laz_geom_bpp` は LAZ を**ファイル全体**で数え、PCC2 と G-PCC は**中身だけ**だった。
LAS の頭は 469 byte で、1 万点のファイルでは 0.351 bpp の下駄になる。

点データだけを数えるように直した。**vegetation の幾何の負けが現れた**
（従来 +0.0% に見えていたものが実は +1.4%）。

同じ期間に幾何の候補も 2 本増やしている（窓 64・255）ので、
幾何の中央値 −9.4% → −8.3% は**2 つの変更が混ざった差**である。片方だけの測定はない。

## 2. 容器の固定費（小さいファイルで効く）

1 万点のファイルで容器が 857 byte（0.642 bpp）払っていた。LAZ の頭 469 byte より重い。
内訳は `python/exp_container.py` で出せる（出力は repo に無い）。

| 内訳 | 前 | 後 |
|---|---|---|
| 計画（正規化の手順） | 333 byte | **49 byte** |
| 流れの表 | 158 byte | 約 90 byte |

計画は JSON をそのまま入れていた。**二値にした。**効いたのは
**列名を schema の添字に置き換えること**で、"classification" の 14 byte が 1 byte になる。
直前のバイトを文脈にした符号化も試したが、333 byte では 256 の文脈を学習しきれず
縮まなかった（333 → 330 byte）ので採らない。

流れの表は列名を添字にし、長さの 8 byte 固定を可変長にした。

## 3. 点の次元が 13/15 のファイルで戻らなかった

**容器に入っていなかった。**読み込みが `bit_fields` に戻り番号 2 つしか詰めておらず、
走査の向き・飛行線の端・分類フラグ・スキャナ番号を捨てていた。
走査角も拡張形式の欄だけを持ち、旧形式（点形式 5 以下）では 0 が入っていた。

- `bit_fields` を 16 bit に広げ、点形式に応じて全部詰める
- 走査角は旧形式なら `scan_angle_rank`、拡張形式なら `extended_scan_angle`
- ExtraBytes の配列型（data_type 11-30）と未定義バイト列（0）を、
  **1 byte ずつの列**として運ぶ（`Colors#0` …）
- 波形パケット（29 byte、点形式 4/5/9/10）を同じやり方で運ぶ

**13/15 → 0/15**（`cover.log`、30 万点）。

## 4. VLR とヘッダの欄が落ちていた

測地系（GeoTiff の鍵、WKT）が消えていた。封筒に生のまま持たせて書き戻す。
ExtraBytes の VLR は**作り直さず元のものをそのまま書く**（作り直すと
scale / no_data / min / max / reserved が既定値になり、192 byte のレコードが
バイト一致しない。extra.laz で 18 byte 相違していた）。

LAS のヘッダの欄（`global_encoding` / `file_source_id` / `system_identifier` /
`generating_software` / 作成日）も運ぶ。`global_encoding` は点形式 6 以上で
WKT の有無を言う必須ビットで、落とすと器が変わる。
`generating_software` は LASzip が既定で上書きするので
`laszip_preserve_generating_software` で止める。

**14/15 のファイルで、次元・VLR・EVLR・ヘッダの欄がすべて一致する**と書いていたが、
この確認は **VLR の並びを見ておらず**、AHN4 の 2 件で並びが入れ替わっていた。
また autzen-2023 の COPC の VLR は laspy が中身を出せず、実は比べていなかった。
**§26 で直し、いまは 15/15 で全欄が一致する**（`verify_unpack.log`）。
**EVLR も運ぶようにした。**laszip の C API は EVLR を配列で出さないので、
LAS/LAZ のファイルを直に読み書きする（ヘッダの 235 に位置、243 に本数。
EVLR の頭は 60 byte）。simple1_4 の WKT（157 byte）がバイト一致で戻る。

autzen-2023 は COPC の VLR を laspy が比較できないので未確認。

## 5. 次元を保存したら、属性で 2 件負けた

保存し始めた欄の符号化が弱く、USGS AK が +2.6%、NY が +13.6% になった。
`bit_fields` は 2.221 bpp かかっていたが、**条件付きエントロピーは 1.553 bit**
だった（中央 200 万点、字母 50 種、H0 3.401）。

原因は `UIntCoder` が値を「桁数＋下位ビット」に分けて送ること。
50 種のような小さな字母では、その分解が無駄になる。

**字母をそのまま送る符号器（`C_RANGE_SYM`）を足した。**
字母を先頭に書き、添字を直前の記号を文脈にした頻度模型で送る。
さらに**既出の列を文脈に使える**ようにした（残差ではなく文脈なので、
相関が単調でなくても効く）。どの列をどのビット位置で使うかは候補にして実測で選ぶ。

USGS NY・中央 200 万点（`bench_split.py` と同じ切り出し）:

| 列 | 前 | 後 |
|---|---|---|
| bit_fields | 2.221 | **1.539**（point_source_id を文脈に） |
| intensity | 5.449 | **4.965**（bit_fields を文脈に） |
| classification | 0.998 | **0.740**（intensity を文脈に） |

属性は **15/15** に戻った（AK −8.2%、NY −0.2%）。全体の中央値も −11.5% → **−13.7%**。

## 7. 査読が見つけたコードの欠陥（5 件、すべて直した）

このうち 3 件は**この記録の変更が新しく入れたもの**である。

### 7-1. ExtraBytes の配列型の大きさが間違っていた

```cpp
if (dt <= 20) { int b = base[(dt - 11) / 2 + 1]; return b * 2; }
```

添字は `dt-10` / `dt-20` が正しい。`(dt-11)/2+1` は dt=11,12 でしか合わない。
`extra.laz` の `Colors`（dt=23、ushort[3] = 6 byte）を **3 byte** と数え、
以降の次元を全部ずれた位置から読んでいた。**往復が通っていたのは偶然**で、
読み飛ばした 3 byte がたまたま全部 0 だったためである。
査読が `Time` に 2^50 を足した反例を作ると、`pack` は「全列一致」と報告しながら
`Time` が壊れていた。直した後は反例も往復する。

### 7-2. 点レコード長が伸びていた（基準が水増しされていた）

`write_las` が `base -= ftype_size(e.type)` としており、生のバイト列の次元で
1 しか引いていなかった。`extra.laz` の点レコードが 61 → 70 byte になり、
**基準の LAZ に 1 点あたり 9 byte のゼロ詰め**が入っていた。
基準 233.465 bpp は水増しで、正しくは 218.471 bpp（実ファイルと一致）。
対 LASzip は −39.2% ではなく **−35.8%** である（その後の改良で現在は −36.1%）。

### 7-3. 点形式 6 以上で分類フラグを立てると書き込みが失敗する

§3 で `extended_classification_flags` を書き戻すようにしたが、
旧欄（`synthetic_flag` など）を設定していなかった。
LASzip は両者の下位 3 bit が食い違うと書き込みを拒む。
**`pack` の基準 LAZ 書き出しでも起き、「基準 0.000 bpp・検証 true」と出て黙って落ちる。**
現在の 15 件は該当フラグが 0 なので表面化していなかった。
合成した点形式 6 のファイルで再現し、直した後は往復する。

### 7-4. 粗い格子と正規化の順序が噛み合っていなかった

復号が `denormalize_frame` → `restore_column_grid` の順だった。正規化の計画は
「割る前」の単位で立てられているので、複製を指す操作が別の値を書き戻す。
8 bit の色を 16 bit 欄に入れて `green = red` にした反例で、`unpack --las` が
**黙って壊れた LAS を書いていた**（green に red/256 が入る）。
順序を逆にした。反例も往復する。

### 7-5. 字母符号器の復号側に参照列の長さ検査が無かった

壊れた容器で領域外を読む。符号化側にはあった検査を足した。

### 幾何で LAZ に負けていた所 — 解消した

vegetation の +1.4% は、**予測子が当たっていなかった**のが原因だった。
潰すまでに 4 つの見立てを測って、3 つは外れた。

**外れ 1: 軸をまたぐ文脈が無いからだ。**既に入っていた。`enc_geom_x`（幾何v3）は
`c==0` なら直前の同軸、`c==1` なら `dx` の桁、`c==2` なら `(dx,dy) の桁の平均` を
文脈にしている。文脈を平均でなく 2 次元の組（24×24 = 576 通り）にすると、
1 万点では適応模型が学習しきれず **悪化**した（24.890 → 26.160）。
根拠にしていた「H(dz | dx,dy の桁) = 5.036 bit」は標本内の条件付きエントロピーで、
**10,683 点の中に実際に現れた文脈が 149 個**あった（文脈の空間は 576 通りで、
そのうち 149 個に標本が散った）。1 点あたり 72 標本では条件付き分布を推定できない。適応模型で同じ手順を回すと 25.257 bpp で、
符号化器の実測 25.307 bpp とほぼ一致する。
**標本内の条件付きエントロピーを符号長の見積りに使ってはいけない。**

**外れ 2: 戻り番号ごとに予測子を分けていないからだ。**LASzip は座標の予測子を
戻り番号と戻り総数で引く別々の状態で持つ。こちらの幾何v2 は状態を分けるが軸を
またぐ文脈を持たず、幾何v3 は逆で、両方を持つ候補が無かった。足したところ
**vegetation では 1 ビットも変わらなかった** — このファイルは全 10,683 点が
戻り 1/1 で、覆いを掛けると定数になる。

仮説自体はほかで当たった。**予測子を揃えて補助列の有無だけを比べる**と、
autzen_trim で `幾何v3半` 22.709 → `幾何v3半補63` **22.485**（−1.0%）である。
候補として残した（このファイルで最後に勝ったのは、中央値 5 と軸をまたぐ文脈も
重ねた `幾何v3中5十補7` の 20.061）。

**外れ 3: 模型の適応が遅いからだ。**`PROB_RATE` を 3〜6 で振ると vegetation は
最良 24.780（既定 5 で 24.795）で、0.015 bpp しか動かない。流れごとに持ち替える
仕組みを入れる価値はないと判断した（`geom_predictor.log`）。

**当たり: 傾きを足すのをやめる。**幾何v3 系はどれも「直前の点＋直近の差分の
中央値」を予測子にしていた。vegetation では、傾きをそのまま足すと 25.592、
半分にすると 24.890、**足さない（直前の点そのもの）と 23.987** になる。
葉群のように隣の点が跳ねる入力では、中央値の傾きは当たらず外れを増やすだけである。
軸をまたぐ文脈は保ったまま傾きの効かせ方だけを選べるようにした
（1/4・1/2・3/4・足さない・中央値 5 の 5 通り、`param[1]` の下位 2 ビットと
最上位ビット）。

「前」は**そのファイルで実際に選ばれていた候補**の値（`bench_three_2m.log`）。

| ファイル | 前 | 後 | LAZ（点データのみ） |
|---|---|---|---|
| vegetation | 24.890 | **23.987** | 24.535 |
| plane | 6.102 | **5.813** | 6.672 |
| autzen_trim | 21.064 | **20.061** | 21.125 |
| fullwave | 25.433 | **23.760** | 27.719 |

**幾何単体で 17/17 のファイルが LAZ より小さい**（比の最大は vegetation の 0.978）。

### 比較がまだ我々に有利に傾いていた（2 度目）

`bench_three.py` の LAZ の bpp は**ファイル全体の大きさ**を使っていて、PCC2 側は
流れのバイト数だけだった。1 万点のファイルでは LAS の頭と VLR が 0.35 bpp の下駄になる。
`exp_order_matrix.laz_geom_bpp` では直してあった同じ誤りが、こちらに残っていた。
直すと vegetation の LAZ は 24.887 → 24.535 になる。
**この表の「勝った」は、直したあとの数字で言っている。**

### 速度の退行について

**列が増えたぶんである。**字母符号器の候補は時間をほとんど食わない
（AHN4 _20 の 200 万点で 2.82 → 2.77 秒。`PCC_SYM=0` で比べられる）。
遅くなったのは、これまで捨てていた列を保存するようになり、
fullwave が 29 列、extra が 12 列増えて、その全部に候補の総当たりが掛かるためである
（fullwave の符号化は 0.030 → 0.120 秒）。

**絞る案を 2 つ測って、どちらも落とした。**

| 案 | fullwave のサイズ | |
|---|---|---|
| そのまま（当時） | **125.8 bpp** | 符号化 0.12 秒 |
| 生のバイト列を 1 本の流れにまとめる | 137.5 bpp | 0.05 秒 |
| 空間予測の候補を外す | 128.9 bpp | 0.11 秒 |

どちらも速くなるが、**サイズが第一**という順位では採れない。

幾何の候補を 20 本足したぶんは、**符号化の中央値を動かさなかった**
（20.7 倍のまま。幾何は標本で予備選別してから全点で測るので、候補を足しても
全点を通る本数はほとんど増えない）。
足した候補は**サイズを一度も悪化させない**（選択は実測なので、負ける候補は選ばれない）。
掛かるのは符号化の時間だけで、その時間が幾何の bpp で
vegetation −3.6%・fullwave −6.6%・autzen_trim −4.8%・plane −4.7% を買っている。

**LASzip に速度で勝つことは、この設計では起こらない。**LASzip は 1 回通すだけで、
こちらは候補を全部符号化して最短を採る。これは欠陥ではなく設計の選択である。
退行（14.9 → 30.6 倍）は記録するが、勝ち負けの表に載せる意味は薄い。

## 8. 査読が見つけた欠陥（2 度目、2 件とも直した）

### 8-1. 包んだ器を選ぶと、正しい出力に対して検証が落ちる

自前の符号器より元の器のほうが短いとき、PCC2 は元の器をそのまま包んで運ぶ
（`中身 元の器を包んだ`）。`pack` の往復検証はその中身を書き出して `load_frame` で
読み直すが、**`load_frame` は入力側で `apply_column_grid` を通す**ので、読み直した側は
粗い格子で割られたままだった。比較相手には `restore_column_grid` が掛かるので、
空間が揃わず `全列一致 = false` になる。

```
$ pccnorm pack data/raw/small/fullwave.laz out.pcc2 --max-points 50
中身        元の器を包んだ（自前の符号器より短かった）
検証        全列一致 = false  差異: red[0]: 25186 != 49        ← 25186 = 514 × 49
```

**圧縮そのものは壊れていない**（包んだバイト列はそのまま）が、検証が落ちる。
自前の符号器の側には `restore_column_grid(g)` が足してあり、包んだ側に足し忘れていた。
直したあと、幾何軸まで割られる場合（合成 LAS で `X 500 / Y 500 / Z 500`）も含めて通る。

**この欠陥が測定に現れなかったのは、包んだ器が選ばれる測定をしていなかったからである。**
`bench_all.py` の 15 ファイルではどれも自前の符号器が勝つ。
**「落ちたもの 0」は「その道を通った」を意味しない。**

### 8-2. `unpack` が包んだ器を出せなかった

包んだ .pcc2 には列が 1 本も入っていないので、`unpack` は `点数 8 / 列 0` と出して

## 9. G-PCC に届かせようとして測った 5 つの筋

素の G-PCC に負けている 6 件（USGS NY・autzen-2023・extra・plane・vegetation・KITTI）
を潰しにいった。**4 つ外れて 1 つ当たった。**ログは `data/work/gpcc/`。

**外れ 1: 順序を捨てて八分木の順で符号化し、置換を送って戻す。**
Morton 順に並べ替えるとこちらの符号器は 0.5〜2.1 bpp しか縮まず、
置換が最安の指し方でも 3.0〜13.3 bpp 掛かる。さらに Morton 順でも USGS NY は 23.774 にしかならず、
G-PCC の 21.140 に届かない。**差は順序ではなく模型にある。**

**外れ 2: z を近傍の面から予測する。**1 点の中で x と y は z より先に送られるので、
その点の x,y を知った状態で z を予測してよい（副情報は生じない）。
地形なら当たるはずだったが、**6 件中 5 件で悪化**した。格納順が既に空間的に
連続しているので、**格子の升より格納順の直前の点のほうが近い**。

**外れ 3: 2 次（曲率）の外挿。**全ファイルで悪化。最良は KITTI が中央値 3、
plane と vegetation が「傾きを足さない」で、どちらも既に入っている。

**外れ 4: 回転予測。**KITTI のリングはセンサ原点まわりの回転なので、直線の
外挿では表せない。方位角の刻み（中央値 0.1797 度）で前の点を回す予測子を作ると、
残差の絶対値は 178.7 → 161.7（x、**−9.5%**）、134.5 → 130.2（y、**−3.2%**）しか
減らない。
**KITTI の残差を支配しているのは距離の跳び**（|dr| の平均 220.8）で、
これは場面そのものの情報であり幾何の模型では落とせない。

**当たり: y をその点の dx から予測する（向き追従、`C_GEOM_DIR`）。**
1 点の中で x は y より先に送られるので、`dy ≒ dx × (前の dy / 前の dx)` が使える。
既存の幾何v3 は dx の**桁数**しか文脈に使っておらず、値としては使っていなかった。
積は int64 で溢れうるので 128 bit を経由する。

| | 前 | 後 |

## 10. G-PCC との比較は、そのままでは同じ仕事ではなかった

**G-PCC は点を多重集合として扱い、格納順を捨てる。**LAS/LAZ を 1 本復元する
用途では属性がファイル上の点順に並ぶので、順序を復元できなければ同じファイルに

**この節は 2 度書き直した。どちらも「置換をもっと安く送れる」を見落としていた。**

下がる一方である。したがって **「PCC2 ＜ G-PCC＋順序」と言えるのは余裕が十分

対応／**tmc3 の固定費（約 42 byte。1 点でも bitstream は 43 byte）を G-PCC から引く**。

ファイル**である。plane は 225×198 の格子に 28,185 点（占有 63%、Z は 5 値）で

## 11. 仮数部を素通しにする — 一様なビットに適応模型は害になる

`delta記` のように**文脈を一切使わない**符号器が勝つファイル（extra、1065 点）で、
静的な下限（45.916 bpp）と実測（47.023）に 1.1 bpp の開きがあった。
内訳を測ると、**桁数の適応が 0.28、残りは仮数部**だった。

**一様に近いビットを適応模型に通すと 1 ビットが 1.0119 ビットに付く**
（`PROB_RATE=5` で乱数ビットを 10 万個通した実測。+1.19%）。
模型の `p0` が雑音に振られるためで、偏りが無い限り取り返せない。
仮数部の下位はほぼ一様なので、ここは**模型を通さず等確率で書く**ほうが短い。

範囲符号器に直接ビットの入出力を足し（`encode_raw` / `decode_raw`）、
**上から 1 ビットだけ模型に通して残りを素通しにする**旗を作った（`C_RAW_BIT`）。
分布の形は最上位ビットに出るので、そこだけ模型に残す。

**全部に掛けてはいけない。**下位に偏りがある列では模型が勝つ。
全ファイルに一律で掛けると vegetation が 41.771 → 43.469 と伸びた。

| 幾何のみ | 素通し無し | 素通し |
|---|---|---|
| extra | 47.023 | **46.693** |
| KITTI | 16.899 | **16.830** |
| autzen_trim | 20.061 | **19.950** |
| plane | 5.813 | **5.811** |
| vegetation | 23.987 | 24.016（採らない） |

**候補として出すのではなく、勝者に後追いで 1 本足す。**候補を倍にすると符号化が
倍になるうえ、**標本での順位が崩れて全点の最良が押し出される**（幾何で候補を
倍にしたら KITTI が 16.830 → 17.010 に伸びた）。

**`rank` の上位に広げてはいけない。**打ち切り（`enc_best`）は候補が終わる順で効くので、
どの候補が `rank` に残るかはスレッド数で変わる。上位 3 本に広げたら
**17 件中 3 件で md5 がスレッド数によって動いた**。勝者は打ち切りに依らず決まる
（打ち切られた候補は必ず勝者より長い）ので、そこだけなら決定的である。

15 ファイル中 **11 件で縮み、悪化は 0**（残り 4 件は 3 桁まで同値）。
autzen-2023 −9.9 → −10.1%、extra −35.8 → −36.1%、fullwave −17.0 → −17.1%。

## 13. 恒等候補が narrow な列の天井になっていなかった

`C_RAW64`（恒等候補）は 1 値を 64 bit で格納する。**1 byte の列に対しては
天井として働かない。**fullwave の波形バイト 6 列は、範囲符号器を通して
**8.177 bpp** — 素で格納する 8.000 より膨らんでいた。一様に近いバイト列に
適応模型を掛けた代償（§11）が、逃げ道の無いまま出ていた。

**列の自然な幅でそのまま格納する符号器**（`C_RAW_W`、param = 幅 byte・符号つきか）を
足した。幅に入らない値が 1 つでもあれば候補ごと外すので、黙って壊れることはない。

| fullwave の波形バイト | 前 | 後 |
|---|---|---|
| wave_packet#13/17/18/21/22/25 | 8.173〜8.177 | **8.000** ちょうど |
| fullwave 全列 | −18.0% | **−18.7%** |

**これで「どの列も自然な幅を超えない」が保証される。**恒等候補は「器の長さが
有限で閉じる」ための仕掛けだったが、64 bit 固定では閉じ方が粗すぎた。

**実際に勝ったのは 17 ファイル中 fullwave の 6 列だけ**（30 万点で数えた）。
病巣は狭いが、**保証としては全部の列に効く**。列や器を足したときに同じことが
起きても、もう素の幅より膨らむことはない。

## 14. 属性の高い列を洗った — 残りは模型の限界だった

`extra` の `gps_time`（32.714 bpp）と幾何（46.460）に、まだ取りこぼしが無いかを
同じ手法で確かめた。**どちらも無かった。**

| extra の幾何 | 46.460 | 46.464 | 45.916 |

## 15. 内挿（持ち上げ変換）— 実装して測って外した

文献調査（`results/literature_2026.md`）で見つけた「粗い層を先に確定させて細かい層の
文脈にする」（PACE の post-causal、八分木の多段）を、我々の系列に落として実装した。
外挿でなく**前後の点で挟んで内挿**する形（`C_GEOM_LIFT`）。往復は通る。

**10 ファイルすべてで負けた**（+6.4〜27.0%）。段数を 1 まで浅くしても変わらない。

**見積りの比較相手が弱すぎた。**素朴な外挿（直前からの差）を相手にすると −13.0% と
出たが、実際の符号器は AHN3 で `幾何v4W16記` を使っており 19% 良い。
**内挿の実装自体は見積りより良かった**（26.263 < 26.984）ので実装は正しい。
**これで「弱い相手と比べて利得を見積もる」罠を 3 度踏んだ。**

**構造的な理由。**AHN3 の勝者が 幾何v4（直近 16 点の最近傍）だということは、
格納順が滑らかな曲線ではないということである。格納順に沿って挟んでも、
空間的に近い点がそこにあるとは限らない。

符号器は残してあるが**候補からは外した**（勝たないのに符号化時間だけ掛かるため）。
粗い層に強い予測子を使う形でやり直すなら、候補に戻すだけでよい。

## 17. 桁長の照合模型 — 22 列で 0 列

`C_MTC_BIT`。直前 3 つの桁長と文脈から合図を作り、同じ合図のときに前回来た
桁長を予測に使う。当たり外れを 1 ビットで送り、当たれば桁長そのものは送らない。
表も合図も両側が同じ履歴から作るので**送るものは増えない**。

勝者に対して 8 ファイル 22 列で測り、**採られたのは 0 列**。
下表は `--trace` の X+Y+Z 流そのものの値で、**標本は格納順の先頭 200 万点**
（`--max-points`）である。`bench_split_*.log` の「幾何」は中央 200 万点なので、
同じファイルでも値が違う（red-rocks は 7.044 対 6.979）。§16 も同じ標本。

| 列 | 勝者 | 照合版 |
|---|---|---|
| plane X+Y+Z | ctx記 1.204 | 1.438 |
| USGS NY X+Y+Z | 幾何v4W4記 24.986 | 26.307 |
| vegetation gps_time | 差分表記 11.257 | 11.545 |
| red-rocks X+Y+Z | 幾何v3中5記 7.044 | 7.551 |

**桁長の文脈が既に効いているので、当たりの目が薄い。**外れたときは当たり外れの
1 ビットが丸ごと損になる。適応模型なので 1 ビットまでは払わないが、
それでも 1 値あたり 0.1〜0.2 ビットで、桁長を送る費用に対して重い。

符号器は残してあるが**勝者に対して測るのもやめた**（採られないのに
符号化時間だけ掛かるため）。

## 18. 文脈を束ねる — 11/25 列で採られたが、全体では 0.05% 未満

`C_BND_BIT`。文脈ごとの表は、その文脈をまだ数えるほど見ていないうちは
当てにならない。見た数が 24 に届くまでは**全文脈に共通の表**で符号化し、

**送るものは増えない**（値ごとの旗も要らない）。照合模型と違ってここが効く。

10 ファイル 25 列で測って **11 列で採られた**（gps_time が 6 列、幾何が 1 列、
参照系が 3 列、wave_packet が 1 列）。**ところが全体の効きは 0.05% 未満である。**

## 21. 非可逆の選択肢を器に繋いだ（`pack --eps`、既定では通らない）

極座標格子の機構は `geom.cpp` に前からあったが、**解析用の道具**で、
器（PCC2）には繋がっていなかった。繋いだ。

- 器に `T_POLAR`（原点・距離の刻み・角度の刻み・元の器）を足した
- `frame_world` と `denormalize_frame` が `geom_repr == "polar"` を扱う
- `pack --eps <m>` を足した。**指定しなければ一切通らない**
- 粗いデカルト格子（`kind == "grid"`）も受ける。こちらは既にある
  整数格子の表し方（値 = scale*q + offset）でそのまま言えるので、
  復号側に足すものは無い
- 検証が二本立てになる。**属性はビット完全**、幾何だけ誤差上限の中

**符号化時の誤差の申告が、出力側の丸めを数えていなかった。**
復号は世界座標を元の器（1 mm の整数格子、または float32）に書き戻すので、
極座標の丸めの**後にもう一度**丸めが入る。1 mm 格子なら最大 0.866 mm 増える。
KITTI の 5 frame 15 通りのうち 5 通りで、宣言した 2 mm を超えて出ていた
（実測 0.00223607 m = 1 mm 格子の √5 倍）。**復号と同じ道を通して測り**、
超えたぶんだけ刻みを詰めて測り直すようにした。

## 22. 分野を変えて探した — 2 つ外れ、その理由が 1 つ当てた

点群圧縮の文献は調べ尽くしたので、**可逆音声・可逆画像・汎用データ圧縮**の
符号器が使っている道具を持ってきて測った。詳細は `results/newfields.md`。

**外れた 2 つは `enc_geom_x` を通るファイルでしか測っていない。**
`PCC_LMS_KIND=0/1` の分岐は `enc_geom_x` にしかないので、勝者が 幾何v4
（`enc_geom_w`）や走査のファイルでは**何も測っていない**（USGS NY を
`PCC_LMS_KIND=1` で回すと 3 本とも無印と同値になる）。
以下の「全部で負けた」は**その範囲での話**である。

**外れ 1: 縦続の適応フィルタ**（MPEG-4 ALS / Monkey's Audio）。
予測子の出力に、直近 16 個の残差から作る補正を足す。重みは符号×符号で動かす。
副情報は増えない。plane 5.611 → 5.847、vegetation 23.963 → 25.830、
red-rocks 7.044 → 7.865。重みに歯止めを付けても、次数を 16 → 4 → 1 と
下げても負ける。**予測子が既に線形の傾きを取っているので、取るものが残っていない。**

**外れ 2: 文脈ごとの偏り補正**（JPEG-LS / CALIC）。
文脈ごとに残差の和と個数を持ち、平均を予測に足す。
plane 5.661、vegetation 25.578、red-rocks 8.436、fullwave 26.656 と**大きく外れた**。

**外れた理由がそのまま当たりを教えた。**我々の文脈は `ctx_of(zigzag(残差))`、
つまり**残差の桁数**で、**符号を捨てている**。符号を捨てた文脈の中では
残差の分布は対称で、平均は 0 に近く、そこから作る補正は雑音でしかない。
JPEG-LS が条件にしているのは**符号つきの勾配**である。

**当たり: 符号つきの文脈。**文脈に「直前の残差の符号」を 1〜4 個ぶん足す。
送るバイトは増えない（長さの指定は既存の符号器 id の空きビットに乗る）。
長さの最適値はファイルで違う（USGS NY は 2 個、red-rocks は 4 個、
autzen_trim は 1 個）ので、**3 通りを出して実測で選ばせる**。

実装したのは 3 経路だけ — `enc_geom_x`（幾何v3・回転）・`enc_geom_w`（幾何v4）・
`enc_resid_x`（走査 var 3/4）。**効いたファイルの勝者は 4/5 が「傾きを足す」
予測子**なので、「無傾が勝つファイルで効く」とは言えない。言えるのは
「残差の符号に相関がある入力で効き、その相関の長さはファイルで違う」まで。
なお `sgn_push` は「正か否か」の 1 ビットで、**残差 0 は負と同じ袋**に入る
（JPEG-LS の 3 値量子化とは違う）。

| | 符号つき文脈の前 | 後 |
|---|---|---|
| USGS NY 全列 | −7.6% | **−9.7%** |
| AHN5 _20 全列 | −9.8% | **−10.1%** |
| plane 全列 | −32.4% | **−33.1%** |
| autzen_trim 全列 | −12.2% | **−12.4%** |
| 全列の幅の下端 | −7.6% | **−8.5%** |
| **幾何の中央値** | −10.0% | **−12.9%** |
| 符号化 / LASzip | 30.6x | **28.9x** |

**幾何の中央値が 2.9 ポイント動いたのは、中央のファイル（USGS NY）が
そのまま動いたためである。**動いたのは 15 件中 5 件（AHN3・AHN5・USGS NY・
autzen_trim・plane）で、残り 10 件は 1 ビットも動いていない。
中央値の動きを「全体が良くなった」と読んではいけない。

符号器は残してある（`LmsPred` と `BiasTab`）。旗 `C_LMS_BIT` / `C_SGN2_BIT` の
組で 0 = 切・1 = 符号 1 個・2 = 符号 2 個・3 = 符号 4 個を表す。
適応フィルタと偏り補正は `PCC_LMS_KIND=1` / `=0` で測り直せる。

**後置検査は「実装した経路の勝者」に限った。**最初は勝者の基底 id だけで判定して
いたので、幾何v1 が勝つファイル（red-rocks の中央 200 万点）では
**同じバイト列を 3 回符号化していた**。限ったら符号化が 32.0 → **28.9x**
（符号つき文脈を入れる前の 30.6x より速い）。

## 23. `--force-geom` で候補が 1 本になると、器が壊れることがあった

`tls_scan1.ply` を `--force-geom 素4B` で強制すると、復号が
「RAW64 の長さが合わない」で落ちた。f64bits の座標は 4 byte に収まらないので
候補が失敗し、**`--force-geom` が候補を 1 本に絞っているので恒等候補ごと消える**。
`best` は `codec = raw64`・`data` が空のまま書かれていた。

器の設計は「**恒等符号器 raw64 を必ず候補に含めるので長さは有限で閉じる**」だが、
`--force-geom` はその前提を壊していた。**どの候補も通らなかったら恒等符号器で
書く**ようにした。直したあとは 192.009 bpp（3 軸 × 64 bit）で往復する。

`pack` の自己検証が捕まえていたので、壊れた器が黙って出ることは無かった。


## 24. パルス構造（光線）— 物理は成り立つが、効いたのは予測でなく流れの分け方

詳細は `results/structure.md` §1。1 パルスの複数の戻りは 1 本の光線に乗り、
隣り合うパルスの戻り間ベクトルの cos の中央値は ≈ 1（USGS NY・AK・AHN3・AHN4 で
1.00000、AHN5 で 0.99975。`exp_ray.py x 300000`）。
その平行性で「前の戻り＋戻り間ベクトル」と予測すると、Python の見積りは
多重戻りの点で −5.5〜−29.6%。**実装すると USGS NY は 24.133 → 25.106 と伸びた。**

**実際の符号器の中で数えると**（診断コードは削除済みで再現できない）、続きの点の
残差は光線なしで約 21.3 bit/点、光線ありで 20.8 bit/点（−2%）しか違わない。
本物の 幾何v4W4 は直近 4 点の最近傍を使うので、既にほぼ同じ精度で送っていた。
Python の「幾何v4 相当」は**戻り間ベクトル（10〜27 m）の中央値**を傾きとして
足していた。**相手が弱すぎた（7 度目）**。ただし傾きを抜いても Python では
光線が −10% 良いと出るので、傾きで説明できるのは差の一部である。

**効いたのは構造のほう**である — 続きの点に**別の文脈**を割り当てること
（AHN5 で 24.679 → 24.591）と、**傾きの履歴に入れない**こと（傾きを足す予測子で
AHN5 24.591 → 23.916）。勝者が傾きを足さない USGS NY と AHN3 では前者だけが効く。予測部分は `PCC_RAY_PRED=0` を既定にした。
全 15 件で 6 件が動き、**中央値が −13.9% → −14.3%**（前後とも中央は workshop で、
その 1 件の変化がそのまま中央値の変化）。**速度の費用はほぼ無い**
（PCC2 の符号化の実時間 15 件合計 30.20 → 30.27 s）。

後置検査は 4 通り（光・光＋符1・光＋符2・光＋符4）。**続きの点が 1 つも無い
ファイル**（plane・TLS・KITTI）では出さない（同じバイト列を 4 回符号化するだけに
なるため）。**復号は波ごとに並列なので、光線版の幾何は `bit_fields` への依存を
宣言している**（しないと同じ波で書きかけの bit_fields を引く）。

## 25. 曲面による z の予測 — 神託では −10〜17%、実装すると 1/15 件で −0.07%

詳細は `results/structure.md` §2。z を送る時点で (x, y) は既知なので、
(x, y) の近くの復号済みの点から z を予測する（最近傍・平面の 2 つ）。
単独では全部負けるが、**点ごとの最良（神託）は −10〜17%**。
復号済みの情報で選ぶ（直近の減衰誤差）と、診断では red-rocks −15.3%・
autzen-2023 −11.2%・AHN5 −9.9%・workshop −6.2%（いずれも z の桁数、先頭 200 万点、
旗の無い 幾何v4 の基底を強制。**診断コードは削除済みで再現できない**）。

**実装すると、ほぼ全部で負けた。**選んだ予測子の番号を z の文脈に入れても
変わらない。全 15 件で動いたのは AHN4 _21 だけ（52.140 → 52.106）。

**診断は「実際の符号器の中」で測ったが、相手が旗の無い 幾何v4 の基底だった。**
なぜ消えたかは確かめていない（候補は `structure.md` §2 に並べた — 勝者の旗が
掴んでいた／桁数の和が符号長の代わりとしてずれていた／z の文脈を 3 倍にして薄まった）。
**「符号器の中で測る」だけでは足りず、勝者の旗まで含めて本物にすること（8 度目）。**

**残した**（サイズは悪化しない）。**代償は実時間で +19%**（PCC2 の符号化 15 件合計
30.27 → 36.16 s）。AHN4 _21 は 4.66 → 6.99 s、効かない AHN3 も 4.24 → 5.86 s。
LASzip との比で見ると分母が揺れるので費用が小さく見える（比の中央値は 34.2 → 35.9x）。
**外す第一候補**である。外すなら `best_stream` の「2 段目: 曲面による z の予測」を消すだけでよい。

**潜在的な欠陥を 1 つ直した**（査読が見つけた）。格子の鍵を 32 bit に切り詰めているので、
座標が double のビット列で広い範囲に散る入力では**遠い点が同じ鍵に入り**、平面の
計算で差の 2 乗が __int128 でも溢れうる（符号つきの溢れは未定義動作）。
隣の 3×3 マスに入る点は |dx|, |dy| < 3·2^S なので、2^(S+2) を超える近傍と、
|dz| が 2^40 を超える近傍を捨てるようにした。普通の入力では出力は変わらない
（15 件のサイズが一致）。

## 26. VLR の並びが入れ替わっていた — 以前の「VLR はバイト一致」は並びを見ていなかった

査読で `unpack --las` の全欄比較にログが無いと指摘されたので、
比較を**再現できるスクリプト**にした（`python/verify_unpack.py`）。元のファイル
そのものと、点の全次元・VLR と EVLR のバイト列・ヘッダの欄を比べる。

**AHN4 の 2 件で VLR の並びが入れ替わっていた。**中身のバイトは全部一致するが、
元は `LASF_Spec 7` → `LASF_Spec 4`（ExtraBytes）の順なのに、書き戻すと逆になる。
読み込みで ExtraBytes の VLR を取り出し、書き出しでは**常に先頭に**書いていたためである。
§4 の「VLR はバイト一致」は、並びを見ない確認だった。

**元の位置を覚えて、そこに書き戻す**ようにした。位置は封筒の末尾に持たせ、
**先頭（0）のときは書かない**ので、AHN4 以外の 13 件は 1 byte も増えない
（常に 4 byte 書くと extra で 0.03 bpp 伸びる）。古い封筒は 0 と読む。

**もう一つ、比較の穴も見つけた。**laspy は COPC の VLR（`copc 1`・`copc 1000`）の
中身を出せず例外を投げる。それを両側とも空として比べると、**確かめていないのに一致**と
出る。以前 autzen-2023 を「未確認」としていたのはこのためである。
VLR と EVLR は**ファイルのバイト列から直接読んで**比べるようにした。

**直したあと、15/15 で全欄が一致する**（先頭 30 万点、`verify_unpack.log`）。
autzen-2023 の COPC の VLR もバイトは一致する。ただし COPC の VLR は点データの
配置を指すので、**点を書き直した器が COPC として正しく読めるかは確かめていない**。

平面は**整数演算（__int128 とクラメルの公式）で厳密に**解いている。

## 検証（すべて現在の二値）

**ここに挙げた検査は全部、2026-09-23 の二値（符号つき文脈・恒等の退避路・
パルス構造・曲面を入れたあと）で、他の測定と重ねずに 1 本ずつ取り直した。**以前はこの見出しに「すべて現在の二値」と書きながら、
