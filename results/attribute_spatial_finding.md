# 属性の空間予測 — 幾何は先に復号されるのだから、順序を幾何から導いてよい

## なぜこれを測ったか

幾何側の 4 方向（点間隔以下の文脈・反復測量の差分・ECT・位相）は全て閉じた。
一方で AHN4 のビットの内訳は **幾何 41% / 属性 59%** であり、
属性については「A は B の完全な複製か」しか調べていなかった。
ビットの多いほうを調べていなかった。

## 発端 — 属性は 2 群にきれいに割れる

AHN4 60万点で、属性を「格納順の 1 つ前」で予測した場合と
「空間最近傍」で予測した場合の 0 次エントロピーを比べた。

| フィールド | 格納順差分 | 空間最近傍差分 | 改善 |
|---|---|---|---|
| Reflectance | 9.415 b | 9.343 b | 0.8% |
| intensity | 9.413 b | 9.141 b | 2.9% |
| Deviation | 4.390 b | 4.278 b | 2.6% |
| **blue** | 5.420 b | 3.060 b | **43.6%** |
| **nir** | 5.284 b | 2.973 b | **43.7%** |
| **green** | 5.411 b | 3.050 b | **43.6%** |
| **red** | 5.419 b | 3.056 b | **43.6%** |

レーザー由来の 3 フィールドは空間的に滑らかでない（スペックルと入射角依存）。
RGB+NIR はオルソ画像から点に貼り直した値なので、元が滑らかな 2 次元ラスタである。
**本来は画像なのに、点ごとの測定値であるかのように格納されている。**

## 方法 — 符号化の順序そのものを幾何から導く

容器は幾何を先に復号する。つまり**復号器は属性を読む前に全点の座標を持っている**。
したがって次の 2 つが許される。

1. 属性を符号化する順序を幾何から導いてよい（Morton 順）
2. その順序で先行する空間最近傍を予測に使ってよい

符号化器と復号器はまったく同じ順序表・近傍表を組めるので、副情報は要らない。
色にはさらに**可逆**の色変換 YCoCg-R を掛ける。

```
Co = R − B ;  t = B + (Co>>1) ;  Cg = G − t ;  Y = t + (Cg>>1)
逆: t = Y − (Cg>>1) ;  G = Cg + t ;  B = t − (Co>>1) ;  R = Co + B
```

予測子は **1 個（最近傍のみ）が最良**だった。3 個の平均を取ると悪化する
（AHN4 の RGB で 31.1% → 16.9%）。

### AHN4 60万点・RGB 合計での比較

| 方式 | RGB 合計 | 可逆 |
|---|---|---|
| 格納順差分（チャネル独立） | 16.220 bpp | ○ |
| YCoCg-R のみ（格納順） | 9.965 bpp | ○ |
| Morton 空間予測のみ | 11.179 bpp | ○ |
| **YCoCg-R + Morton 空間予測** | **6.430 bpp** | ○ |

色の脱相関と空間予測は独立に効き、重ねると掛け算になる。

## G-PCC は既にこれを取っているか — 取っていない

mpeg-pcc-tmc13 v23.0 に同じ 60万点を通した（幾何は可逆、色は QP=4）。

| 方式 | RGB 合計 | 可逆 | 実測の最大誤差 |
|---|---|---|---|
| G-PCC RAHT | 11.977 bpp | **×** | **±1**（後日判明・下記訂正） |
| G-PCC Predicting | 11.936 bpp | ○ | 0 |
| G-PCC Lifting | 11.513 bpp | **×** | **±3**（後日判明・下記訂正） |
| G-PCC Predicting + YCbCr | 6.588 bpp | **×** | ±1（59.3万点が不一致） |
| **本手法** | **6.430 bpp** | ○ | 0 |

> **訂正（2026-09-18）**: RAHT と Lifting の「可逆・誤差 0」は誤りだった。
> 当時 全点照合したのは Predicting だけで、他の 2 つは未検証のまま可逆と記していた。
> QP を 0/1/4/8 で振って照合し直したところ、**可逆になるのは Predicting・QP=4 のみ**である。
> したがって「G-PCC の可逆最良は Lifting 11.513」も誤りで、正しくは Predicting 11.936。
> 詳細は `end_to_end_comparison.md`。

**重要**: tmc13 の `convertPlyColourspace=1`（RGB→YCbCr）は**可逆ではない**。
6.588 bpp という数字はここから出ている。復元して全点照合するまでこれに気づかず、
一度は「G-PCC に負けた」と判断しかけた。可逆同士で比べると本手法が 44% 良い。

なお最初の tmc13 実行では属性パラメータを `--attribute` より**後ろ**に置いたため
全設定で同じ結果（15.62 bpp）が出ていた。tmc13 は前に置くことを要求する。

### 部分標本では測れない

既報では「先頭 200万点の数字は全体を 0.2 ポイント以内で代表していた」と
確認していたが、**空間予測についてはこれが成り立たない**。

| | 先頭 200万点 | 全点 |
|---|---|---|
| AHN4 | 2.42% | **6.07%** |
| AHN5 | 6.65% | **9.96%** |
| AHN3 | 5.13% | **5.88%** |
| workshop (TerraScan) | 6.37% | **4.70%** |
| autzen-2023 | 1.03% | **3.82%** |

LAS は空間順に並ぶので先頭 200万点はタイルの細い帯であり、
Morton 順に並べ替えても近傍が遠い。空間予測の効き目は点の込み具合に依存する。
ずれは**過小にも過大にもなる**（workshop は部分標本のほうが良く出ていた）。
部分標本の bpp はそもそも全体の bpp と違うので、比率も直接は比べられない。

**この操作については部分標本で測ってはいけない。** 上の表は全点で測り直した。

## これが重要な理由 — 「1 データ特化」からの脱出

これまでの −23.8% は AHN4 の配布設定に固有の重複（`Amplitude ≡ intensity`）
に由来しており、他の 10 ベンダでは 0.0〜0.1% しか縮まなかった。

空間予測は**その制約を外す**。

- **TerraScan の workshop_TM_551_101**: ExtraBytes なし・重複なしで、
  従来は正規化レイヤーが何もできなかった。今回 **−6.36%**
- **YellowScan の fullwave**: 同じく従来 0%。今回 **−12.25%**
- **AHN5**: `Amplitude ≡ intensity` を持たない（AHN4 と設定が違う）。
  従来 −0.77% が **−7.36%** に

つまり削減の根拠が「配布側の設定ミス」から
「**属性の格納表現と本来の表現のずれ**」に移った。後者はずっと一般的である。

## 「LASzip より弱い」は誤りだった — 訂正

初報でこう書いた。

> **LASzip は我々の差分符号器より上手い。** AHN4 で容器から出した 6 フィールドは
> LASzip 内で 9.607 bpp、空間残差にすると 8.298 bpp で、差は 14% しかない。

**これは比較対象がずれている。** 9.607 bpp は「空間予測なしの容器」と
「ありの容器」の差だが、前者では既に red と green が残差として外部に出ていたため、
容器側にその 2 列は含まれていなかった。6 列分の費用ではない。

条件を揃えて測り直した（AHN4 200万点、red/green/blue/nir の 4 列だけ）。

| 方式 | 4 列の合計 |
|---|---|
| LASzip（LAZ の中で） | 14.537 bpp |
| 本実装・格納順差分 | 14.447 bpp |
| **本実装・YCoCg-R + Morton 空間予測** | **11.584 bpp** |

LASzip との比較は **ほぼ互角（差 0.6%）** であり、空間予測を入れると
**20.3% 良い**。「45% 負けている」は事実ではない。

### 容器から外した列は二重払いになっていないか

`write_las` は容器から外した標準次元を削除ではなく 0 で埋める。
0 の列が LASzip 上でタダでないなら、同じフィールドに容器側と外部側で
二重に払うことになる。測った（AHN4 200万点）。

```
fmt8 全部入り           12,205,577 bytes   48.822 bpp
fmt8 色を 0 埋め         8,571,347 bytes   34.285 bpp
fmt6 色の列が存在しない   8,570,701 bytes   34.283 bpp
                         -------------------------------
0 埋めした 4 列の残存費用      646 bytes    0.003 bpp
```

**二重払いは起きていない。** LASzip は定数列をほぼ完全に潰す。
点形式を 8 から 6 に落として列ごと消しても 646 バイトしか変わらない。

また、外部ストリームは LAZ のバイト列ではなく**復号した生の値**に対して
符号化しているので、圧縮の重ね掛けにもなっていない。

### では端から端までの伸びが 6.07% にとどまるのはなぜか

単純に、改善した対象がビット全体の 27% だからである。

```
色 4 列は正規化後 54.349 bpp のうち約 14.5 bpp（27%）
それを 20.3% 改善 → 2.95 bpp → 全体の 5.4%
実測 6.07%（bit_fields と classification の分が加わる）
```

符号器が弱いのではなく、**残り 73% にまだ手を付けていない**。

## 限界

フィールド単体で測った改善幅（色 4 列で 20.3%）は、そのまま容器の削減にはならない。
容器から 1 列外したときの LASzip の減り分は、その列の単体費用とは一致しないからである
（LASzip は列をまたぐ文脈を使う）。採否の物差しに自前の差分符号器を使っているのは
その意味で甘く、合計を両方書いて比べる保険で悪化は防いでいるが、選択自体は最適ではない。

**まだ手を付けていないのは残りの 73%** — 幾何 22.2 bpp（41%）と
Reflectance 9.8 bpp（18%）。後者は空間的に滑らかでないことを確認済みで、
レーザーの戻り強度そのものなので圧縮しにくい。

対象は LAS/LAZ の 12 ファイル、生成元 9 種。TLS・MMS・水中ソナーは未検証。
