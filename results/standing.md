# 既存技術と比べて、いまどこに居るのか

2026-09-21 の測定。標本は各ファイルの**中央 200 万点**（足りないファイルは全点）。
20 万点でも測ってあり、**サイズはほとんど動かないが速度とメモリは規模で変わる**
ので、両方を併記する。すべて可逆で、往復検証とスレッド数を変えた決定性の確認を
通っている。測り直しは `python/bench_all.py`（サイズ・速度・メモリ）、
`python/bench_three.py`（三者比較）、`python/bench_split.py`（幾何と属性の内訳）、
`python/bench_cover.py`（どの次元が戻るか）。

---

## 0. 土俵を先に決める

**相手によって比べられる範囲が違う。**ここを混ぜると数字が意味を失う。

| 相手 | 何を符号化するか | 比べられる範囲 |
|---|---|---|
| **LASzip（LAZ）** | LAS の点レコード全部 | 幾何も属性も |
| **G-PCC** | 幾何だけ | **幾何のみ** |

したがって三者を並べられるのは幾何だけである。属性込みの比較は LASzip としか
できない。以下、表の見出しに必ず土俵を書く。

**さらに、PCC2 が読まない次元がある**（§4）。サイズの比較は「PCC2 が読む列」に
揃えてあり、基準の LAZ も同じ列で作り直しているので比較自体は公正だが、
**LAZ の置き換えとしてそのまま使える段階ではない。**

## 1. 一言でいうと

| | ひとこと |
|---|---|
| **サイズ** | 属性込みなら LASzip より **12.1% 小さい（15/15）**。幾何だけなら G-PCC と**互角**、LAZ より 9% 小さい |
| **速度** | 符号化は G-PCC の **0.85 倍**（速い）、LASzip の **15.4 倍**（遅い）。復号は LASzip の **7.9 倍** |
| **メモリー** | 三者で最も重いが詰めた。G-PCC の **3.3 倍**、LASzip の **6.5 倍**。候補を 1 本に固定した幾何のみなら**全規模で G-PCC を下回る** |
| **可逆の範囲** | 読んだ列は完全に戻る。**読まない次元が 13/15 のファイルにある** |

**強みは属性にある。**幾何だけを見ると横並びだが、属性を入れると差がつく（§3）。

## 1.5 利用者から見た end-to-end — さっぱりした結論

利用者は LAS/LAZ を 1 本渡して、小さくなったものを受け取り、元に戻したい。
その土俵で見ると話は単純になる。

### G-PCC はこの土俵に出られない

**幾何しか符号化しない。**しかも LASzip が使う bit のうち
**属性が中央値 59.2%（幅 27.7〜71.9%）を占める。**
つまり G-PCC 単体では、ファイルの 6 割を占める部分に手が出ない。
使うなら属性の符号器を別に用意することになり、その時点で「G-PCC の性能」は
組み合わせた相手次第になる。

### 欠けている次元を勘定に入れても PCC2 が小さい

PCC2 は一部の次元を読んでいない（§4）。**その次元を LASzip が符号化するのに
使っている bit をそのまま足して**見積もると、こうなる。

| データ | LASzip | PCC2（読む列） | 欠けの費用 | PCC2（埋めた） | 対 LASzip |
|---|---|---|---|---|---|
| AHN4 _20 | 69.817 | 44.750 | 0.035 | 44.785 | **−35.9%** |
| AHN4 _21 | 77.401 | 52.997 | 0.011 | 53.008 | −31.5% |
| plane | 16.844 | 12.484 | 0.155 | 12.639 | −25.0% |
| extra | 218.471 | 132.920 | **34.208** | 167.128 | −23.5% |
| workshop | 37.091 | 30.314 | 0.693 | 31.007 | −16.4% |
| fullwave | 149.503 | 54.542 | **76.023** | 130.565 | −12.7% |
| vegetation | 49.845 | 43.568 | 0.000 | 43.568 | −12.6% |
| red-rocks | 20.749 | 18.480 | 0.002 | 18.482 | −10.9% |
| USGS NY | 38.710 | 34.797 | ≤0 | 34.797 | −10.1% |
| autzen_trim | 43.880 | 39.262 | 0.373 | 39.635 | −9.7% |
| USGS AK | 35.629 | 32.228 | 0.169 | 32.397 | −9.1% |
| AHN5 _20 | 59.091 | 53.763 | 0.009 | 53.772 | −9.0% |
| autzen-2023 | 66.665 | 60.720 | ≤0 | 60.720 | −8.9% |
| simple1_4 | 17.730 | 16.601 | 0.069 | 16.670 | −6.0% |
| AHN3 _20 | 53.702 | 50.593 | 0.044 | 50.637 | −5.7% |

**15/15 で小さい。中央値 −10.9%（中央 200 万点）。**欠けが効くのは
fullwave（元の 50.9%）と extra（15.7%）の 2 件だけで、残り 13 件では
中央値 0.1% にすぎない。

見積りの限界: 「欠けの費用」は 元の .laz と pccnorm が書く基準 LAZ の差である。
3 件で負になっているのは、基準を書く LAZ 書き出しが元のファイルより効率が
悪いためで、欠けの費用が負なのではない。それらは 0 として扱った。

### さっぱりまとめると

| 何を重く見るか | 選ぶべきもの |
|---|---|
| **サイズだけ** | **PCC2**（end-to-end で −10.9%、15/15。中央 200 万点） |
| **速度・メモリ・互換** | **LASzip**。符号化 14.5 倍速く、メモリ 8 分の 1、全次元が戻り、どこでも読める |
| **ファイル 1 本を丸ごと** | **G-PCC は候補に入らない**（属性が bit の 6 割） |

**いま LAS ファイルを配るなら LASzip である。**PCC2 が置き換えを名乗るには、
読まない次元を埋めること（§4）と、メモリ（§6）を詰めることが要る。
サイズの利得（−10.9%）はその工事に見合う大きさである。

## 2. サイズ

### 2.1 幾何のみ — 三者比較（15 ファイル）

ファイルごとに比を取ってから中央値を出す（中央値どうしを割ると別の量になる）。

| | 中央値 | 四分位 | 幅 |
|---|---|---|---|
| PCC2 / G-PCC | **1.00x** | [0.95, 1.21] | 0.73〜2.21 |
| PCC2 / LASzip | **0.91x** | [0.88, 0.97] | 0.81〜1.01 |

17 ファイル（車載・地上型を含む）まで広げると、PCC2 が G-PCC に勝つのは
**9/17**、対 G-PCC の中央値 **−3.7%**。LAZ に負けるのは 2/17。

**勝敗はファイルで入れ替わる。**最良は AHN4 _20 の −23.6%、最悪は合成平面の
+121.4%（八分木が 2.775 bpp で収める）。符号化アルゴリズムの優劣で説明できる
差ではない。

### 2.2 属性込み — 対 LASzip（15 ファイル）

| | 中央 200 万点 | 中央 20 万点 |
|---|---|---|
| PCC2 が小さい | **15/15** | 15/15 |
| 中央値 | **−12.1%** | −12.6% |
| 四分位 | [−25.3, −9.3] | [−25.3, −8.2] |

---

## 3. 優位はどこから来ているか

同じ入力を全列と幾何のみで測り、差を属性ぶんとした（容器の頭のぶんだけ目安）。

| | 中央値 | PCC2 が小さい |
|---|---|---|
| 幾何 | −9.2% | 13/15 |
| **属性** | **−18.2%** | **15/15** |
| 全体 | −12.1% | 15/15 |

**属性の優位は幾何の 2 倍あり、しかも全ファイルで勝っている。**幾何は 2 件で
負ける（simple1_4 +1.1%、vegetation ±0.0%）。

効いているのは、幾何から導いた順序で属性を予測すること（空間予測）と、
既出の列との残差を候補に持つこと（参照残差）である。どちらも幾何が先に
復号されている容器だから書ける。

---

## 4. 可逆の範囲 — 但し書き

`pack` → `unpack --las` で戻すと、**元の LAS の次元が 1 つ以上戻らない
ファイルが 13/15** ある。読み取りが列にしていないものがある。

| 戻らないもの | 該当 |
|---|---|
| `scan_direction_flag` / `edge_of_flight_line` / `scanner_channel` | 旧形式を含む多く |
| 分類のフラグ（`overlap` など）、`scan_angle_rank` | AHN3、旧形式 |
| 波形の 7 種 | fullwave |
| 拡張バイトの一部 | extra |
| VLR | ほぼ全て |

`bit_fields` は戻り番号 4 bit と戻り総数 4 bit しか詰めていない。
**`検証 全列一致 = true` は「PCC2 が列として持ったもの」しか見ない。**

## 5. 速度

### 5.1 属性込み — 対 LASzip（15 ファイル）

| | 中央 200 万点 | 中央 20 万点 |
|---|---|---|
| 符号化 | **15.4x** [10.5, 21.1] | 14.6x |
| 復号 | **7.9x** [1.6, 10.4] | 4.0x |

**復号の比は規模で倍になる。**点数に比例して増える近傍表（順序表・KD木・k 近傍）が
効くためで、LASzip 側は素直に伸びる。**速度を述べるときは規模を必ず添えること。**

符号化が復号より掛かるのは、**候補を全部符号化して最短を採る**ためである。
復号は選ばれた 1 本しか通らない。

### 5.2 幾何のみ — 三者比較

| | 中央 200 万点 | 中央 20 万点 |
|---|---|---|
| PCC2 / G-PCC | **0.85x** [0.67, 1.10] | 0.93x |
| PCC2 / LASzip | 10.65x [0.69, 17.01] | 2.40x |

候補を 1 本に固定して規模を変えると（AHN4 _20、幾何のみ、符号化のみ）:

| 点数 | G-PCC | 幾何v3 | 走査v1 |
|---|---|---|---|
| 50 万 | 0.91 s | **0.29 s** | **0.33 s** |
| 100 万 | 1.86 s | **0.60 s** | **0.66 s** |
| 200 万 | 3.77 s | **1.19 s** | **1.86 s** |
| 400 万 | 8.50 s | **2.63 s** | **3.03 s** |

**約 3 倍速い。400 万点まで保つ。**

## 6. メモリ

### 6.1 幾何のみ — 三者比較

| | 中央 200 万点 | 中央 20 万点 |
|---|---|---|
| PCC2 / G-PCC | **3.32x** [0.94, 4.97] | 2.19x |
| PCC2 / LASzip | **6.53x** [6.07, 7.37] | 8.38x |

候補を 1 本に固定して幾何だけを測ると、**メモリーは全規模で G-PCC を下回る**。

| 点数 | G-PCC | 幾何v3 | 走査v1 |
|---|---|---|---|
| 50 万 | 102 MB / 0.94s | **30 MB / 0.22s** | 77 MB / 0.27s |
| 100 万 | 161 MB / 1.86s | **53 MB / 0.43s** | 146 MB / 0.55s |
| 200 万 | 147 MB / 3.76s | **92 MB / 0.87s** | 285 MB / 1.10s |
| 400 万 | 265 MB / 7.89s | **206 MB / 1.77s** | 592 MB / 2.26s |

規模が大きいほど開く。G-PCC はスライスで working set が頭打ちになり、
こちらは点数に比例して伸び続けるためである。

規模を変えると差は開く（AHN4 _20、幾何のみ、候補を 1 本に固定）。

| 点数 | G-PCC | 幾何v3 |
|---|---|---|
| 50 万 | 102 MB | 116 MB |
| 100 万 | 161 MB | 230 MB |
| 200 万 | **147 MB** | 457 MB |
| 400 万 | 266 MB | 875 MB |

G-PCC はスライスに切るので working set が頭打ちになる。こちらは点数に比例する。

### 6.2 属性込み

1 点あたり中央値 **529 byte**（200 万点、全列）。20 万点では 1038 byte だが、これは固定費が薄まる前の値である。

### 6.3 既知の退行

**直した**（記録 70〜72 節）。全列 1 点あたり 866 → 529 byte、符号化のみの
ピーク 1557 → 906 MB、復号 714 → 459 MB。サイズは 1 bit も犠牲にしていない。
残りは「候補を全部試す」「P を 1/3/5 とも試す」という設計そのものに由来し、
削るとサイズを損なう。

---

## 7. 読み方

1. **幾何だけで見ると三者は横並びである。** 中央値の差は数 % で、ファイルごとに
   勝者が変わる。ここだけを見て優劣は言えない。
2. **差がつくのは属性である。** 15/15 で勝ち、中央値 −18.0%。幾何を先に復号して
   その順序と近傍を属性の予測に使う、という容器の作りが効いている。
3. **速度は相手で評価が逆になる。** G-PCC より速く、LASzip より 1 桁遅い。
   遅さの主因は候補を全部試すことで、復号は 4.4 倍に収まる。
4. **メモリは負けている。** 三者で最も重く、点数に比例して増える。
5. **可逆の範囲が LAZ に届いていない。** これは性能ではなく機能の差で、
   置き換えを名乗るには埋める必要がある。

## 付録 — 図にしたもの

- ページ（グラフつき）: `https://claude.ai/artifact/35ZvFH1cgT521zXTPp463R`
- 論文 `paper/coding.tex` の Figure 1（§7.1 Where the bits are）:
  (a) 属性が符号長に占める割合を 15 ファイルで測ったもの、
  (b) 幾何側と属性側それぞれの縮みを散布図にしたもの（対角線より上＝属性側が効く）。

論文はもともと「attributes hold 59%」と 1 タイルから述べていた。15 ファイルの
測定（中央値 59.2%）はそれを独立に裏づける。

**キャプションに誤りを書きかけた。**「30% を下回る 2 件は、色も近赤外も持たない
唯一のファイルである」と書いたが、色を持たないのは **4 件**（USGS AK / USGS NY /
workshop / vegetation）だった。書いた後に点形式を確かめて気づいた。
正しくは「色を持たない 4 件が、割合の下位 4 件と正確に一致する。色を持つ
ファイルはどれも符号長の半分以上を属性に使う」で、こちらのほうが強い主張である。
