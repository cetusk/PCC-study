# 正規化後に何が残っているか / 外部に出すと得か

## 正規化後の内訳（AHN4 200万点, 合計 54.082 bpp）

`pccnorm residue` で、各フィールドを 1 つずつ潰した実測差を取った。
孤立コストではなく「既存コーデックが実際にそのフィールドに使っているビット数」。

| フィールド | bpp | 割合 |
|---|---|---|
| 幾何 (XYZ) | 22.211 | 41.1% |
| Reflectance | 9.774 | 18.1% |
| blue | 5.253 | 9.7% |
| nir | 5.078 | 9.4% |
| Deviation | 4.727 | 8.7% |
| green (外部) | 2.111 | 3.9% |
| red (外部) | 1.990 | 3.7% |
| intensity (外部) | 1.554 | 2.9% |
| gps_time | 1.541 | 2.8% |
| classification | 0.656 | 1.2% |
| その他 | 0.36 | 0.7% |

## 仮説と検証

**仮説**: 外部に出した `intensity` は順序0エントロピー 6.280 bit に対して
実測 1.554 bpp と安い。差分+レンジコーダのおかげなら、残差の相手が
見つからなかった `Reflectance`・`blue`・`nir`・`Deviation`（合計 24.8 bpp）も
単に外部に出すだけで安くなるはず。

**結果**: 外れた。`pccnorm extern`（AHN4 20万点）

| フィールド | 容器 | 外部 | 差 | 判定 |
|---|---|---|---|---|
| Reflectance | 10.010 | 9.694 | +0.316 | 外部が得 |
| user_data | 0.618 | 0.003 | +0.615 | 外部が得 |
| blue | 5.419 | 5.363 | +0.056 | 外部が得 |
| nir | 5.232 | 5.204 | +0.028 | 外部が得 |
| Deviation | 4.676 | 4.755 | −0.079 | 容器が得 |
| classification | 0.746 | 0.981 | −0.235 | 容器が得 |
| gps_time | 1.534 | 2.344 | **−0.810** | 容器が得 |

合計利得 **1.016 bpp**（全体の 2%）。期待した規模に遠く及ばない。

**なぜ外れたか**: `intensity` が安いのは差分符号化のおかげではなく
**残差だから**。`intensity − Reflectance` は物理的にほぼ距離の関数で滑らか。
一方 `Reflectance` 単体は隣接点でも相関が弱く、差分を取っても縮まない。

**LASzip は各フィールドを既にほぼ順序0エントロピーまで符号化していて、
単純な差分+レンジコーダはそれを上回れない。** `gps_time` が −0.810 と
最も損なのも、LASzip が専用の予測器を持つためで整合的。

Bunny 生スキャンで見た「冗長があることと既存コーデックが取り逃していることは
別問題」と同じ構図だった。

## 判断

**実装しない。** 利得 1.016 bpp に対し、フィールドごとに LAZ を書き直す実測が
必要でコストが見合わない。`extern` は診断ツールとして残す。

## 副産物

`user_data` が 0.618 → 0.003 bpp。ほぼ定数（2 値）なのに LASzip が 0.6 bpp
使っている。全体への寄与は 1.2% だが、他のデータで同様の定数に近い
フィールドがあれば効く可能性がある。

# この検証中に見つけたレンジコーダのバグ（重大）

`extern` の初回実行が **35 分以上ハング**した。原因は連鎖していた。

| # | 内容 | 影響 |
|---|---|---|
| 1 | C++ は `gps_time` を float64 の**ビットパターン**（約 4.7e18）として持つ。Python は値（約 2.7e8） | C++ 側だけ巨大な値が流れる |
| 2 | `UIntCoder` の `max_k = 32` に対し k が 62 に達し、`prefix_[k]` が**配列外** | BitModel が壊れる |
| 3 | Python の `zigzag` が int64 で桁溢れ（`v << 1` が負） | `assert v >= 0` で停止 |
| 4 | `decode_ints` の出力が int64 で `2^63` 以上を受けられない | OverflowError |
| 5 | **`t >> 64` が未定義動作**。x86 では `t >> 0` になり `while` が抜けない | **無限ループ（真の原因）** |

5 は、2 を直すために上限を外したときに**自分で混入させた退行**だった。

修正後、**int64 全域（`2^63-1` と `-2^63` を含む）で Python と C++ が
バイト一致**することを 7 ケースで確認した。
