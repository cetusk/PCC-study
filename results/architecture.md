# 現状の構成（2026-09-22）

いま動いているものの**組み立て**を、コードから起こした一覧。
数値の出どころは `data/work/grid/bench_2m_v4.log` ほか（`standing.md` §0 参照）。
「なぜそうしたか」は `results/losses.md`、「何が負けたか」は同 §15〜§21。

---

## 0. 一言で

**列ごとに、符号器の候補を実際に符号化して、いちばん短いものを採る。**
恒等候補（`raw64`）をどの列にも混ぜてあるので、**どの列も自前の符号器の中では
恒等より長くならない**。幾何を属性より先に復号する器なので、属性の予測子は
座標を副情報なしで使える。

**「全部」ではない。**推定で切り落とす段が 2 つある — 幾何の予備選別（§6）と、
属性の参照先の絞り（`XKEEP = 2`、§5.3）。それ以外は実測で決める。

## 1. 全体の流れ

```
入力（.las/.laz/.bin/.ply）
  │
  ├─ 1) 器を読む      .las/.laz → las.cpp   .bin → frame.cpp   .ply → las.cpp
  ├─ 2) 格子を見つける       grid.cpp                     → float を可逆に整数化
  ├─ 3) 正規化              normalize.cpp analyze()      → Plan（落とす列）
  ├─ 4) 列に並べ替える       frame.cpp                    → Frame（列 + スキーマ + 封筒）
  ├─ 5) 粗い格子で割る       frame.cpp apply_column_grid  → coldiv ※LAS の経路だけ
  ├─ 6)〔非可逆〕量子化      geom.cpp + main.cpp --eps    → 既定では通らない
  │
  ├─ 7) 流れを計画する       pcc2.cpp plan_streams        ← ここが本体
  │      列ごとに候補を並べ、符号化して最短を採る
  │
  └─ 8) 器に書く            pcc2.cpp write_pcc2          → .pcc2

復号は 7→1 を逆にたどる。器は自己記述的で、点数もスキーマも外から渡さない。
```

**3 が 4 より先なのは、メモリのため。**計画を先に立てれば、残す列だけを
`PointCloud` から**移して** `Frame` に渡せる。逆順だと同じ中身を同時に 2 つ
持つ瞬間ができる（100 万点の LAS で 147 MB のうち 95 MB がその二重持ちだった）。

`main.cpp` の `pack` は既定で、**まず決定性**（もう一度符号化してバイト一致）を
確かめ、**次に復号して元と突き合わせる**。この順なのは、決定性の確認に符号化側の
`Frame` と流れが要るためで、先に済ませればそれを手放してから復号に入れる。
**`--no-verify` で両方飛ぶ。ベンチのスクリプトは速度とメモリを他の符号器と
同じ土俵で測るために全部これを付けている**ので、検証は別走（`roundtrip_all.log`）で取る。

## 2. 入力側

### 2.1 器を読む

| 器 | 経路 | 備考 |
|---|---|---|
| `.las` / `.laz` | `las.cpp`（laszip の C API） | 点形式 0〜10。EVLR は LAS を直に読む（C API が配列で出さない） |
| `.bin`（KITTI） | `frame.cpp` の `load_kitti` | float32 × 4（x, y, z, 強度） |
| `.ply` | `las.cpp` の `read_points_any` | ascii / binary、float32 / float64 |

（`pccfile.cpp` は PCC1 の古い器で、いまの経路からは呼ばれない。）

**運ぶものは「読めた列」ではなく「元のファイルを再現できるもの」全部。**
点の次元・VLR・EVLR・LAS ヘッダの欄・ExtraBytes の配列型・波形パケットの
29 byte を、封筒（`Frame::envelope`）と列に分けて持つ。

### 2.2 float の座標を整数に直す（`grid.cpp`）

点群を float で持つ器は、中身が整数のことがある。
**候補は統計で探し、採否はビット単位の証明で決める** — 刻み `s` について
全点で元のビット列が再生できることを確かめ、1 点でも再生できなければ採らない
（`-0.0` だけは符号が消えるので位置を別に覚える）。道は 2 本ある:
`round(v/step)` と、**十進の `round(v*10^d)`**。十進の文字列から来た値は
`10^-d` を掛けても戻らない（2 進で表せない `10^-d` を先に丸めてしまう）ので、
`10^d` で割る道が要る。

KITTI の `.bin` で 1 mm 格子が見つかる。整理後の PCC2 は**ファイル全体で
22.300 bpp**、素の `.bin`（float32 × 4 = 128.000 bpp）に対して **−82.6%**
（幾何のみなら 17.520 bpp）。**これは整数化単体の効果ではなく、
整数化を含めた現在の符号化全体の値である。**

### 2.3 列が粗い格子に乗っていたら割る（`apply_column_grid`）

宣言された分解能が実際の分解能とは限らない（8 bit の色を 16 bit 欄に
入れた LAS など）。列ごとに `(最小値, 刻み)` を見つけて割る。15 件中 7 件で縮み、
中央値が −12.1% → −14.0% になった。**幾何を割ったときは scale/offset も
合わせて動かす**ので、世界座標は 1 ミリも変わらない。

### 2.4 正規化（`normalize.cpp`）

フィールド名をハードコードせず、**列どうしの関係をデータから見つける**。

| 種類 | 何をするか |
|---|---|
| `drop_constant` | 定数列を落とす（値だけ計画に残す） |
| `drop_duplicate` | 同一の列を落とす |
| `drop_affine` | `b = num/den * a + b0` が全点で成り立つ列を落とす |
| `residual_code` | 関係が概ね成り立つ列を、残差だけ持つ |

**`residual_code` は `pack` の経路では一度も作られない。**`pack` は
`residual_ops = false` で `analyze` を呼ぶので、生成されるのは上 3 つの
「厳密な構造の操作」だけである。概ねの関係は符号器側の `参照<列>`（§5.3）が
担当する（そちらは実測で採否が決まるので、見積りで取りこぼさない）。

**前に出す 3 列は落とさない。**`point_source_id` / `gps_time` / `bit_fields` は
定数列でも `drop_constant` の対象から外してある。落とすと走査モデルを候補として
提示できなくなるためで、§4 の順序と対になっている。

**採用は全点検証を通ったものだけ。**計画は二値で器に入る（JSON をそのまま
入れていた頃は 333 byte、いまは 49 byte）。

## 3. 列（`col.hpp`）

`Col` は `base + （詰めた符号なし整数）`。幅は列の値域から 1/2/4/8 byte を選ぶ。
**定数列は 8 byte で済む。**64 bit 固定で持つと 200 万点 × 17 列で 272 MB になる。

`Frame` はこれを名前で引く地図と、出現順のスキーマ（＝元のファイルの列の並び）を持つ。
各列は `Raw`（そのまま入っている）/ `Derived`（計画から復元する）/
`Residual`（他の列との残差で入っている）のどれか。

---

## 4. 流れの順序 — なぜ `gps_time` が幾何より前か

器は**書いた順に復号する**。したがって「先に置いた列は、後の列の予測に副情報
なしで使える」。この一点が構成全体を決めている。

```
1) point_source_id, gps_time, bit_fields     ← 走査モデルが要る 3 列
2) X + Y + Z                                  ← 幾何（3 軸まとめて 1 本の流れ）
3) それ以外の属性                              ← 座標が揃っているので空間予測が使える
```

- **1 を前に出す理由**: 走査モデル（`C_GEOM_SCAN`）は飛行線と掃引を組み直すのに
  時刻と線番号が要る。前に出しておけば、幾何の符号器に副情報を持たせずに済む。
- **代償**: 前に出した 3 列自身は空間予測を候補に持てない（座標がまだ無い）。
  だから**走査モデルが要る 3 列だけ**に限ってある。
- **属性が後ろ**: `intensity` は `point_source_id` を文脈にでき、
  `classification` は `intensity` を文脈にできる。この鎖が属性側の利得の源。

**点の順序は並べ替えない。**Morton 順に直すと全列で **+25.9%** 伸びる
（`gps_time` が 3.066 → 19.168 bpp）。順序は代償ではなく資産である。

## 5. 符号器

### 5.1 汎用の符号器

**どの列にも全部出るわけではない。**属性の列には下の 10 種が全部出る。
幾何（`X+Y+Z`）に出るのは `raw64` / `素4B` / `range` / `delta` の**4 つだけ**で、
`ctx` / `ctx2` / `med3` / `差分表` / `直前` / `字母` は出ない
（代わりに §5.2 の幾何専用の系統が出る。基底は 58 本）。
幾何より前に出す 3 列には `素<幅>B` が出ない — **この 3 列の恒等候補は
64 bit の `raw64` だけで、「自然な幅を超えない」は保証されていない。**

| id | 名前 | 中身 |
|---|---|---|
| 0 | `raw64` | **恒等候補。**1 値 64 bit。これがあるので器の長さは有限で閉じる |
| 13 | `素<幅>B` | 列の自然な幅でそのまま。1 byte の列の天井（raw64 では天井にならない） |
| 1 | `range` | zigzag + レンジ符号 |
| 2 | `delta` | 1 次差分 |
| 3 | `ctx` | 1 次差分＋**直前の差分の桁数**を文脈に |
| 4 | `ctx2` | 2 次差分＋文脈（一定刻みの列） |
| 5 | `med3` | 直近 3 差分の中央値を予測子に |
| 6 | `差分表` | 直近 K 個の相異なる差分の表を指す |
| 7 | `直前` | **値そのもの**を直前の値を文脈に（1,2,3,1,2 と繰り返す詰め込みビット） |
| 8 | `字母` | 値の種類が少ない列を、字母のまま直前の記号を文脈に送る |

`字母` は既出の列を**文脈**に使える（残差ではなく文脈なので、相関が単調でなくてよい）。
USGS NY の `bit_fields` が 2.221 → 1.539 bpp。

### 5.2 幾何（3 軸まとめて 1 本）

**文脈は残差の桁数で作る。**`ctx_of(zigzag(残差))` を軸ごとに持ち、
後の軸は前の軸の桁数も見る。桁数は符号を捨てるので、旗 `符1/符2/符4` で
**直前の残差の符号**を文脈に足せる（§5.4）。JPEG-LS が符号つきの勾配を
条件にしているのと同じ考えで、走査線に沿って向きが続く入力に効く。

| id | 名前（`cand_name`） | 中身 |
|---|---|---|
| 9 | `交差軸` | 3 軸を順に送り、後の軸の文脈に前の軸の差の桁数を使う |
| 10 | `幾何v0`〜`幾何v4` | `param[0]` で系統が変わる。下表 |
| 11 | `走査v1`〜`走査v4` / `走査変換`（= v5） | ALS の走査モデル（`scanmodel.cpp`）。飛行線と掃引を当てはめる。5 変種すべてを候補に出す |
| 12 | `向き<予測子>` | y をその点の `dx` から予測（副情報は増えない） |
| 15 | `回転<予測子>` | 主成分に座標系を合わせる。**せん断 3 回で整数のまま可逆** |

`幾何v0`〜`幾何v4` の `param[0]`:

- `0` — 軸ごとに独立（`幾何v0`）
- `1` — 直近 3 差分の中央値（`幾何v1`、`enc_geom_med`）
- `2` — 予測子の**状態を補助列ごとに分ける**（`幾何v2`、`enc_geom_aux`）。
  1 発から複数の点が返る入力では、格納順の隣が走査線上の隣ではない
- `3` — 軸をまたぐ文脈（`幾何v3`）。`param[1]` で予測子と文脈の粗さを切り替える
- `4` — **直近 W 点の最近傍**から予測（`幾何v4`）。格納順が空間的に飛ぶ入力に効く
- `3` + 補助列 — 軸をまたぐ文脈と状態分けを**同時に**持つ（LASzip と同じ構え）

`Pred` は 8 通り: med3 / avg4 / 半分 / med5 / 四半 / 三四半 / **無傾**（直前そのもの）/ med5半。
無傾を足した時点で vegetation の幾何が 24.890 → 23.987 になり、LAZ の 24.535 を
下回った（現在値は **23.963**）。

**回転が整数のまま可逆な理由**: 回転を 3 回のせん断に分解すると各段が
「片方の軸を、もう片方の整数倍だけずらす」になり、丸めが打ち消せる。
π のぶんは符号反転として**厳密に**外に出す。せん断の係数そのものを流れの
先頭に書く（三角関数を復号側で計算すると桁が食い違うため）。

### 5.3 属性

| id | 名前 | 中身 |
|---|---|---|
| 20 | `sp(P=k)` | 幾何由来の順序で**先行する近傍 P 個**から予測（P = 1/3/5） |
| 21 | `色` | 3 列に可逆色変換を掛けてから同上 |
| 22 | `参照<列>` | 既に復号済みの別の列との残差 |

`参照<列>` の**相手は見積りで 2 本に絞る**（`XKEEP = 2`）。差分の 0 次エントロピーと
空間予測つきの見積りは別のものを測るので、それぞれの上位を採る。
**ここが、実測でなく推定で切り落としている 2 か所目である。**

色は「まとめて 1 本」と「汎用の経路が出す 3 本の合計」を**両方測って短いほうを採る**。
さらに blue → green → red の鎖も候補にする。**この 3 通りの比較は、幾何が揃って
いて属性が 1 つ以上残っているとき（`want_spatial`）だけ有効になる。**

### 5.4 旗（符号器 id に重ねる）

| 旗 | 名前 | 中身 |
|---|---|---|
| `0x8000` | 記 | 桁長と下位ビットを**1 記号ずつ**送る（ビットごとに送らない） |
| `0x4000` | 生 | 仮数部の下位を**模型に通さず素通し**。一様なビットに適応模型は害（1 bit が 1.0119 bit に付く） |
| `0x1000` | 束 | 文脈ごとの表が温まるまで**全文脈に共通の表**を使う。送るものは増えない |
| `0x2000` | 照 | 桁長の照合模型。**実装したが候補から外した**（22 列で採用 0 列） |
| `0x0200` | 光 | **同じパルスの続きの点**（戻り番号が 1 増え、戻り総数が同じ、戻り番号 ≥ 2）に別の文脈を割り当て、**傾きの履歴**に入れない（幾何v4 では最近傍を探す窓には残る）。`bit_fields` が幾何より先に復号されるので送るものは増えない。幾何v3・幾何v4・回転に効く |
| `0x0100` / `0x0080` | 面6 / 面7 / 面8 | z を「(x, y) の近くの復号済みの点」からも予測し、直近の成績で 3 つの予測子を切り替える。幾何v4 だけ。**1/15 件で 0.07% しか効かず、符号化の実時間が +19%**。外す第一候補 |
| `0x0800` / `0x0400` | 符1 / 符2 / 符4 | **文脈に直前の残差の符号を 1 / 2 / 4 個足す。**実装した 3 経路（`enc_geom_x` = 幾何v3・回転、`enc_geom_w` = 幾何v4、`enc_resid_x` = 走査 var 3/4）にだけ効く。送るバイトは増えない |

## 6. 選び方（`best_stream`）

```
候補を並べる
  │
  ├─ 予備選別（幾何だけ。**点数が標本の 2 倍を超えるときだけ**発動する）
  │     2 万〜2.5 万点の標本で順位を付け、上位 4 本に絞る
  │     + 族 × 記号版の**直交する 2 軸**で、組ごとに 1 本を必ず残す
  │       （族 1〜5 = 走査 / 空間 / 幾何v4 / 向き / 回転、× 記号版か否か）
  │     + 残った各候補の「記号版・非記号版の対」も一緒に測る
  │     + 勝者の族だけ、あとで詳しく測り直す
  │     **標本の上では打ち切りを掛けない**（控えが欠けて選択が変わるため）
  │
  ├─ 全点で符号化（プールで並列）
  │     最短より長いと判ったものはその場で捨てる（メモリ）
  │
  ├─ 後置検査 1 段目: 勝者に旗を重ねた版を**まとめて並列に**測る。勝者だけに限る
  │     生（勝者がまだ生でないとき）/ 束・生＋束（**勝者が記号版のときだけ**）
  │     符1 / 符2 / 符4（**勝者が幾何v3・幾何v4・回転・走査 var 3/4 のときだけ**）
  │     光・光＋符1/2/4（**勝者が幾何v3・幾何v4・回転で、続きの点があるときだけ**）
  │
  ├─ 後置検査 2 段目: 1 段目の勝者に 面6 / 面7 / 面8 を重ねる（**幾何v4 のときだけ**）
  │
  └─ いちばん短いものを採る（同じ長さなら添字の早いほう）
```

**予備選別には点数の門がある。**小さい入力では候補が丸ごと全点で回る。
vegetation（10,683 点）はこれに当たり、`X+Y+Z` に **116 本**（基底 58 本 ×
記号版の有無）、`intensity` に 54 本、`bit_fields` に 34 本を全点で符号化している。
予備選別が効く規模では数が違う — autzen_trim（110,000 点）では `X+Y+Z` は
標本で 116 本、**全点では 19 本**である。

後置検査が 3 本出るのは勝者が記号版のときだけである。vegetation では
`gps_time` がそれに当たり（記号版が勝っていた）、束ね版が採られて
最終的に `差分表記束` になった。`point_source_id`（`字母`）と
`X+Y+Z`（`回転無傾`）は記号版でないので 生 の 1 本だけを測り、どちらも負けた。
autzen_trim の `X+Y+Z` では 生 が勝って `回転生` になっている。

**族の保護がある理由**: 標本は族の**中**の順位を取り違える。
族の上限を 3 のままにして向き追従（族 4）を足したとき、保護が一度も効かず
TLS p1 が 25.457 → 26.765 に伸びた。

**後置検査を勝者だけに限る理由**: 打ち切り（enc_best）は候補が終わる順で効くので、
どの候補が順位表に残るかは**スレッド数で変わる**。上位 3 本に広げたら
17 件中 3 件で md5 が動いた。勝者は打ち切りに依らず決まる。

## 7. エントロピー符号器（`rangecoder.hpp`）

```
Encoder / Decoder      LZMA 方式のレンジ符号。キャリーは cache/cache_size で伝播
  ├─ BitModel          2 値。p0 を 1/32 ずつ寄せる
  ├─ FreqModel         多値。+32 して、総和の 1/32 ごとに表を作り直す
  └─ UIntCoder         非負整数 = 桁長 k + 下位 k ビット
       ├─ 既定          k を単項、下位をビットごと
       ├─ FSYM（記）    k を 1 記号、k ≤ 8 なら下位も 1 記号
       ├─ RAWKEEP（生） 下位の上から 1 bit だけ模型に通し、残りは素通し
       └─ BUNDLE（束）  文脈の観測数が 24 に届くまで共通の表
```

**表を作り直す間隔は字母の数でなく「加わった重みの相対量」で決める。**
固定にすると序盤が古い表のまま流れる。1065 点の extra で最初の 65 個を
一様な表で送っていた（幾何が 0.25 bpp 伸びていた）。

`encode2/decode2` は**桁長の文脈と下位ビットの文脈を分ける**。
桁が決まったあとの下位の分布は、桁を当てるのに使った文脈にほとんど依らない。

## 8. 器の形（`.pcc2`）

```
マジック + 版
タグつきの頭（順不同・未知のタグは読み飛ばせる）
  1 出所の種類   2 元のバイト数   3 scale   4 offset   5 スキーマ
  6 正規化の計画 7 精度の申告     8 封筒    9 幾何の列名 10 幾何の表し方
  11 包んだ器     12 粗い格子      13 極座標格子
流れの表（列名 → 符号器 id + param + 長さ）
流れの本体（連結）
crc64
```

- **自己記述的** — 点数もスキーマも外から渡さない
- **精度の申告が器の中にある** — ベンチで必ず勘定に入る
- **包んだ器（`T_EMBED`）** — **自前の符号器の出力より、`pccnorm` が書き直した
  基準 LAZ のほうが短いとき**は、その中身をそのまま包んで運ぶ。LAS の入力でだけ
  働く退避路で、包んだ側も PCC2 の頭と crc64 を足すぶんは長くなる。
  保証されるのは「自前の符号器より長くならない」まで。
  **ベンチはこれを `--no-fallback` で切って走らせている**（自前の符号器の実力を
  測るため）ので、報告している数値に退避路は入っていない
- 未知のタグを読み飛ばせるので、タグを足しても古い器は読める

## 9. 非可逆の枝（`pack --eps <m>`、既定では通らない）

浮動小数の座標を持つ器（`.bin` / `.ply`）にだけ使える。

```
世界座標 → choose_geometry（geom.cpp）
             ├─ 極座標格子（回転式 LiDAR）   → geom_repr = "polar" + T_POLAR
             └─ 粗いデカルト格子             → geom_repr = "int" + scale/offset
           → 以降は可逆の経路と同じ
```

**誤差は復号と同じ道を通して測る。**極座標に丸めた誤差だけでは足りない —
復号は世界座標を元の器（1 mm の整数格子、または float32）に書き戻すので、
そこでもう一度丸めが入る。超えたぶんだけ刻みを詰めて測り直す。

検証は二本立てになる: **属性はビット完全、幾何だけ誤差上限の中**。

| 誤差上限 | KITTI 中央値 bpp | 可逆比 |
|---|---|---|
| 可逆 | 21.622 | — |
| 2 mm | 17.954 | −17.0% |
| 5 mm | 14.232 | −34.2% |
| 20 mm | 10.202 | −52.8% |

## 10. 並列とメモリ

- 計画を立てている間だけ生きるプールを 1 つ建て、**列も候補もまとめて
  1 つの待ち行列に流す**。列を 1 本ずつ回すと候補が終わりかけで機械が空く
- どの列にどの候補を出すかは**列の名前と並び順だけで決まる**ので、
  貯める側は結果を 1 つも要らない（例外は色の判定だけ）
- 最短より長いと判った出力はその場で捨てる。同じ長さのものは捨てない
  （選択は添字の早いほうを採るので、捨てると結果が変わる）
- 空間予測の近傍表は、幾何の列を符号化している裏で作っておく

いまのメモリは **647 byte/点**（全列、200 万点）。
三者で最も重い軸で、幾何だけを G-PCC と比べると 4.1 倍
（G-PCC 160.86 MB 対 PCC2 819.61 MB）。
こちらが重い理由は分かっている — 全点と、試している候補を同時に抱える。
**相手がなぜ軽いかは測っていない。**

### 図に書いていない枝

## 13. いまの成績

| 指標 | 値 |
|---|---|
| 全列 対 LASzip | **−14.3%（15/15）** 四分位 [−32.2, −10.6] 幅 −36.5〜−8.5 |
| 幾何 / 属性 | **−13.0%**（15/15）/ −17.3%（15/15） |
| 幾何のみ 17 ファイル | 対 G-PCC 0.94x（11/17）、対 LAZ 0.90x（**17/17**） |
| 速度 | 符号化 LASzip の 36.5 倍、復号 9.5 倍 |
| メモリ | 647 byte/点 |

**勝っている軸はサイズだけである。**速度は「候補を全部符号化して最短を採る」
という設計そのものに由来し、メモリは全点と候補を同時に抱えることに由来する。
