### フルタイルの内訳（C++, 4,929万点）

```
読込 26.7s / A書き 18.8s / 解析 233.4s / B書き 16.8s / 外部 1.6s / 検証 27.6s
                         ^^^^^^^^^^^^ 全体の 72%
```

レンジコーダは 286s → 1.6s になったが、次のボトルネックは `analyze()` の
残差の相手選びで、全フィールド対の順序 0 エントロピーを全点で計算している。
これは**アルゴリズムの問題**なので言語では解けない（標本で候補を絞る必要がある）。

## 移植で見つかった改善

**残差に差分を掛けてから符号化する** — Python 側は `pccfile.py` が差分を掛け、
`bench_normalize.py` は掛けないという経路の食い違いがあった。C++ で経路を
統一したところ露見し、揃えると:

```
差分なし  外部 11.80 bpp → 合計 60.226 bpp （−15.4%）
差分あり  外部  5.66 bpp → 合計 54.082 bpp （−24.1%）
```

フルタイルでも **440MB → 335MB（−23.8%）**、可逆で復元検証を通過。

## 移植中に潰したバグ

1. `liblaszip_api` は動的ロード用のシムで `laszip_create` が必ず失敗する。
   `liblaszip` に直接リンクする必要があった
2. `laszip_point.extra_bytes` のポインタを差し替えると LASzip 側の解放と
   二重になって落ちる。既存バッファに書き込むのが正しい
3. PLY の binary big endian 未対応（Armadillo が読めていなかった）

## 残っている C++ 側の限界

- **ノイズ下の lfs** は依然 13.7%（σ=0.01）〜33.0%（σ=0.03）過小評価する。
  Python 版と同じ性質で、再構成した曲面自身の凹凸に由来する。過小評価なので
  予算用途では安全側
- `analyze()` が O(フィールド² × 点数)。標本で絞る実装が必要
