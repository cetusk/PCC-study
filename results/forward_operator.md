## 一言で

**賞金は KITTI にあった。float32 の xyz は 1 mm の整数倍であり、値を落とさずに
整数へ戻せる。**同じ符号器（xz -9）のまま表現だけ変えて 42.752 → 25.467 bpp
（**−40.4%**）、PCC2 まで足して 17.520 bpp（最良の float32 基準に対し **−59.0%**）。
108 frame 全件で `.bin → PCC2 → .bin` のバイト一致まで確かめた（5 節）。

残る 4 つの筋（当てはめの改良・同族分解・確率モデルの混合・予測の混合）は、
全 bpp に揃えるといずれも 1% 未満か、仮説そのものが否定された。

**同じ問いを LAS にも投げたら、こちらにも取り分があった（8 節）。**
LAS の整数がさらに粗い格子に乗っていることがあり（8 bit の色を 16 bit 欄に
入れた RGB など）、割ってから符号化すると 7/15 で縮む。悪化 0 件。
対 LASzip の中央値が **−12.1% → −14.0%**。ただし KITTI の −59% とは桁が違い、
中央値を動かしたのは 2 万点以下の小さいファイル 4 本である。
予備選別の標本も先頭から取っていたが、直しても縮まなかった（9 節）。

## 標本の作り方（全節に効く）

`--max-points N` は**格納順の先頭 N 点**を取る。§1 で述べるとおり、これは
取得順に並んでいないファイルでは時間的にばらばらな標本になり、取得構造を使う
候補だけを不当に不利にする。**§0・§2・§3・§7 はすべて `python/make_contig.py` で
作った取得順に連続な 200 万点から、さらに先頭 30 万点を取って測った。**
§4 の KITTI は 1 frame が 1 回の取得なので、この問題は起きない。

## 0. 当てはめに、線形の探査で見つかる構造はほとんど残っていない

走査モデルが払っている残差を符号化器から直に出し（`PCC_RESID_DUMP`）、
3 方向から白色化した。解析は `python/exp_ceiling3.py`。

| データ | 採用率 | 面内 | 面外 | z | 計 | 線形探査で取れた分 |
|---|---|---|---|---|---|---|
| AHN4 _21 | **0.945** | 6.13 | 2.37 | 7.66 | 16.15 | 3.1% |
| autzen-2023 | 0.285 | 8.49 | 4.17 | 10.92 | 23.58 | 2.3% |
| AHN3 _20 | **0.000** | 10.00 | 4.80 | 10.93 | 25.72 | 0.8% |
| AHN5 _20 | 0.159 | 8.33 | 10.70 | 11.47 | 30.50 | 0.8% |

探査は 3 つ。走査線に沿った 5 次多項式、自分の過去 1〜4 点の線形予測、
隣の走査線の最近傍点。いずれも符号長は離散ラプラスの**見積り**である。

### この 0.8〜3.1% は下限であって、天井ではない

取れた分は「まだモデル化していない構造が**少なくともこれだけある**」という
下限を与える。取れなかった分が床だとは言っていない。非線形な構造も、
もっと遠い文脈も見ていない。**「当てはめの伸びしろは 3.1% 以下」とは書けない。**

さらに 2 つ、この数字を割り引く理由がある。

- 探査はすべて**同じデータ上の最小二乗**（in-sample）で、5 次多項式の係数 6 個と
  AR 係数 1〜4 個を走査線ごとに送る費用を引いていない。§3 では副情報を引いたが、
  ここでは引いていない。**扱いが揃っていない。**
- **採用率 0.000 の AHN3 と 0.159 の AHN5 は、当てはめの天井を測っていない。**
  それらの残差はほぼ全部が退避路（中央値予測）のものである。当てはめについて
  言えているのは AHN4（0.945）だけで、autzen（0.285）は部分的にすぎない。
  **実質 n=1。**

### 副産物として見えた 2 件

- **z が全件で最大の成分**（7.7〜11.5 bit）なのに、走査モデルは z を
  「同じ戻り番号の直前の点」という素朴な予測のままにしている
- **AHN5 の面外が 10.70 bit（305 格子単位）。**「走査線」が線になっていない

### 自前で当てはめ直してはいけない

最初、ダンプした生の点に Python で同じモデルを当てはめて残差を測った。
長い走査線で LM が発散し、残差が 625・3558 格子単位と出た（符号化器の実値は
12.9・188.2）。**符号化器が実際に払っている値を出させるほうが正しい。**
`PCC_RESID_DUMP` はそのために足した。

### 査読で直した点

「天井」という節タイトルと、順位表の「≤3.1%」を撤回した。同じ数字を本文で
「下限」、表で「上限」と書いていた。採用率 0.000 の件を根拠に数えていた点も明記した。

## 4. KITTI — float32 の中身は整数だった

対象は `2011_09_26_drive_0001_sync` の全 108 frame、13,178,862 点。
**1 ドライブ・1 センサ（HDL-64E）のみ。**他ドライブ・他センサは未検証。

### 直接の確認

```
x, y, z  … すべて 1 mm の整数倍          108 frame 全件
強度      … 0.01 の整数倍                 最大ずれ 2.9e-08（float32 の分解能）
round(v/0.001) * 0.001 を float32 に戻すと、負のゼロを除きビット一致
  負のゼロ以外の不一致  0 点 / 39,536,586 成分
```

刻み 0.001 は仮定していない。`python/exp_gridfind.py` が差分のおよその
最大公約数からデータ側で見つけた（3 軸とも 0.001、格子らしさ 1.0000）。
KITTI の値域（±80 m）での float32 の刻みは 7.6e-6 m なので、
1 mm の格子に乗ることは自明ではない。

### 負のゼロ

`-0.0` は整数 0 を経由すると `+0.0` に戻る。**値は同じだがビット列は違う。**

```
値が 0 の成分    計 2323   frame あたり 4〜50（中央 18）
うち負のゼロ     計 1152   frame あたり 1〜27（中央 9）   全成分の 0.00291%
```

ビット完全にする費用は 2 通り。

| 方式 | 合計 | bpp |
|---|---|---|
| 0 の成分にだけ符号ビットを立てる | 2,323 bit | **0.000176** |
| 位置を素に送る | 29,073 bit | 0.002206 |

結論は動かない大きさだが、**「可逆」は値の可逆であって、ビット完全には
この例外表が要る。**比較相手（下表の float32 の行）は生のビット列に対する完全可逆である。

（**5 節で例外表を実装したので、いまは除外なしでビット完全**である。
`.bin → PCC2 → .bin` を 108 frame で `cmp` して不一致 0。）

### 効き目（幾何のみ、xyz、108 frame の中央値）

| 表現 | 符号器 | bpp | 幅 |
|---|---|---|---|
| float32 素 | — | 96.000 | — |
| float32 | zstd -19 | 52.819 | 52.51〜55.19 |
| float32 | **xz -9** | **42.752** | 42.46〜43.91 |
| 整数 1mm | **xz -9** | **25.467** | 25.14〜26.51 |
| 整数 1mm 差分 | zstd -19 | 24.446 | 24.08〜25.45 |
| 整数 1mm 差分 | xz -9 | 20.525 | 20.24〜21.47 |
| **整数 1mm** | **PCC2 幾何v3** | **17.520** | 17.18〜17.99 |

**2 つの利得を分けて読むこと。**

- **表現の利得（この節の発見）**：符号器を xz -9 に固定して 42.752 → 25.467 = **−40.4%**
- **符号器の利得**：25.467 → 17.520 = −31.2%
- 合わせて **−59.0%**

### 記録の先行結果との関係

`results/kitti_polar_finding.md` は 108 frame 平均で

- 可逆（取得順差分 + zstd）**46.183 bpp**
- 非可逆 極座標 2mm/0.002°（誤差 2.11 mm）**14.184 bpp** → −69.3%

を報告していた。46.183 に対しては −62.1%、14.184 に対しては +23.5% である。
ただし**この文書自身が測った中で最良の可逆基準は xz -9 の 42.752** であり、
headline はそちらを使うのが公正である（→ −59.0%）。

### 記録の推論にあった誤り

> 実測でも、KITTI の r は 2mm の整数倍になっていない（誤差中央値 0.2492 ≒ 無相関）。
> 校正・自己運動補正の変換を経ているため、元の極座標格子は既に壊れている。

**「r が 2mm の整数倍でない」から「格子は壊れている」は導けない。**
既知の順演算子で作った合成データで対照を取ると（`python/exp_kitti_grid.py`）、

| 合成の場合 | 素の r の外れ | レーザごとの下駄つき |
|---|---|---|
| 1. 純粋（float64） | 0.0000 | 0.0000 |
| 2. float32 に丸めた | 0.0004 | 0.0004 |
| 3. ＋レーザごとの距離の下駄 | 0.2327 | 0.0571 |
| 4. ＋原点の縦ずれ | 0.2763 | 0.1802 |
| 5. ＋剛体変換 1 つ | 0.2505 | 0.2494 |
| KITTI の実測 | 0.2490 | 0.1876 |

格子が完全に生きている場合 3 でも、素の r は 0.2327 になる。
**「素の r が無相関に見える」検査は、壊れている場合と、モデルが足りないだけの
場合を区別できない。**そこが記録の推論の穴である。

**この対照表は、KITTI がどの場合かを決めない。**第 1 列は場合 5 に近く、
第 2 列は場合 4 に近い。前の版は第 2 列だけを見て「場合 4 に一致する」と
書いたが、それは言い過ぎだった。結論を付けたのは対照ではなく、
**上の直交座標の直接検査**である。極座標の対照は、記録の検査が不十分だったこと
だけを示している。

もう 1 点。**float32 への丸めは格子を壊さない**（場合 2 の 0.0004）。
「仮数部の下位 18 ビットが H=1.000 の乱数」は、**整数を float で書いたことの
副作用**であって、情報が失われた証拠ではない。

1 回通したのは frame 0 のみ**（負のゼロ 14 点を除きビット一致）。

### どこまで一般的か

`python/exp_gridfind.py`。**float32 の刻み（ULP）より細かい「格子」は表現そのもの
であって、データの性質ではない。**その保護を入れて測り直した。

| データ | x | y | z |
|---|---|---|---|
| KITTI `.bin` | 0.001（1.0000） | 0.001（1.0000） | 0.001（1.0000） |
| Stanford bunny | 0.00025（1.0000） | 1e-07（1.0000） | 1e-07（0.9436） |
| Stanford dragon | 見つからず | 1e-07（1.0000） | 見つからず |
| `data/work/tls_scan1.ply` | 見つからず | 見つからず | 見つからず |
| `data/work/ahn4_win.ply` | ULP の偽陽性 | ULP の偽陽性 | 0.001（1.0000） |

括弧内は格子らしさ。dragon の x・z は、差分から出した種が真の刻みの約数でなく、
十進の候補にも当たらなかった**取りこぼし**である（格子が無いとは言っていない）。

`ahn4_win.ply` の x・y は、原点オフセットが 13 万 m あるため float32 の刻みが
1.6 cm になっており、**元の 1 mm 格子は ply に書いた時点で失われている**。
前の版は「LAS 由来なので当然」と書いたが、逆で、失われた例だった。

**LAS は最初から整数なので、この発見は LAS の測定を動かさない。**
効くのは float で座標を持つ容器（`.bin` `.ply` `.pcd` など）である。
**実際に圧縮まで測ったのは KITTI 1 ドライブだけ**で、一般性はまだ薄い。

### 査読で直した点

−61.6% を表現の利得と符号器の利得に分解した。基準を 46.183 から
自分で測った最良の 42.752 に変えた。負のゼロの費用（前の版の「14 bit」は誤り）と
frame あたりの幅（6 frame の 9〜15 → 108 frame の 1〜27）を測り直した。
合成対照表の読み方を訂正した。`exp_gridfind.py` に ULP の保護を入れ、
一般性の表を作り直した。まとめ経路の可逆性検査を追加した。

## 5. 整数化を道具に組み込んだ（2026-09-22）

Python の変換器を別に持つのをやめ、`pccnorm` の入力側で刻みを見つけて
整数に直すようにした。新しいのは `cpp/include/pcc/grid.hpp` と `cpp/src/grid.cpp`。

### 設計 — 候補は統計で探し、採否はビットの証明で決める

刻みは差のおよその最大公約数から探し、値そのもので磨く。
**採るのは、全点でビット列が再生できると証明できたときだけ**である。
証明が落ちれば今までどおり浮動小数のビットを詰める。

**保証されるのは可逆性だけで、符号長ではない。**証明が通っても整数が大きければ
浮動小数のビットより伸びうる。実際に伸びた（下記）。符号長で選び直す仕組みは
入れていないので、**「悪化しない」とは書けない。**5 件で伸びなかったことを
実測しただけである。ULP の保護（後述）は経験則であって証明ではない。

証明で気をつけた点が 3 つある。いずれも実際に踏んだ。

1. **証明は、実際に格納する道順と同じでなければならない。**
   double の `round` はゼロの符号を残すが、`int64` に落とすと消える。
   残る側で試すと、-0.0 の例外を数え落とす。
2. **磨いた刻みの 10^-13 のずれが効く点がある。**
   値が隣り合う 2 つの float32 のちょうど中間に落ちる点では丸めが反転する
   （`-14.7959995` が `-14.7960005` になった。この値は 108 frame 中 104 frame に
   あり、最初に気づいたのが frame 70 だったというだけである）。
   十進に丸めた候補も並べ、通った最初のものを採る。
3. **十進の文字列から来た値は「10^-d を掛ける」と戻らない。「10^d で割る」と戻る。**
   2 進で表せない 10^-d を先に丸めてしまうため。bunny の x は掛け算だと
   40256 点中 20710 点しか戻らず、割り算なら全点戻る。
   **封筒には刻みだけでなく、掛けるのか割るのかも載せる**（載せ忘れると、
   十進の列は書き戻したときに元のビット列に戻らない）。

表現の刻み（ULP）より細かい「格子」は、データの性質ではなく表現そのもので
あって同語反復になる。掛け算の道にも十進の道にも保護を入れた。
**入れ忘れると伸びる。**3 つの状態を比べるとこうなる。

|---|---|---|
| 旧コード（float64 のビットを詰める） | 71.466 | 50.338 |

基準は「**器が宣言している型**で x/y/z を並べたとき」。ascii でも宣言型を使うので

それでも変更前の 130.788 bpp よりはるかに短い。

LAS は最初から整数なので、この変更は LAS の測定を一切動かさない

`data/work/grid/las_regression.log`）。構造上も `fit_grid` を呼ぶのは

## 8. 同じ教訓を LAS に当てる — 整数もまた粗い格子に乗っている（2026-09-22）

4〜6 節は「float で書かれた値が実は整数だった」話である。同じ問いを LAS にも
投げた。**LAS は int32 + scale で持っているが、その整数自体がさらに粗い格子に
乗っていないか。**一度も測っていなかった。

**独立した査読を 1 回通し、10 箇所を直した。**最初の版の誤りは各所に書く。

### 何が見つかったか

`python/exp_intgrid.py` で 15 ファイルの全列を調べた。乗っていた。

| データ | 列と刻み |
|---|---|
| simple1_4 | X 10^6 / Y 10^7 / Z 10^3 / RGB 256 |
| fullwave | RGB 257 |
| plane | intensity 256 / gps_time 16384 |
| vegetation | intensity 257 |
| extra | Intensity（ExtraBytes, U32）256 / Time（同, U64）2^24 |
| autzen-2023 | RGB 256 |
| USGS NY | gps_time 16 |
| red-rocks | Y 50 |

RGB の 256 と 257 は、**8 bit の色を 16 bit の欄に入れた**ものである
（256 倍は左詰め、257 倍は 0..255 を 0..65535 に伸ばしたもの）。LAS では珍しくない。

gps_time の 16 や 16384 は、**ビット列の差が刻みの倍数**、すなわち
**下位のビットが全点で同じ**ということである（plane の gps_time は下位 14 bit が
全点 6699。0 ではない）。最初の版は「下位が揃って 0」と書いたが、**誤り**である。

### 「浮くビット」は利得ではない

最初 `log2(刻み)` を足して「simple1_4 は 77 bit/点 浮く」と書きかけた。**誤りである。**
値の種類が少なければ符号化器は既に取っている（X は 226 種しかないので、
どう表しても 7.8 bit を超えない）。実際の利得は 4.3 bit/点だった。
**実際に割って符号化して比べるしかない。**

### 実装 — どこで割るか

`apply_column_grid`（`cpp/src/frame.cpp`）。LAS を読んで**正規化の計画を立てた後**に、
列ごとに `値 = base + step × 格納値` を見つけて割る。`step` は封筒ではなく容器の
新しいタグ（`T_COLDIV`）に入れ、LAS へ書き戻すときに掛け戻す。
幾何は `scale`/`offset` も合わせて動かす。`PCC_COLDIV=0` で切れる
（入れた前後を同じ二値で比べるために置いた）。

実数の列はビット列を int64 に入れてあるので、正負が混ざると `c[i] - mn` が
符号付きの桁あふれ（未定義動作）になりうる。**符号なしで引いて割る。**
現在の 15 ファイルでは符号が混ざると gcd が 1 に落ちて割られないので踏まないが、
踏まないことは保証ではない。

### base の取り方で列の符号長が 3.7 bpp 動いた

（**列の** bpp である。全列の bpp ではない。）

最初は全列で `base = 最小値` にした。`extra.laz` の `Intensity`（U32 の
ExtraBytes）が **11.050 → 14.776 bpp と伸びた**。原因は base の引き算で
**バイト境界がずれる**こと。記号版の符号器はバイトごとに模型を持つので、
絶対値のバイト構造が崩れると読めなくなる。

かといって全列 `base = 0` にすると、`plane` の gps_time の利得が消える。
実数のビット列では「値が刻みで割り切れる」に意味が無く、意味があるのは
**下位のビットが全点で同じ**という差の構造のほうだからである。

分けた。**整数の列は base = 0、実数の列（F32/F64）は base = 最小値。**

### 固定費と、割っても意味のない列

値が 1〜2 種類しかない列でも刻みは見つかる（AHN4 _21 の先頭 30 万点では
`point_source_id` が {79} の 1 種類だけで、刻み 79・割った後の幅 0。
AHN5 は 1110、USGS AK の `user_data` は 32）。**縮まないのに容器に刻みを書くぶん
損をする**（+0.002〜0.004 bpp）。割った後の幅が 1 以下の列は外した。
`scale`/`offset` の 6 個の double も、幾何を割ったときだけ書くようにした。

3 回ずつ測ったところ、符号化時間は切/入とも 0.50〜1.26 秒とばらつき（差は読めない）、
ピークは 0.27〜0.29 GB（切）→ 0.29〜0.32 GB（入）で**むしろ増えた**。
機構の勘定も合わない（autzen-2023 で狭くなるのは RGB 3 列だけで、
200 万点でも約 6 MB にしかならない）。

### 検証が、割り算の可逆性を試していなかった

最初の実装では、比較相手の `orig` も `load_frame` で読み直されるので**同じ割り算を
通る**。両辺とも「割った後」の空間で比べており、**割り算が情報を落としても、
刻みの書き出しが壊れても検証が通ってしまう**状態だった。
`frames_equal` は `coldiv` 自体も比べない。

直した。検証の前に**両方を `restore_column_grid` で戻してから**比べる
（`cpp/src/main.cpp`）。15 ファイルすべてが通る。

### `unpack --las` が戻すもの・戻さないもの

**X/Y/Z の整数と `scale`/`offset` は元と完全に一致する**
（simple1_4 / fullwave / extra / plane で確認。simple1_4 の scale は
`0x1.0c6f7a0b5ed8ep-20` までビット一致）。

一方で**全列が戻るわけではない**。plane は `return_number` と
`number_of_returns`、fullwave は wavepacket 系 7 列、extra は bit フィールド 4 列と
ExtraBytes 2 列が戻らない。**これは `PCC_COLDIV=0` でも同一**で、
8 節の変更とは無関係な `write_las` 側の既存の欠陥である
（記録の「戻らない次元があるファイル 13/15」と同じもの）。
最初の版は「全列一致」と並べて「完全に一致」と書いており、全列と読まれる書き方だった。

### 容器の中での世界座標

`scale*g`・`offset + scale*base` の計算には丸めが入り、pcc2 の中の表現では
simple1_4 で最大 **2.8e-14 m** ずれる。書き戻すときは元の `scale`/`offset` を
覚えておいてそのまま書くので、**最終的な LAS では完全に一致する**。
最初の版の「世界座標は 1 ミリも動かない」は、順序を書いていない点で不正確だった。

### red-rocks の Y（刻み 50）が縮まない理由

200 万点では差が 0.000 だが、30 万点では +0.001 bpp とわずかに伸びる。
査読が pcc2 を分解して内訳を出した。

```
header    752 → 830 byte  （+78。うち 48 は幾何の scale/offset）
X+Y+Z  272188 → 272143    （−45）
他の列                     すべて同一
合計                       +33 byte = +0.00088 bpp
```

**「残差が変わらないから利得が出ない」ではなく、45 byte の利得が 78 byte の
固定費に負けている。**最初の版は前者を推測として書いたが、測ると外れていた。
割るかどうかを列ごとに実測で決める仕組みは入れていない。

## 9. 予備選別の標本も「先頭から」だった — が、直しても縮まなかった（2026-09-22）

1 節は「`--max-points` が格納順の先頭を取るので標本が代表しない」ことを示した。
**符号化器の内側にも同じものがあった。**`best_stream` の予備選別
（`cpp/src/pcc2.cpp`）は、候補に順位を付けるのに**列の先頭 2 万〜2.5 万点**を使う。

### 費用は出ていた（ただし、先頭 200 万点でだけ）

先頭 200 万点で `PCC_PRESELECT=0`（全候補を全点で測る）と比べた。

| データ | 予備選別あり | なし | 差 |
|---|---|---|---|
| red-rocks | 18.661 | **18.571** | **−0.090** |
| autzen-2023 / AHN3 / AHN4 _21 / AHN5 | | | 0 |

red-rocks だけ 0.090 bpp（0.48%）の費用。列を突き合わせると
**X+Y+Z で標本が `走査変換記`（7.070）を選び、全点では `幾何v1記`（6.980）が
短かった**。全候補を全点で測ると 1.2〜1.4 倍遅くなるので、標本はやめられない。

### 等間隔の塊に変えてみた

間引くと走査線や空間の並びが壊れるので、**等間隔に置いた連続した塊**にした。
塊の数を掃くと、2 が唯一 red-rocks を直しつつ AHN4 _21 を保つ
（3 以上は塊が掃引を切り、AHN4 _21 が 0.056 bpp 伸びる）。
先頭 200 万点の 15 ファイルでは red-rocks −0.090、残り 14 件 0.000。

**ここで止めていれば「改善した」と書いていた。**

### 中央の切り出しと全点で測ったら、消えた

ベンチ（`bench_all.py`）は**中央**の 200 万点を使う。同じ切り出しで測り直した。

| データ | 塊 1 | 塊 2 | 塊 4 |
|---|---|---|---|
| autzen-2023 | **60.614** | 60.756 | 60.756 |
| red-rocks | 18.480 | 18.480 | 18.480 |
| AHN5 _20 | 53.763 | 53.763 | 53.763 |

**中央の切り出しでは red-rocks の利得が消え、autzen-2023 が 0.142 bpp 伸びる。**
さらに red-rocks を**全点（400 万点）**で測ると、塊 1 と 2 は同値（18.247）だった。

つまり先頭 200 万点で見えた 0.090 は、**外側の標本が先頭だったことの副作用**で、
実ファイルには存在しない。1 節の欠陥を内側にも見つけたつもりで、
**1 節の欠陥が作った幻を追っていた。**

既定は先頭のまま（`PCC_PRE_CHUNKS=1`）に戻した。`PCC_PRE_CHUNKS` は
この測定を再現するために残してある。

### 教訓

**標本の欠陥を直す実験を、欠陥のある標本の上で評価してはいけない。**
1 節で `--max-points` が代表しないと結論したのに、その `--max-points` で
予備選別の改善を測っていた。中央の切り出しと全点を見るまで気づかなかった。
