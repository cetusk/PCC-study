# 走査モデル符号器 — 当てはめの誤りを見つけるまで

測定日 2026-09-19。`cpp/build/pccnorm pack` による実測で、
すべて往復検証（全列一致）と決定性（2 回書いてバイト一致）を通している。

## 一言で

**符号器を実装して測ったら規模で逆転した。原因を追ったら当てはめの符号が逆だった。**
ガウス・ニュートンの更新を引き算していたため、毎回逆方向に動いて固着していた。

## 1. 最初の測定 — 規模で逆転する

走査モデルを PCC2 の幾何の候補として実装し、規模を変えて測った。

| 規模 | 幾何v3 | 走査モデル | |
|---|---|---|---|
| 200 万点 | 22.032 | **20.801** | 走査の勝ち −5.6% |
| **4,929 万点（タイル全体）** | **22.542** | 24.964 | **走査の負け +10.7%** |

タイル全体では選択原理が自動的に幾何v3 を採ったので悪化はしていないが、
実装した符号器は採用されなかった。所要 enc 1086 秒・ピーク 26.6 GB。

**この節の数字はすべて、下記の誤りを含む実装で出したものである。**

## 2. 外れた仮説 2 つ

### 副情報が重くなる — 外れ

走査線ごとに 56 bit の副情報を送るので、規模が上がると重くなると考えた。逆だった。

| 点数 | 走査線あたり | 副情報 | 標識 | 残差 | 合計 |
|---|---|---|---|---|---|
| 50 万 | 160 点 | 0.866 | 0.317 | 19.046 | 20.230 |
| 200 万 | 258 点 | 0.556 | 0.309 | 19.936 | 20.801 |
| 800 万 | 490 点 | **0.307** | 0.311 | **22.898** | 23.515 |

規模が上がると走査線が長くなり、副情報は薄まる。伸びているのは残差だけ。

### 退避路が弱いから — 部分的に当たり、しかし主因ではない

モデルを採らない走査線は素朴な差分に退避する。そこが弱いと考えた。

```
200万点: 採用した線 14.88 bit / 退避した線 17.63 bit   モデルが良い
800万点: 採用した線 22.43 bit / 退避した線 19.02 bit   モデルが悪い
```

800 万点では、符号化器が「モデルが勝つ」と判断して採用した線のほうが悪い。
**判定そのものが壊れていた。**

## 3. 成分別に見ると面外が犯人だった

```
             面内     面外     z      計
採用した線   8.81    4.92    8.70   22.43
退避した線  10.01    1.56    7.45   19.02
差          −1.20   +3.36  +1.25   +3.41
```

面内はモデルが効いている（−1.20 bit）。面外が +3.36 bit 悪化して食い潰していた。

採用すると面外の予測が「直前点との差分」から「定数 off0（中央値）からの差」に
切り替わる。薄くない走査線では線の厚み全体に広がる。
**判定は面内しか見ていないので、この巻き添えが見えない。**

## 4. 試作と実装の食い違い

同じデータ・同じモデルなのに採用率が桁違いだった。

| | 掃引 | 走査線 | 分割 | モデル採用率 |
|---|---|---|---|---|
| Python 試作（300 万点） | 6,757 | 6,558 | 318（4.7%） | **0.998** |
| C++ 実装（200 万点） | 4,681 | 7,756 | **3,075（66%）** | **0.229** |

分割条件（走査角の幅が 20 度以上の掃引だけ分割を試す）を移植し忘れていた。
入れると分割は 6.8% に戻り、標識も 0.309 → 0.062 bpp に減った。
**しかし採用率は 0.224 とほとんど動かなかった。** 過剰分割は主因ではない。

## 5. 診断を 3 方向から一度に取る

走査線ごとに当てはめの様子を書き出す診断を入れた
（`PCC_SCAN_DUMP=<path>`。環境変数を付けたときだけ働き、符号化の結果には影響しない）。
解析は `python/exp_scan_diag.py`。

### (1) scipy と比べて桁違いに悪い

```
C++ − scipy の残差差: 中央 +15.14 bit/点  平均 +9.11  P90 +17.18
scipy のほうが良かった線: 91.5%
```

### (2) 反復すると悪化して固着する

```
反復    0      1      2      3    ...   11
      18.85  19.88  20.09  20.11 ...  20.11
```

1 回目が最良で、2 回目以降は悪化し、3 回目で完全に固着。
反復 0→11 の改善は 0.000 bit。**反復そのものが逆効果だった。**

### (3) 走査線の性質は主因ではない

不採用の線の 10% は高度が縮退していた（採用側は 0.2%）が、
点数の中央値は採用 292・不採用 307 とほぼ同じ。縮退は主因ではない。

## 6. 原因 — ガウス・ニュートンの符号

```cpp
g0 -= j0 * r;                             // g = -Jᵀr
double dth = (g0 * B11 - g1 * B01) / e;   // B δ = g を解く
double nt = th0 - dth;                    // ← 足すべきところを引いている
```

$B=J^{\top}J$、$g=-J^{\top}r$ として $B\delta=g$ を解いた $\delta$ は足すのが正しい。
引いていたので毎回逆方向に動き、境界 $|\theta_0|<\pi/4$ に張り付いて更新が
棄却され続けて固着していた。観測された 3 つの徴候すべてがこれで説明できる。

## 7. 修正後

| | 修正前 | 修正後 |
|---|---|---|
| 反復 0→11 の改善 | 0.000 bit | **+2.515 bit**（2 回で収束） |
| scipy との差 | +15.14 bit/点 | **+1.95 bit/点** |
| モデル採用率 | 0.224 | **0.296** |
| 幾何（200 万点） | 20.159 | **20.079** |
| PCC2 合計（200 万点） | 48.863 | **48.783 bpp** |

幾何v3 の 22.032 に対して **−8.9%**。

あわせて直したもの。

- 面外を採用・退避で切り替えず、常に中央値予測にした
- 退避路も中央値予測（幾何v1 と同じ）にした
- 採否の判定を残差の標準偏差からビット長に変えた。
  符号長を決めるのは裾の重さで、標準偏差では判断を誤る
- 判定の基準を、符号化器が実際に使う退避路と同一にした

## 8. 残っている課題

- **scipy との差 1.95 bit/点。** `shot` は最大 7 万、`Sz` は約 130 万（mm）と
  列のスケールが 6 桁違う。レーベンバーグ・マルカート法の対角スケーリングが要る
- **採用率 0.296 止まり。** 不採用の線は角速度の符号が採用側と逆（+17,182 対 −19,284）。
  走査の向きが逆のコースなのか、別の極小に落ちているのか未確認
- **800 万点とタイル全体が未測定。** 修正前の 22.797 / 24.964 は無効

## 教訓

このプロジェクトは「推定ではなく実測で選ぶ」を原則にしているが、
符号器の内側に代理指標が 2 つ残っていた。

1. 採否を残差の**標準偏差**で判定していた（符号長は裾の重さで決まる）
2. 判定の基準が、符号化器が実際に使う退避路と**違うもの**だった

どちらも「実測で選ぶ」から外れている。外側の選択原理だけ実測にしても、
内側に代理指標が残っていれば同じ誤りが起きる。

# 続き — LM の導入と、太い走査線の正体

## 9. レーベンバーグ・マルカート法で当てはめを作り直した

符号を直しても scipy との差が 1.95 bit/点 残っていた。
交互最適化では列のスケールの違いを扱えないためと見て、4 パラメタ同時の
LM に置き換えた。$A_{33}/A_{00}\sim10^{22}$ になるので、
$D=\mathrm{diag}(\sqrt{A_{kk}})$ で正規化してから解く。

目的関数は符号化器（`scan_predict`）と同じく $|\theta_i|\le45°$ で打ち切る。
当てはめの目的関数と符号化器の計算がずれると、実態に合わない最適化になる。

| | 符号修正のみ | LM |
|---|---|---|
| scipy との差 | +1.945 bit/点 | **+0.046 bit/点**（中央値） |
| scipy のほうが良かった線 | 92.6% | 68.1% |
| 反復 0→最終の改善 | +2.515 bit | **+5.769 bit** |
| モデル採用率（200 万点） | 0.296 | **0.656** |
| モデル採用率（800 万点） | 0.323 | **0.506** |
| 幾何（200 万点） | 20.079 | **19.128** |
| **幾何（800 万点）** | 22.694 | **22.122** |

**800 万点で初めて幾何v3（22.541）を下回った。**

## 10. 外れた推測 — 「角速度 0 の線で LM が止まっている」

8 節で不採用の線の角速度の符号が採用側と逆だと出たので、LM が動いていない線が
あると考えた。20 点以上の線に限って数えると、角速度が厳密に 0 の線は
2M・8M とも **0 本**だった。中央値 0 は、20 点未満の極小の線
（当てはめ以前に打ち切られ既定値 0 が入る）が支配していたもの。
LM が 1 歩も動かなかった線も 0.8〜1.1% しかない。

## 11. 外れた推測 — 「退避路が規模で弱くなる」

退避側の面内費用は、線ごとの中央値で 6.64（2M）→ 6.84（8M）とほぼ変わらない。
走査線の長さ別に見ても 6.4〜7.1 で平坦だった。

規模で悪化して見えたのは、点で重み付けすると 6.61 → 8.33 になるためで、
**少数の巨大な線が全体を引いている**。

## 12. 本当の原因 — 分割に失敗した太い走査線

走査線の長さ別の採用率（点で重み付け）:

| | 20-100 | 100-300 | 300-600 | 600-1200 | 1200- | 全体 |
|---|---|---|---|---|---|---|
| 200 万点 | 0.607 | 0.475 | 0.615 | 0.695 | 1.000 | 0.655 |
| 800 万点 | 0.657 | 0.615 | 0.428 | 0.712 | **0.351** | 0.506 |

1200 点超の帯だけが 1.000 → 0.351 と激減する。2M の範囲には無く 8M で現れる。

分割の結果を記録すると（8M、20 点以上の線）:

| 分割の結果 | 線 | 点の割合 | 薄さ中央 | 採用率 |
|---|---|---|---|---|
| 試みず（34 度未満） | 7,318 | 0.464 | 4.1 mm | 0.638 |
| EM が偏った | 3 | 0.000 | 11,075 mm | 0.000 |
| **判定で棄却** | **378** | **0.123** | **23,607 mm** | **0.000** |
| 分割した | 2,672 | 0.413 | 4.5 mm | 0.510 |

棄却された線は $w/r_0$ の中央値が **0.515**（閾値 0.5）で、わずかに外している。
しかし分割後も 12.4 m あり（成功例は 4.5 mm）、**2 群に分かれていない**。
閾値を緩めるのは誤った対処になる。

## 13. 太い線は走査線の集合ではなかった

失敗した線を EM で k 本に分けたときの薄さ:

| k=1 | k=2 | k=3 |
|---|---|---|
| 14.1 m | 7.15 m | 4.74 m |

**ほぼ $r_0/k$ で減る。** 一様に厚い帯を平行な短冊に切っているだけで、
構造を見つけていない。2 本の向きの差も 4〜5 度しかない。
分割に成功した線は k=2 で 0.0007〜0.0028 m（サブ mm）まで落ちる。

時間幅を測ると:

```
失敗した太い線: 2,092 点 / 時間幅 0.950 ms / 発射間隔 10 ulp / 時間の隙間 0 本
                地上の広がり 185 × 764 m
```

**単一の連続した掃引である。** 掃引の切り出しは正しく、複数の掃引が混ざっても
いない。0.95 ms の間に機体は 6 cm しか動かないので、厚さ 14〜17 m は
機体の移動では説明できない。走査幅 34 度をまるごと含むときだけ現れるので、
広い角度範囲では地上軌跡が曲がる、というのが最も素直な説明になる。
**ただしこれは説明であって、まだ測っていない。**

§9 で「走査幅いっぱいの掃引が平面でないのは 2 台のスキャナの混在が原因」と
書いたが、それは一部にしか当てはまっていなかった。混在した掃引は EM で
分離でき（229 本成功）、残る 298 本は線の集合ですらない。

## 14. 効かなかった対処 — 回転を実測で選ぶ

太い線では面内座標 $s$ が意味を成さないので、回転しないほうが安いはずと考えた。
モデルを採らない線について、主軸回転と恒等回転の退避路の費用を両方測り、
短い方を採るようにした。

| | 回転選択なし | あり |
|---|---|---|
| 200 万点 | 19.128 | 19.090 |
| 800 万点 | 22.122 | 22.102 |

**ほぼ効果なし（−0.02〜0.04 bpp）。** 回転は 1 次変換なので局所的な滑らかさを
壊さず、中央値予測の性能は座標系にほとんど依存しなかった。
太い線が高くつく理由は座標系ではなく、その領域の点そのものが予測しにくいこと。

面外は掃引を走査線に切り分けられたかの指標なので、改善の的は
当てはめではなく分割である、という解釈自体は機構として自然だが、
この標本では支持されていない。

### autzen-2023 — 採用率 0.037 で勝つ

採用した線 79 万点（16.79 bit）に対し、退避した線 2044 万点が 14.55 bit。
勝ちの中身はすべて退避路、すなわち掃引の分割・走査線ごとの主軸回転・
MedPred であって、`s = s0 + (Sz-z)tan(θ0 + ω·shot)` の当てはめではない。
座標変換そのものが幾何v3 の交差軸文脈より 4.9 bpp 良い。

### AHN5 — 分割が発火しない

53,296 掃引に対し分割は 1,079 回（2%）。1 掃引を 1 走査線として扱った結果、
面外 6.52 bit の帯になっている。AHN4 タイルで見た「太った掃引」と同じ症状。

### AHN3 — gps_time の表現が違う

2013 万点に対し掃引が 1639 万個、走査線あたり 1 点。時間差 > 200 ulp という
間隔条件がほぼ全点で成立している。AHN3 の gps_time は ctx2 で 9.693 bpp

採用率は 0.009〜0.035 と 0.477〜0.528 の二塊で、その間にデータ点が 1 つもない。

可能性を排除できていない。

変換だけのほうが短い。ただし低採用側の差は 0.025〜0.074 bpp（0.1〜0.3%）と小さい。

## 33. 先行技術（2026-09-20、独立査読の調査）

28〜30 節で扱った「順序を復元しながら費用は順序非依存」という性質について、
会話の文脈を持たない査読に先行技術を調べさせた。**構成要素はすべて既発表・既特許で、
新規性として主張できるのは 1 点だけだった。**

| 要素 | 状態 |
|---|---|
| 幾何の費用が入力順に不変 | **既知**（G-PCC のオクツリー、Draco の kd-tree） |
| データから走査順を内部で再導出 | **既知**（TMC13 の `--sortInputByAzimuth` / `--predGeomSort`、SerLiC ICML 2025） |
| 順序の情報を別チャネルで送る | **既知**（US10796457B2、shuffle coding） |
| 元の入力順を可逆に復元 | **既知（限定的）**（US10796457B2） |
| 上記を同時に満たす可逆符号器の実装と実測 | 公刊物は見つからず |
| 入力順がビットレートに与える影響の系統的測定 | **公刊物は見つからず（ここが空白）** |

### 危険な先行技術

1. **US10796457B2**（Van Beek, Intel, 優先日 2018-06-26,
   "Image-based compression of LIDAR sensor data with point re-ordering"）。
   明細書に「点位置を可逆符号化すればどの順で符号化しても X,Y,Z は同一」と
   順序不変性が明記され、「順序保存が必要な場合は符号化順の選択をデコーダへ送り
   元順序を再構成できる」とも書かれている。**最大の脅威。**
   差別化しうるのは「事前定義集合からの選択」対「任意置換の完全符号化」、
   および range image を前提にしていない点。独立クレームの内容は未確認。
2. **Kunze et al., ICLR 2024（shuffle coding）** と
   **Severo et al., IEEE JSAIT 2022（Random Order Coding）**。
   **「canonical ordering」という用語と log(n!) の理論枠組みを先取りしている。**
   向きは逆（彼らは順序を捨てて log n! を節約、こちらは順序を保って払う）だが、
   同じ道具立ての符号反転と見なされうる。
3. **G-PCC / TMC13** の `sortInputByAzimuth`、`predGeomSort`、
   `canonical_point_order_flag`。「順序不変な幾何符号化」は標準に既に入っている。
4. **LASzip**（Isenburg, PE&RS 2013）は再ソートしない。順序依存の代表例である。
   再ソートは外部ツール `lassort` の役割で、これは入力順を破壊する。
5. **Mongus & Žalik (IJRS 2011)** は LAS のファイル順をそのまま列として扱う。
   内部再ソートの記述は確認できず、先行技術にはならない。

### 帰結

- **「順序を復元しながら費用は順序非依存」を新規性の中心に置くことはできない。**
  しかも 29〜30 節の測定で、その性質は符号器ではなく鍵の一意性に依存すると分かった。
- **空白は「入力順のビットレート感度の系統的測定」だけである。**
  恒等 / Morton / 局所シャッフル / 完全ランダム / 逆順 を統制条件として
  比較した評価プロトコルの論文は見つからず、MPEG の共通試験条件にも
  順序の規定が無い。30 節がその測定にあたる。
- 既発表の `paper/coding.tex` の `sec:order-matters` が
  「幾何由来の順序を使うから色の費用は順序に依存しない」を既に主張しているので、
  本測定はその列を色から幾何に替えたものである。**新規性は
  「それが鍵の縮退の性質であり、完全に縮退したとき何が起きるかを定量化した」点に限られる。**

### 欠陥 1 — 「鍵だけを壊す」操作になっていない

**`gps_time` は鍵であると同時に走査モデル自身の説明変数である。**
`build_scan_ctx` は掃引の切れ目を「時刻差の中央値 × 20」で決め、
`enc_geom_scan` は `scan_predict` に `bg[i] - bg[0]` を渡す。量子化は両方を粗くする。

証拠が恒等条件の bpp に出ている。**AHN4 は最も細かい 10% 水準
（量子化幅 6.0e−7 秒）で既に 17.098 → 19.068 と +11.5% 悪化している。**
AHN4 の入力は降順隣接がほぼ 0 で鍵順そのものなので、恒等条件では
**復元される点順序が全水準で同一**である。つまりこの +11.5% は順序では
説明できず、**量子化による走査モデルの劣化そのもの**である。
**交絡（11.5%）は中間水準の主指標（±1%）の 10 倍ある。**

### 欠陥 2 — 逆順は雑音床ではない

AHN4 の逆順 Δ は **0 → +2.3 → +4.5 → +6.1 → +13.9 → 0** と、
タイ率とともに単調に増えて 100% で 0 に戻る。鍵にタイがあるとき、
逆順は `stable_sort` のタイを**決定的に逆向きに解く** —— 走査線内の点列を
反転させる、幾何的に意味のある処置である。100% で 0 に戻るのは、
鍵が完全に縮退すると符号化順 = 入力順になり、系列反転が差分符号にとって
ほぼ無償になるためである。**引くと調べたい効果が消える。**

30 節は自分で「符号つきの単一標本の雑音を信号から引く操作で、分散を減らさず
増やす。統計的な正当化は無い。この 1 数字で段階的な法則を支えてはいけない」
と書いていたのに、36 節はその指標を主表の唯一の列に昇格させていた。

### 欠陥 3 — 対照は原理的に動きえない

幾何v3 が 6 水準すべてで完全に一定（+56.1% / +150.5%）なのを
「測定系が健全であることの、事前に決めた証拠」と書いたが誤りである。
報告値は X+Y+Z のみで、量子化はスケール済み整数 XYZ に一切触らない。
**幾何v3 が動かないのは同語反復で、反証条件は発火しえない条件だった。**

### 欠陥 4 — x 軸が 5 桁空いている

平均群サイズで見ると 6 点のうち 5 点が **1.0〜4.0** に密集し、
最後の 1 点だけが **5×10³〜5×10⁵** にある。
タイ群は時間的に隣接する＝空間的に近い点の集合なので、置換の損害は
群の空間的な広がりにほぼ比例するはずで、群サイズ 4 で損害が小さいのは
設計の当然の帰結である。

### いま言えること

**符号器単独の性質ではない。** 入力順を恒等に固定したまま `gps_time` を
操作すると走査v1 の置換感度が変わるので、不変性は入力に依存する
条件つきの性質である。因果の向きは観測相関よりは強く支持される。

**それ以上は言えない。** 処置が単一でないので「鍵の単射性が原因」と
「時刻の精度が原因」を区別できない。「符号器ではなく鍵」は誤った二分法で、
正しくは **「走査モデルの順序不変性は、再構成鍵の単射性を前提とする
条件つきの性質である」**。

標本も実質 1 件である。vegetation は全水準で走査v1（29.485）が
幾何v3（25.592）より 15.2% 悪く、**そもそも走査モデルが採択されない**。

| 欠陥 | 扱い |
|---|---|
| 量子化が鍵と時間解像度を同時に壊す | **次の測定で閉じる** — ディザ条件（37 節） |
| 群サイズ 4〜5×10³ に観測点が無い | **次の測定で閉じる** — 交絡を切ってから log 群サイズ軸で刻む |
| 逆順を主指標にしていた | **いま直した** — 生 Δ を主とし、逆順は別条件として併記 |
| 標本が実質 1 件 | **直さないと決める** — この実験は機構の確認であって一般性の主張ではない |
| `plane` の飽和の機構 | **直さないと決める**（当面）— 29 節の観測でこの実験の対象外 |

「退避路に落ちる」という語を、容器の退避路（`--no-fallback` で切ったもの）と
走査モデル内部の退避（`sp.ok == false` のときの線内中央値予測）の両方に
使っていた。以後は後者を**線内の退避**と呼ぶ。

## 40. 取得順の置換を符号化したときの費用（2026-09-20）

多重集合符号器を系列可逆にするには、出力順から入力順への置換を送る必要が
ある。その上界は `log2(n!)/n` だが、取得順は空間的に相関しているので
実際はもっと安い。**上界で止めずに、実際に符号化して達成値を出した。**

`rec.ply` の並びから実出力順を取るようにした。復号は元々走らせているので
追加の計算は要らない。

| | 中央値 [bit/点] |
|---|---|
| 上界 `log2(n!)/n` | 18.489 |
| **実出力順（達成値）** | **7.800** |
| Morton 順（参考） | 10.197 |
| 一様乱数（達成値） | 22.874 |

**実出力順は上界の 45.9%（中央値）。** 基準順を取り違えていた分だけ
30% 高く見積もっていた。

**含意。** 恒等順で G-PCC（中央値 24.21 bpp）に置換を課すと 32.0 bpp 相当に

「$(0, 18.489]$ の範囲としか言えない」と書いていたが、**測って 7.800 に置き換える。**

8 条件のうち 3 条件で落ちたブロックが再開時に丸ごと飛ばされ、残りが
二度と生成されない状態だった。3 時間の測定が落ちたら黙って穴の開いた
データが出来上がる。条件数で判定するよう直した。

ほかに、置換の基準順が代理（Morton）だった件、ディザが「単射性」と
「取得順の情報」を同時に配っていた件、集計の nan マスクが片側しか
見ていなかった件、取得した LAZ が切り詰められてもヘッダは読めた件。

## 44. 作った縮退と自然に生じた縮退は違う（2026-09-21）

`python/exp_key_resolution.py`、出力は `data/work/key_resolution.txt`。

42 節の掃引（段階的）と 30 節の観察（閾値的）が食い違う理由を、
**発射間隔に対する量子化幅の比**で示す。発射間隔は同じ飛行線の中で
連続する点の時刻差の正の中央値。

| データ | 鍵重複 | 発射間隔 | 60% を作る量子化幅 | 比 |
|---|---|---|---|---|
| AHN4 _20 | 5.3%（自然） | 5.96e-07 s | 1.41e-06 s | **2.36** |
| vegetation | 0.0%（自然） | 9.08e-01 s | 3.59e-06 s | 0.00 |
| USGS NY | **57.7%（自然）** | 8.34e-06 s | — | — |

**AHN4 で 60% の縮退を作るには、発射間隔の 2.36 倍の量子化幅が要る。**
連続する発射が同じ時刻に潰れるので、走査モデルが当てはめに使う説明変数
そのものが失われる。中間水準で逆順Δ が 8〜16% と大きいのはこれである。

**vegetation は発射間隔が 0.908 秒**と桁違いに粗く、100% 以外の水準では
量子化幅が発射間隔に届かない（比 0.00）。だから逆順Δ が 5% 未満に収まる。

**USGS NY は発射間隔 8.34e-06 秒を保ったまま 57.7% が重複している。**
同じ発射の複数リターン（あるいは複数チャネル）どうしの重複であって、
発射どうしの重複ではない。

**帰結。** 掃引が支えるのは因果（原因は縮退であって分解能ではない。同じ
量子化幅のままディザで Δ が 0 に落ちるのがその証拠）であり、
**中間水準の効果量は、同時に壊した分解能の分だけ水増しされている。**
応答の形は掃引からは決められない。

## 45. PCC2 の時間とメモリ — 計測の誤りと、最初の改善（2026-09-21）

## 46. PCC2 を G-PCC より軽く速くする（2026-09-21、第 2 周）

45 節の続き。回帰試験は `python/regress_pcc2.py`（9 ファイル）で、
どの変更でも**可逆性・決定性・全列 bpp が完全一致**であることを確かめている。

### 直したもの

**(a) LAS 読み込みが点ごとに map を引いていた。** `pc.fields["intensity"].v[i]`
という書き方で、400 万点 × 10 列 = 4000 万回の文字列比較をしていた。
ポインタを事前に取る形に直した（符号化全体で約 9% 速い）。

**(b) 定数の列を全点ぶん確保していた。** 幾何だけの PF6 では大半の列が定数なのに
`resize(n)` で 8n バイトを払い、400 万点で 265 MB になっていた。
「値が変わるまで確保しない」形にして、`Field` に `is_const` / `cval` を持たせた。
正規化（`analyze`）は定数を展開せずに判定し、定数列は残差の相手からも外す。
**400 万点の読み込みが 265 → 113 MB。**

**(c) 走査の残差を符号化する前に走査文脈を解放。** 効果は限定的（418 → 408 MB）。
ピークは残差ループの最中（走査文脈と残差が同居する区間）に立つので、
解放を後ろに置いても届かない。

**(d) 標本で候補を選ぶ経路（`--sample-select`）の精度を上げた。**
標本の 1 位だけを信じると AHN3 で bpp が 3.3% 悪化していた。
上位 4 つを全点で測り直す形にして **+1.07%** まで縮めた。3〜4 倍速い。
残る誤差は `nir` 1 列で、標本にすると点密度が下がり**空間予測が系統的に
不利になる**ことによる。既定にはせず、任意指定のままにしてある。

### 結果（幾何のみ、符号化のみ）

規模を変えたとき（AHN4 _20、時間 [s] / ピーク [MB]）:

| 点数 | G-PCC | 幾何v3 | 走査v1 |
|---|---|---|---|
| 50 万 | 0.91 / 102 | **0.27 / 37** | **0.70 / 56** |
| 100 万 | 1.82 / 161 | **0.54 / 67** | **1.37 / 105** |
| 200 万 | 3.67 / 147 | **1.07 / 129** | **2.74** / 202 ✗ |
| 400 万 | 7.36 / 266 | **2.28 / 250** | **5.44** / 408 ✗ |

5 ファイルで 100 万点（中央値）:

| | 秒 | ピーク | bpp |
|---|---|---|---|
| G-PCC | 1.81 | 161 MB | 24.755 |
| **PCC2 幾何v3** | **0.58** | **67 MB** | 25.518 |
| **PCC2 走査v1** | **1.54** | **107 MB** | 25.336 |

**幾何v3 は、試した全ての規模で G-PCC より速く（3.2〜3.4 倍）軽い。目標を満たす。**
**走査v1 は全ての規模で速い（1.2〜1.4 倍）が、200 万点以上でメモリが超過する。**

### 走査v1 のメモリが規模で超過する理由

G-PCC は `sliceMaxPoints`（既定 110 万点）でスライスに切って処理するので、
**メモリが点数に対して頭打ちになる**（200 万点で 147 MB と、100 万点の 161 MB より
少ない）。PCC2 は全点を一度に抱えるので線形に増える。

走査v1 の超過分は、残差（3 列 × 8 バイト = 24 B/点）と走査文脈
（順序 4 B/点、時刻 8 B/点、戻り番号 8 B/点）が残差ループの最中に同居することによる。
**解消にはブロック処理が要る**（符号化の単位を分けると容器の形式が変わる）。

### 第 1 周からの変化（100 万点、幾何のみ）

| | 開始時 | いま |
|---|---|---|
| 幾何v3 | 0.64 s / 147 MB | **0.54 s / 67 MB** |
| 走査v1 | 3.05 s / 147 MB | **1.37 s / 105 MB** |

メモリは 54%／29% 減、走査v1 の時間は 55% 減。bpp は走査v1 が改善
（当てはめの打ち切り、45 節）、幾何v3 は不変。

### 第 2 周の続き — 走査v1 のメモリ

さらに 3 つ。いずれも回帰試験で **bpp が 1 バイトも変わらない**ことを確かめている。

- **戻り番号を uint8 に。** 4 ビットの値を int64 で持っていた（400 万点で 32 MB）。
- **残差を int32 に。** 座標の差なので 32 bit に収まる。収まらない点が出たら
  その場で int64 に退避する。400 万点で 48 MB。
- **時刻の並べ替え複製をやめた。** `sc.gps[t]` は元の列を `ord` で引いただけの
  複製だった。指す先を変えて 400 万点で 32 MB。

| 点数 | G-PCC | 幾何v3 | 走査v1 |
|---|---|---|---|
| 50 万 | 102 MB | **37** | **42** |
| 100 万 | 161 MB | **68** | **77** |
| 200 万 | 147 MB | **129** | **147**（同点） |
| 400 万 | 266 MB | **251** | 306 ✗ |

**100 万点以下では両候補とも G-PCC の半分以下。200 万点で同点。**
400 万点で走査v1 だけが 15% 超過する。残りは Frame が座標を int64 で持つこと
（LAS は int32）と、`ord` と残差が同居することによる。
**int32 の列を扱えるようにするか、ブロック処理にするかのどちらかが要る。**

### 到達点（AHN4 _20 中央 100 万点、符号化のみ）

| | 時間 | ピーク |
|---|---|---|
| G-PCC（幾何のみ） | 1.79 s | 161 MB |

| **PCC2 走査v1（幾何＋鍵）** | **1.37 s（1.3 倍速）** | **77 MB（2.1 倍軽）** |

参考として、PCC2 が実際に行う仕事（全 25 列、候補選択つき）は

| 全点で候補選択 | 21.31 s | 214 MB | 45.703 |
| 標本で候補選択 | 7.73 s | 229 MB | 45.708 |

**これは G-PCC と比べてはいけない値である。** G-PCC は幾何しか符号化しない。
比べてよいのは上の表だけで、下の表は PCC2 の中での選択肢の比較である。

### 目標に対する結論

**「G-PCC よりメモリ消費が低く、高速であること」は、幾何の符号化という
同じ仕事で比べる限り、試した全ての規模（50 万〜400 万点）で幾何v3 が満たす。**
走査v1 は 200 万点まで満たし（200 万点で同点）、400 万点で 15% 超過する。

超過が残る理由は 2 つある。**LAS の座標は int32 なのに Frame が int64 で持つこと**
（400 万点で 48 MB の余分）と、**G-PCC がスライスで working set を頭打ちにするのに
PCC2 は全点を抱えること**である。前者は列の型を選べるようにすれば解け、
後者はブロック処理が要る。どちらも容器の形式に触る変更なので、
この周では手を付けていない。

### 素の bpp では横並びで、ファイルごとに勝敗が割れる

7 ファイル × 100 万点、幾何のみ（47 節の実測）。G-PCC 比:

### 勝敗を決めているのは「格納順が空間的に連続か」である

右端の「比」は**格納順で連続する 2 点の距離の中央値を、点間隔（水平面積 ÷ 点数の
平方根）で割った値**である。この 1 つの量が 7 ファイルの勝敗をほぼ完全に並べる。

  格納順で隣り合う点が 1 点間隔ぶんしか離れていないので、差分が小さい。
- **比が 1.6 を超える 3 件で負ける。** USGS NY は 8.23 で、
  連続する点が 8 点間隔ぶん飛んでいる。格納順が空間的に連続していない。

O(n) で測れるので、**符号化の前にどちらが勝つか予測できる。**

### 系列を復元させると、7 件すべてで勝つ

G-PCC は多重集合しか復元しない（47 節で確認。系列は一致しない）。
系列可逆にするには置換を送る必要があり、その費用は実測できる（40 節）。
ブロックごとの実測値を足すと:

| データ | G-PCC 素 | 置換 | G-PCC＋置換 | PCC2/LAZ 最良 | 差 |
|---|---|---|---|---|---|
| AHN4 _20 | 24.755 | 8.389 | 33.144 | 19.254 | **−41.9%** |
| USGS AK | 26.755 | 8.593 | 35.348 | 23.673 | **−33.0%** |
| AHN3 _20 | 25.495 | 7.610 | 33.105 | 24.187 | **−26.9%** |
| AHN5 _20 | 25.707 | 9.122 | 34.829 | 25.518 | **−26.7%** |
| workshop | 18.470 | 8.963 | 27.433 | 20.500 | **−25.3%** |
| autzen-2023 | 20.363 | 10.825 | 31.188 | 25.336 | **−18.8%** |
| USGS NY | 21.036 | 11.512 | 32.548 | 28.086 | **−13.7%** |

**7 / 7 で勝つ。中央値で −26.9%。** 最も分が悪い USGS NY（比 8.23）でも −13.7%。

**置換の費用は格納順の連続性とともに増える**（8.389 → 11.512）。
連続していない並びほど置換の情報量が大きいので当然だが、
**PCC2 が負ける条件と G-PCC の課金が重くなる条件が同じ**なので、
課金後は差が縮んでも逆転はしない。

### 結論（サイズ、速度、メモリの順）

1. **サイズ。** 系列を復元するという同じ条件なら 7/7 で勝ち、中央値 −26.9%。
   条件を揃えないなら 4 勝 3 敗で、中央値の差は 2% 以内。
   **どちらの数字を出すかは「何を復元させるか」で決まる。**
2. **速度。** 符号化は LAZ が G-PCC の 1/13 で最速。PCC2 は 1/3〜9/10。
   復号は PCC2 が 1/7〜1/6。
3. **メモリ。** 符号化は PCC2 が最軽量（G-PCC の 42〜50%）。
   ただし 200 万点を超えると G-PCC のスライス分割に追いつかれる。

**7.800（中央値）は達成した上界であって下限ではない**ので、真の置換費用が
これより低ければ課金後の差は縮む。上の表は各ブロックの実測値を使っており、
中央値どうしの割り算はしていない。

2 点を後から補う。**「対 G-PCC（最良の系列符号器）」の列は PCC2 と LAZ の
短いほうである**ので、PCC2 単独の成績ではない（50 節の台の誤り (3) と同じ形）。
また**順序の復元を要求するかは用途による**。要求しない用途では G-PCC に置換の
費用を課す理由がないので、この節の 7/7 は「系列を復元させるなら」という
条件つきの数字である。

## 49. 圧縮後サイズを詰める — 第 1 周（2026-09-21）

指標の優先順位は**サイズ > 速度 > メモリ**。全 18 入力（LAS 16・KITTI・TLS）から
標本 20 万点を取り、`python/bench_size.py` で素早く回す台を作った（並列実行）。
候補は固定せず、選択原理に選ばせた値を PCC2 の値とする。

### 出発点

系列符号器が勝つのは **8/18**、対 G-PCC 中央値 **+1.5%**、四分位幅 27.7%点、
幅 −22.8%〜+124.1%。

### 勝敗を決めているのは「格納順が空間的に連続か」

**連続比**＝格納順で隣り合う 2 点の距離の中央値 ÷ 点間隔（√(水平面積/点数)）。
O(n) で測れて、18 入力の勝敗をほぼ完全に並べる。

- 比が 1 前後（0.13〜1.13）→ 逐次予測が効く
- 比が 1.6 を超える（USGS NY 5.77、autzen-2023 9.06、AHN4 _21 22.93）→ 負ける

### 損は予測にあって、符号化には無い

残差の 0 次エントロピーと実際の符号長を比べると、**文脈モデルは H0 を下回っている**
（AHN4 で −2.4 bit/点、USGS NY で −1.8）。**エントロピー符号化は既に十分で、
改善は予測子でしか取れない。**

### 幾何v4 — 直近 W 点の最近傍から予測し、選んだ点を送る

**最初に作ったものは復号できなかった。** 「復号側も直近 W 点を持っているのだから
最近傍を選び直せる」と考えたが、最近傍の判定にはこれから復号する点そのものが要る。
往復検証が即座に落ちた（`X[4]: 675 != 676`）。そのとき報告された 3.881 bpp は
意味の無い値である。

添字（直前から何点戻るか）を符号化する形に直した。残差の減りから添字の費用を
引いた正味は、実測で AHN4 _21 −7.5、USGS NY −2.2 bit/点。W=4 が最良で、
W=64 はどの入力でも採択されなかった（添字の費用が残差の減りを上回る）。
**ただし W=64 の候補はいまのコードに無く、`git log -S` でも過去に存在した形跡が
無いので、この 1 文は再現できない**（51 節を参照）。

| データ | 前 | 後 |
|---|---|---|
| AHN4 _21 | +9.4% | **+1.6%** |
| USGS NY | +28.4% | **+14.5%** |
| workshop | −1.9% | **−7.3%** |
| autzen-2023 | +25.9% | **+23.1%** |

**中央値 +1.5% → +0.9%、四分位幅 27.7 → 21.1%点。**

### 試して駄目だったもの

**Morton 順に並べ替えてから符号化し、置換を送る案**は 4 件すべてで負けた
（autzen-2023 は 34.171 対 いまの 26.610）。並べ替えで幾何は縮むが、
置換の費用がそれを上回る。

### 速度 — 候補の事前選別

幾何の候補は 11 個あり、全点で符号化すると 100 万点で 3.3 秒かかっていた。
標本（点数の 1/8、下限 2 万・上限 20 万）で順位を付け、上位 3 つだけを
全点で測る形にした。

**標本で系統的に不利になる族は、順位に入らなくても必ず 1 つ残す。**

- **走査モデル** — 掃引の数が減ると当てはめが効かない。
  AHN3 の走査変換は標本では 6 位以内にも入らないのに全点では 1 位だった。
- **空間予測** — 点を間引くと近傍が遠くなる（30 節の nir と同じ理由）。
- **幾何v4** — 最近傍の当たり方が場所で変わる。AHN4 _21 は先頭 12.5 万点だけ
  見ると 3 位以内に入らず、1M で +7.8% の悪化を出していた。

**属性には使わない。** USGS NY の全列 bpp が +3.7% 悪化したためである
（K を 10 まで増やしても +0.66% が残った）。サイズが第一なので幾何だけに限る。

## 50. 圧縮後サイズを詰める — 第 2 周（2026-09-21）

49 節が残した 2 つの課題（小さい入力、オクツリー順の入力）に当たった。
どちらも見立てどおりには進まなかった。あわせて比較の台に 4 つの誤りが
見つかったので直した。

### 入力の 2 つの形

この節の表は 2 種類の入力で測っている。**表ごとにどちらかを明記する。**

- **鍵つき** … `python/bench_size.py` が las 入力に対して詰めるファイル。
  XYZ に gps_time と point_source_id を足したもの。走査モデルはこの 2 列を
  副次情報として使う。
- **鍵なし** … XYZ だけを書き出した LAZ。gps_time と point_source_id の列は
  定数として存在する。

同じデータでも採択される符号器が変わることがあるので、2 つの表の bpp は
一致するとは限らない（17 件中 13 件は 3 桁まで一致し、4 件が違う。
plane は鍵つき 6.146、鍵なし 6.207）。

### 台の誤り 4 つ

**(1) extra と extrabytes は同じデータだった。** `extra.laz` と `extrabytes.las`
の XYZ は 1065 点とも完全に一致する（`np.array_equal` = True）。幾何だけを
比べる台では 1 件である。18 件と数えていたのを 17 件に直した。

**(2) LAZ の符号化時間を測っていなかった。** `python/bench_size.py` は LAZ の
時間に定数 `0.0` を書き込んでいた。書き出しの実測に直した。
（47 節の 5 軸表は `python/bench_all.py` が `lazio.py` を別プロセスで起動して
実測しているので、そちらの LAZ 0.12 s は定数ではない。ただしそれは
**プロセス起動を含む実時間**で、この環境では `import numpy, laspy` だけで 0.08 s
かかる。0.12 s の大半はインタプリタの起動であり、符号化の時間ではない。）

**(3)「対 G-PCC」を LAZ との `min` で出していた。** PCC2 が LAZ に負けている
件が、LAZ の値に隠れて見えなくなっていた。PCC2 単独の比に直した。
この 1 点で vegetation は +19.7% → +19.9%、simple1_4 は +20.9% → +22.8% になる。

**(4) PCC2 の時間が符号化の時間ではなかった。** 旧コードは `runpeak.py` が
`wait4` で測る **pccnorm プロセス全体の実時間**（LAS 読込 0.08 s とプロセス起動を
含む）を使っていた。49 節の 0.39 s / 1.66 s はこの値である。
X+Y+Z の列だけの時間に直した。LAZ は XYZ だけの書き出しなので、これで

### 全点で符号化する候補の本数と時間（鍵なし、autzen-2023 20 万点）

その 1 件が中央値の位置にいたためで、残る 16 件は bpp が 3 桁まで一致する。

既定の標本は `n/8` を [20000, 200000] で挟んだ値なので、25000 になるのは
20 万点の 11 件、autzen_trim は 20000 である。さらに
`ncols_n > PRE_SAMP * 2`（標本の 2 倍より点数が多いこと）という門があるので、
既定では extra・vegetation・fullwave・simple1_4・plane の 5 件で事前選別自体が

vegetation・fullwave・simple1_4・plane の 4 件が新たに選別の経路に入る
（extra は 1065 点なので 2000 でも入らない）。ただし**この 4 件は 5000 でも
2000 でも 1 つも動いていない。**

### 候補を 1 本に固定したときの時間（鍵なし、17 件）

選別を完全になくせばどこまで速くなるかを測った（`python/exp_single_cand.py`、
X+Y+Z の列だけ、6 並列）。4 回走らせた **幾何v3 / LAZ** の中央値は
**1.5・1.6・1.9・2.1 倍**である。

これは 幾何v3 に固定したときの比であって、「採択される符号器に固定したとき」
ではない。17 件のうち 5 件は走査変換を採択しており、走査変換は上の表のとおり
幾何v3 の 2 倍強かかる。

ファイルごとの比は載せない。pccnorm の表示が 0.01 秒刻みで、11 万点未満の
5 件は 0.000 と出て比が取れず、残る 12 件も 0.010〜0.190 s の値どうしの比なので、
**同じファイルの比が回ごとに数倍動く**（4 回それぞれの最小〜最大は
0.3〜4.7、0.4〜4.6、0.2〜4.0、0.7〜12.4 だった）。
**言えるのは「幾何の候補 1 本にすれば LAZ と同じ桁になる」までである。**

### 標本をファイル全体に散らす（鍵つき、17 件、出力のバイト数）

事前選別は標本を**先頭から連続して**取っている。走査モデルは掃引の数が減ると
当てはめが効かず、幾何v4 は場所によって最近傍の当たり方が変わる。族の保護は
これを補うために入っている。標本をファイル全体に散らせば保護は要らなくなるか
を確かめた。既存の `--sample-select` は `sample_frame` で塊を散らして取り、
標本用の副次情報も一緒に作る経路である（`python/exp_sample_select.py`）。

**要らなくはならない。** 16 件は出力のバイト数が完全に一致するが、
**USGS AK だけが 765,936 → 790,678 バイト（+3.2%）に伸びる。**
散らした標本でも走査変換は上位に入らず、全点で測り直す勝者と控えの 4 本にも
残らないためである。族の保護が守っているのはまさにこの族である。

時間は判定できない。この台が取るのは pccnorm の `enc`（全列・全工程）で、
4 回の実行の中央値は既定が 0.21〜0.35 s、散らした標本が 0.18〜0.30 s と
重なっている。`--sample-select` を付けると
内側の事前選別は `ncols_n > PRE_SAMP * 2` の門で**無効になる**（標本フレームは
25000 点、PRE_SAMP の下限は 20000）。X+Y+Z には 11 候補すべてが 25000 点で並び、
続いて勝者と控えを全点で測るので、既定とほぼ同じ仕事量になる。
ファイル単位では大きく動く件もある（USGS AK は 2.14 s → 0.34 s）。

### 速度について、この節で分かったこと

- **符号器そのものは LAZ と同じ桁にある**（候補 1 本での中央値 1.5〜2.1 倍）。
  既定の 0.21 s との差は候補の選別が占める。
- **選別を軽くする筋は、この節で試した 2 つとも通らなかった。**

速度を詰めるには、選別の回数を減らすのではなく、走査変換の当てはめ自体を
速くするか、符号長を測らずに族を決める別の指標を見つける必要がある。
どちらもまだ手をつけていない。

測っても、動いたのは 2 件だけで、しかも桁が違う。

| データ | 既定 | 文脈を足し、事前選別も切った場合 | 差 |
|---|---|---|---|
| autzen_trim | 21.064 | 21.043（幾何v3平均4文） | −0.10% |
| AHN5 _20 | 26.713 | 26.694（幾何v3文） | −0.07% |

**見積りの 10 分の 1 以下である。** 見積りは「bit 長を文脈ごとの適応モデルで
符号化する」という模型で作ったが、`UIntCoder` の実際の符号化はそれと違う。
模型が符号器と違えば、条件付きエントロピーの改善はそのまま符号長に出ない。
0.1% 未満のために候補を 2 本と模型の記憶を 8 倍増やす価値は無いので**差し戻した。**

ついでに分かったこと: **いまの候補の組では、事前選別はサイズを 1 bit も
損なっていない**（`PCC_PRESELECT=0` と既定で 17 件すべて一致）。
50 節で測った「標本を 2000 まで小さくすると 1 件が伸びる」は、
標本を小さくした場合の話であって、既定の標本では損が出ていない。

### 全点で測る候補を 3 本から 2 本に減らした

事前選別が上位いくつを全点で測るかを掃引した（鍵つき、17 件）。

| 上位 | 既定から動いた件 | 符号化 中央値 |
|---|---|---|
| 3（これまでの既定） | — | 0.22〜0.23 s |
| 2 | 0/17 | 0.20〜0.22 s |
| 1 | 0/17 | 0.19 s |

`regress_pcc2.py` の 9 件（全列、全点）でも上位 1 で全列 bpp は変わらなかった。
**既定を 2 にした。** 1 にしないのは、予測子を足す前は上位 1 だと TLS p1 が
24.252 → 25.462 bpp に伸びていたからで、余裕が要らないという根拠は無い。

## 52. 差分の値が繰り返す列を表で指す（2026-09-21）

### 全列で比べると、負けは属性側にあった

これまでの台（`bench_size.py`）は幾何だけを見ていた。G-PCC が幾何しか
符号化しないためである。利用者が受け取るのは全列なので、**基準を LASzip に

各ファイルの中央から最大 20 万点。vegetation 10683・extra 1065・fullwave 10750・
simple1_4 22600・plane 28185・autzen_trim 110000 はそれ未満の全点。
`--no-fallback --no-verify` で回す）。

改善前は **11/15 で LASzip より小さく、中央値 −7.5%** だった。負けていたのは
vegetation +8.7%、AHN3 _20 +6.3%、autzen_trim +1.5%、USGS AK +0.7% の 4 件である。
このうち幾何（`bench_size.py`、対 G-PCC）でも負けているのは vegetation +19.7% と
autzen_trim +0.3% で、AHN3 _20（−20.4%）と USGS AK（−7.4%）は幾何では勝っている。
**負けの主因は属性側にあった**が、vegetation は幾何でも LASzip に僅差で
負けている（24.890 対 24.887）ので、属性だけの問題ではない。

### gps_time の差分は、値の種類が少ないのに桁が大きい

LAS の gps_time は倍精度なので、ビットパターンを整数と見なして差を取る。

| データ | 範囲 | 点 | Δ の異なり | Δ の 0 次エントロピー | 使っていた bpp |

ビット位置ごとの適応モデルで送る。**同じ値が何度出ても毎回その桁ぶん払う。**
vegetation の Δ は上位 2 つ（−8389 が 3624 回、−8388 が 2279 回）だけで
全体の 55% を占める。

`regress_pcc2.py`（小さい 5 件は全点、AHN4 _20・AHN3 _20・USGS NY・autzen-2023 は

比べると vegetation は 54.198 → 44.385、AHN3 _20 は 53.392 → 47.530 になる。

### この符号器の危険

- **表の探索は O(K) の線形走査**で、採られなかった列でも必ず 1 回通る
  （候補を実符号化して比べるため）。当たりは移動前置で先頭に寄るので平均は
  短いが、外れが続く列では毎回 K 回走る。実測では AHN3 _20 30 万点の enc が
  K=64 と K=1024 で 5.84 s 対 5.87 s、全体で +1〜2% である。
- **復号側に探索は無い。** 添字で直接引くだけなので、復号時間は変わらない。
- 当たり率が低い入力（extra は 0.3%）では表が逆効果になるが、
  選択原理が採らないので出力は伸びない。

### 幾何だけの台は変わらない

`bench_size.py` の 17 件は bpp が完全に同値である。この台は X+Y+Z の行しか
読まず、しかも `--fast-attr` を渡すので 1 次元の列の候補も `{delta, ctx}` に
縮み、差分表は候補に入らない。**この台の符号化時間 0.20 s も、この符号器を
一度も通っていない数字である。**

## 53. 幾何の候補を並列に符号化する（2026-09-21）

### 競合の無い実時間で測り直す

`bench_size.py` は 6 並列で走るので、実時間は競合を受ける。同じ 17 件を
**1 つずつ順に**測り直した（各 2 回の短い方、X+Y+Z の列だけ、標本 20 万点）。

| | 中央値 | 四分位 | 幅 |
|---|---|---|---|
| PCC2 / LAZ（並列前） | **20.0x** | [16.4, 23.3] | 9.1〜28.7 |

競合下の台で出ていた 3.6〜43 という幅は、台の雑音を含んだ値だった。
競合の無い実時間では 9〜29 倍に収まる。

### 候補は互いに独立に符号化できる

幾何の候補が触るのは復号済みの列だけである。属性の候補は `CodecCtx` の
可変メンバ（順序表・予測子表・world）を作るので同時には走らせられないが、
**事前選別を使うのは幾何の列だけ**（`plan_streams` の 1 か所）なので、
そこだけ並列にすればよい。

出力は候補の順に並べ直してから比べるので、**選ばれる符号器は並列でも変わらない。**

### 結果

| | 1 本 | 並列 |
|---|---|---|
| PCC2 / LAZ 中央値 | 20.0x | **9.5x** |
| 四分位 | [16.4, 23.3] | **[6.4, 10.7]** |
| 幅 | 9.1〜28.7 | **3.2〜12.2** |

**比も、ばらつきも半分になった。** 16 コアの機械での測定である。

出力は変わらない。**17 件すべてで、1 本のときと並列のときの出力が
バイト一致し、往復検証も通る。**`regress_pcc2.py` の 9 件も全列 bpp が
±0.000%、可逆性・決定性とも保たれる。`bench_total.py` も 15/15・中央値
−10.1% で変わらない。

### 代償はメモリ

候補ごとに出力を同時に持つので、ピークが増える。

| データ | 点 | 1 本 | 並列 | 増 |
|---|---|---|---|---|
| AHN4 _20 | 1000000 | 216 MB | 240 MB | +11.0% |
| AHN3 _20 | 1000000 | 189 MB | 227 MB | +20.3% |
| autzen-2023 | 500000 | 100 MB | 118 MB | +17.6% |

指標の順は サイズ > 速度 > メモリ なので、この取り引きは採る。
`PCC_THREADS=1` で元の挙動に戻せる。

### 届いていないところ

**9.5 倍はまだ「LAZ に匹敵」ではない。** 残る下限は、全点で符号化する候補の
うち最も重いもので決まる。走査変換は 1 本で 0.09 s（幾何の候補は 0.04 s）かかり、
これは LAZ の 0.010 s の 9 倍である。並列にしても、この 1 本より速くはならない。

走査変換を全点で測らずに済ませる道は、族の保護に閾値を入れて掃引したが、
**サイズを保ったまま時間を縮める閾値は無かった。**

| PCC_FAMTHR | 動いた件 | 符号化 中央値（6 並列の台） |
|---|---|---|
| 1.5 | 0/17 | 0.20 s |
| 1.2 | 0/17 | 0.20 s |
| 1.1 | 1/17（AHN3 _20 +2.26%） | 0.16 s |
| 1.05 | 1/17（AHN3 _20 +2.26%） | 0.15 s |

AHN3 _20 の走査変換は標本で最良の 1.1〜1.2 倍のところにおり、
**落とせば当たり、残せば時間を払う。**族の保護はこのためにある。

走査変換の 0.09 s のうち、当てはめ（Levenberg–Marquardt）は 0.02 s しかない
（`PCC_FIT_TOL` を 1e9 にして 1 歩で打ち切っても 0.07 s。bpp は 19.263 →
19.260 でむしろ僅かに短い）。残る 0.07 s は並べ替え・掃引の切り出し・残差の
符号化である。ここを詰めない限り 9 倍は動かない。

### 走査変換の中を詰める

並列にしたあとの律速は、全点で符号化する候補のうち最も重い**走査変換**である。
内訳を測った（`PCC_SCAN_PROF=1`、AHN3 _20 中央 20 万点、合計 0.09 s）。

| 工程 | 時間 |
|---|---|
| 並べ替えと掃引の切り出し | 0.00 s |
| **走査線の分割と当てはめ** | **0.06 s** |
| 残差を作る | 0.00 s |
| 残差を符号化 | 0.02 s |

並べ替え（`stable_sort` で (point_source_id, gps_time) 順）は 0.002 s しかない。
15 件のうち 9 件はもともと整列しているが、**AHN3 _20 は整列していない**ので
整列済みの近道を作っても効かない。重いのは走査線の分割と当てはめである。

**分割の試みに足切りを入れた。** 掃引ごとに EM（`split_two_lines`）と
当てはめ 2 回を回すので重い。分けるべき掃引は主軸から見た散らばり
（`line_thinness`）が大きい。AHN3 _20 では分割した 74 本の thinness が
中央値 16.84 mm（5 パーセンタイル 12.46）なのに対し、費用で棄却した 281 本は
中央値 3.62 mm だった。USGS AK でも分割 332 本が 25.89 mm、棄却 810 本が 2.69 mm。

座標の刻みはファイルで違うので、**先頭 200 本の thinness の中央値の C 倍**を
基準にした。`C = PCC_SPLIT_THIN` を掃引した。

| C | 動いた件（17 件、幾何のみ） | 走査変換 1 本（AHN3 / USGS AK / AHN4 _20） |
|---|---|---|
| なし | — | 0.09 / 0.16 / 0.10 s |
| 1.2 | 0/17 | 0.08 / 0.15 / 0.09 s |
| **1.5** | **0/17** | **0.08 / 0.15 / 0.08 s** |
| 2 | 1/17（AHN4 _20 +0.03%） | 0.08 / 0.14 / 0.08 s |
| 5 | 3/17（最大 +0.06%） | 0.08 / 0.13 / 0.07 s |

**C=1.5 を既定にした。** 17 件すべてで bpp が変わらない上限である。
この足切りは**符号化側だけの判断**で、分けた結果は流れに書かれるので
復号側には影響しない。

**当てはめの打ち切りを緩める案は採らなかった。** `PCC_FIT_TOL` を 3e-2 から
3e-1 にすると走査変換 1 本は USGS AK で 0.15 → 0.09 s と大きく縮むが、
`regress_pcc2.py` の AHN4 _20（先頭 30 万点）が 48.179 → 48.248 bpp（+0.14%）に
伸びる。幾何だけの台（中央 20 万点）では動かないので、標本によって出方が違う。
**サイズが第一なので 3e-2 のままにする。**

| FIT_TOL | AHN4 _20 30 万点の全列 bpp |
|---|---|
| 3e-2（既定） | 48.179 |
| 1e-1 | 48.216 |
| 3e-1 | 48.248 |

### 走査変換の中も並列にする

掃引ごとの当てはめは互いに独立である（触るのは自分の区間の `L.label` と
`L.split[k]` だけ）。結果を一度配列に貯め、`L.line` への追加だけを後で順に
行えば、並列にしても出力は 1 本のときと同じになる。足切りの基準は先頭 200 本から
決めるので、そこまでは順に回す。

**最初の版は `double free or corruption` で落ちた。** 足切りの基準を作る
`thin_hist` への `push_back` が、並列に回す区間でも走っていた。共有の
`std::vector` に複数のスレッドから `push_back` すれば壊れる。基準が決まった後は
積まないように直した（`warm` の引数を足した）。**1 回目の実行では落ちず、
`PCC_SCAN_PROF` を付けた 2 回目で出た。競合は走らせるたびに出るとは限らない。**

| | 1 本 | 並列 |
|---|---|---|
| AHN3 _20 の当てはめ | 0.06 s | 0.04 s |
| USGS AK の当てはめ | 0.11 s | **0.02 s** |

bpp は変わらない。**17 件すべてで、1 本のときと並列のときの出力が
バイト一致し、往復検証と決定性検査も通る。**

### いまの速度

競合の無い実時間（1 つずつ順に、各 3 回の最小、X+Y+Z の列だけ）:

| | 中央値 | 四分位 | 幅 |
|---|---|---|---|
| 並列にする前 | 20.0x | [16.4, 23.3] | 9.1〜28.7 |
| 候補を並列に | 9.5x | [6.4, 10.7] | 3.2〜12.2 |
| **走査の中も並列に** | **9.2x** | **[6.2, 9.6]** | **3.1〜12.2** |

スレッド数は掃引した（`PCC_THREADS`）。4 / 8 / 16 / 24 で中央値 10.5 / 10.8 /
9.5 / 10.2 倍と差が出ないので、コア数（16）のままにする。

**ここから先は設計の問題である。** 候補を全部符号化して最短を採る限り、
実時間の下限は「候補の仕事の総和 ÷ コア数」と「いちばん重い候補 1 本」の
大きいほうで決まる。いまの候補の総和は約 0.6 s、いちばん重い走査変換は 0.06 s
なので、下限は 4〜6 倍あたりである。**LAZ に匹敵する（1〜2 倍）には、
候補を符号化せずに 1 本選ぶしかない。** 51 節と 53 節で測ったとおり、
標本での符号長も連続比もその判断には足りない。

### 候補を 3 本減らし、暖機をやめ、掃引を塊で配る

全候補を全点で符号化して（`PCC_PRESELECT=0 --trace`）、どの候補が 1 位に
なるかと、1 位との差を 17 件で数えた。

| 候補 | 1 位になった件 | 1 位との差の中央値 | 同 最小 |
|---|---|---|---|
| 走査変換 | 5 | 4.9% | 0.0% |
| 幾何v4W4 | 4 | 3.8% | 0.0% |
| 幾何v3 | 2 | 3.9% | 0.0% |
| 幾何v4W4傾 | 2 | 6.1% | 0.0% |

あわせて 2 つ直した。

- **当てはめを 1 本も順に回さない。** 足切りの基準は先頭 200 本の散らばりから

  散って `L.label` と `sp_out` の同じキャッシュ行を取り合う。
  走査変換 1 本が AHN3 _20 で 0.07 → 0.04 s、USGS AK で 0.15 → 0.05 s になった。

往復検証と決定性検査も通る。**

16 コアで完全に並列化できれば 0.021 s のはずだが、実際は 0.09 s しか出ない。

帯域が頭打ちになっていると見ているが、**まだ測っていない。**

### 符号器 1 本を速くする — 3 つとも採らなかった

残る差は候補の数ではなく符号器 1 本の速さである（幾何v3 が 0.030 s、
LAZ が 0.010 s）。`UIntCoder` は値ごとに「ビット長 k を単進で k+1 回」＋
「下位 k ビットを 1 回ずつ」の二値符号化を回す。3 軸で 1 点あたり 30〜70 回になる。

**(1) 下位ビットを生で書く（確率モデルを持たない）。**
`PCC_BYPASS_LOW=4` で 17 件を測ると、中央値は −0.08% と僅かに縮むが、
**simple1_4 が +22.4%、workshop が +5.7%、AHN4 _21 が +5.1%、
autzen-2023 が +4.3%** 伸びる。サイズが第一なので採らない。

**(2) ビット長を 7 段の二分木にする。** 単進の k+1 回が常に 7 回になる。

| | サイズ | 速度（2 回ずつ） |
|---|---|---|
| 単進（いま） | — | 5.0x / 5.1x |
| 二分木 | 中央値 **−0.24%**（12 件が縮み、5 件が伸びる。plane +1.37%） | **6.3x / 5.8x** |

**二分木のほうが遅い。** 残差が小さく k の平均が 5 前後なので、単進なら
6 回で済むところを木は必ず 7 回かける。さらに `idx = idx*2 + bit` の
依存の鎖ができ、128 個のモデルを飛び回るので当たりも悪い。
サイズは中央値で縮むが 5 件が伸び、速度は落ちるので採らない。

**(3) `BitModel::update` の内側に寄せる分岐を外す。** rate ≥ 1 なら
p0 は 2^rate − 1 と PROB_ONE − (2^rate − 1) の間で止まり、**この分岐は
1 度も働かない**（rate=5 での実際の範囲は [31, 65505]、総当たりで確認）。
外しても出力は 17 件とも 1 bit も変わらないが、**速度も変わらない**
（5.2x / 5.3x）。最適化器が既に落としていると見て、安全網として残す。

### 速度の到達点

| | 中央値 | 四分位 | 幅 |
|---|---|---|---|
| この時点（X+Y+Z の列だけ） | 5.1x | [4.7, 7.0] | 3.3〜9.4 |

**この値は古い。** 54 節で候補 3 本を戻したので 6.2 倍になり、さらに 55 節で
「X+Y+Z の列だけを見ていたのが誤り」と分かった。全列の値は 56 節にある。

**「LAZ に匹敵する」には届いていない。** 残りは `UIntCoder` の二値化そのもので、
LASzip は k を多値の記号として 1 回で符号化し、下位ビットも記号単位で扱う。
同じ形にするには符号化層を作り直すことになり、サイズへの影響は上の (1)(2) の
とおり一方向ではない。**サイズを第一に置く限り、ここは踏み込めない。**

### 下位ビットを生で書く案を、選択原理に選ばせても採られない

(1) を候補の 1 つにして、選択原理に選ばせる形で測り直した
（`UIntCoder` に生ビット数のパラメタを足し、幾何v3 と 幾何v4 に
「下位 4 ビットを生」の候補を 3 本追加）。

**17 件のうち 1 件も採られない。** 残差の下位ビットは一様ではなく、
確率モデルを持たせたほうが常に短い。候補を 3 本増やすだけなので差し戻した。

**途中でビット位置を取り違えた。** `mb = k - bypass` と書いたため、
生ビット数 0（既定）のときに**下位 k ビット全部が生**になっていた。
正しくは `mb = min(bypass, k)` で、mb がモデルつきで書く最下位の位置である。

この誤りは**全 17 件が悪化したことで見つかった**（中央値 +0.87%、
simple1_4 は +32.5%）。選択原理があるのだから、候補を足して全件が悪化するのは
おかしい。事前選別を切っても同じだったので、候補の選び方ではなく
**共通部分を壊している**と分かった。採択された符号器の名前が変わっていない
ファイル（USGS AK の走査変換）まで bpp が動いていたのが決め手である。

## 55. 属性の列を速くする（2026-09-21）

54 節で、全体の符号化時間は幾何ではなく属性が占めると分かった。そこを詰める。

### 近傍の予測子表を候補ごとに作り直していた

空間予測の候補は `CodecCtx::ensure(n, P)` で近傍の予測子表を作る。この表は
**1 つ（n, P）ぶんしか持っていなかった**ので、同じ列で sp(P=1) / sp(P=3) /
sp(P=5) …と候補が変わるたびに建て直していた。14 列のファイルでは 30 回を超える。

P ごとに取っておくようにした（表は n×P の int32。100 万点・P=5 で 20 MB）。

AHN3 _20 の 100 万点・全 14 列、列ごとの時間:

| 列 | 前 | 後 |
|---|---|---|
| intensity | 2.59 s | 1.70 s |
| classification | 1.78 s | 0.30 s |
| scan_angle | 1.87 s | 0.38 s |
| red / green / blue / nir | 2.28 / 2.10 / 2.08 / 2.19 s | 0.76 / 0.66 / 0.61 / 0.71 s |
| X+Y+Z | 0.34 s | 0.34 s |
| **合計（enc）** | **16.4 s** | **6.7 s** |

**サイズは 1 bit も変わらない。** 同じ候補を同じ順で測っているだけである。

### 属性の候補も並列にできるようになった

表への書き込みを排他で囲い、同じ (n, P) は 1 回しか作らないようにした。
表ができた後は読むだけになるので、54 節で `SIGSEGV` を出した並列化が成り立つ。
（`CodecCtx` が「読むだけ」になったわけではない。表は今も遅延構築される。）

AHN3 _20 100 万点・全 14 列の `enc`（3 つの設定を区別する）:

| 設定 | 時間 |
|---|---|
| `PCC_THREADS=1`（幾何も属性も直列） | 8.0 s |
| `PCC_PAR_ATTR=0`（幾何だけ並列） | 6.6 s |
| 既定（属性も並列） | **2.2 s** |

**属性の並列化そのものの効果は 6.6 → 2.2 s（3.0 倍）**である。
8.0 → 2.2（3.6 倍）には幾何の並列化ぶんが混ざっている。
AHN4 _20 は 8.5 → 2.4 s、autzen-2023 は 10.2 → 2.6 s（どちらも
`PCC_THREADS=1` との比なので、同じく幾何のぶんを含む）。

**17 件すべてで、スレッド数 1 / 3 / 16 の出力がバイト一致**し、往復検証と
決定性検査も通る。`bench_total.py` は 15/15・中央値 −10.1% で変わらない。
`regress_pcc2.py` の 9 件も全列 bpp が ±0.000%。

### 代償はメモリ

2 つある。**表を P ごとに取っておくぶん**と、**候補ごとに残差の配列と出力を
同時に持つぶん**である。前者は並列にしなくても増える（AHN3 _20 100 万点で
`PCC_THREADS=1` のピークが 188 MB → 226 MB。P=1/3/5 の表が n×P の int32 で
4+12+20 MB）。

| スレッド | ピーク | enc |
|---|---|---|
| 1 | 226 MB | 8.0 s |
| 4 | 328〜353 MB | 2.98 s |
| 8 | 429〜495 MB | 2.31 s |
| 16（既定 = コア数） | **535〜729 MB** | **2.2 s** |

**ピークは実行ごとに振れる。** 16 スレッドで 3 回測ると 535 / 561 / 729 MB
だった。有効数字 3 桁で読める値ではなく、順序関係（スレッドを増やすと増える）
だけが頑健である。

指標の順は サイズ > 速度 > メモリ なので既定はコア数のままにする。
`PCC_THREADS=4` で 333 MB / 2.98 s に落とせる。

### 全列での速度 — 初めて正しく測った

これまで速度として出していたのは X+Y+Z の列だけだった。全列で測り直す
（`python/exp_speed_total.py`、標本 20 万点、las 15 件、1 つずつ順に）。

| | 中央値 | 四分位 | 幅 |
|---|---|---|---|
| 表のキャッシュ前 | 99.3x | [45.8, 221.5] | 23.9〜264.5 |
| キャッシュ後・属性は直列 | 57.3x | [23.8, 102.5] | 11.7〜131.3 |
| **属性も並列** | **28.6x** | **[12.9, 44.3]** | **8.7〜50.7** |

**基準の LASzip は laspy の既定バックエンド（lazrs の並列版）である。**
単スレッドの LASzip ではない。20 万点 14 列を 0.014 秒で書けるのはそのためで、
上の比は「16 スレッドの PCC2 対 並列 lazrs」の壁時計比である。

X+Y+Z の列だけを測ると 6.2 倍だが、**これは別の台の値で直接は比べられない**
（`exp_speed.py` は 17 件・LAZ 側は XYZ 3 列だけの書き出し・各 3 回、
`exp_speed_total.py` は las 15 件・LAZ 側は全列・各 2 回）。
LASzip は全列を 1 回のパスで詰めるのに対し、PCC2 は列ごとに十数個の候補を
全点で符号化して最短を採っている。**選択原理の費用がそのまま出ている。**

## 56. 最短を超えた候補を打ち切る（2026-09-21）

候補を全部符号化して最短を採るなら、**符号化の途中で既に見つかっている最短を
超えた候補は、最後まで回しても最短にはなり得ない。**そこで打ち切ってよい。
選ばれる符号器は変わらない。

実装は算術符号化器の中に置いた。出力が 1 バイト増えるたびに、スレッドごとに
置いた「いまの最短」への参照と比べ、超えていたら例外を投げる。候補は並列に
符号化されるので、最短は `std::atomic` で共有する。

### 事前選別の標本では打ち切ってはいけない

最初の版は標本でも打ち切っていた。**17 件のうち 1 件で出力が変わった。**
打ち切った候補は順位表から消えるので、族の保護が「その族の候補が 1 本も無い」と
見てしまい、走査変換を全点に進められなくなる。標本の符号化は全点の 1/8 しか
かからないので、そこでは打ち切らないことにした。

直した後は**スレッド数 1 / 3 / 7 / 16 の出力が 17 件ともバイト一致**する。

### 効果

| AHN3 _20 100 万点・全 14 列 | 打ち切り前 | 打ち切り後 |

### 安い候補を先に 1 本走らせる案は遅くなった

打ち切りは「いまの最短」が判っているほど早く効くので、安くて筋の良い候補
（delta / ctx）を 1 本だけ先に回して上限を決めてから残りを並列にする案を試した。

**遅くなった。** AHN3 _20 100 万点・全 14 列で 1.68 s → 2.06 s。
先に回す 1 本は他と重ならないので、その時間がそのまま足される。
コア数（16）が候補の数（10〜14）より多いので、**全部同時に始めても
安い候補は先に終わり、上限はすぐ決まる。**わざわざ直列にする理由が無い。
差し戻した。

### 打ち切りが `--sample-select` の選択を壊していた

56 節で「選ばれる符号器は変わらない」と書いたが、**既定の経路でしか成り立って
いなかった。**

`best_stream` は候補の符号長を `rank` に集め、そこから `best.alt`（控え）を作る。
`alt` は `--sample-select` の経路（`main.cpp`）で、**標本で選んだ勝者と控えを
全点で測り直す**ために使われる。打ち切った候補は `rank` に入らないので控えから
消える。標本で負けた候補が全点で勝つことがあるので、控えが欠けると選択が変わる。

中央 80 万点・`--sample-select 100000` で 6 回ずつ測った出力のバイト数:

| | 打ち切り前 | 打ち切り後（誤り） |
|---|---|---|
| AHN3 _20 | 4,930,956（6 回とも同じ） | 4,931,142 / 4,931,515 |
| autzen-2023 | 6,465,428（6 回とも同じ） | 6,465,427 / 6,468,141 / 6,468,184 / 6,472,953 / **6,748,049** |

**最大 +4.4%、しかも同じ設定の再実行で値が割れる。**
`rank` は「空間予測を必ず 1 本残す」保証にも使われており、標本で不利になる
空間予測の候補こそ打ち切られやすい。

**直した。標本の上で計画を立てているとき（`ctx->full` が立っているとき）は
打ち切らない。** 直した後は 6 回とも打ち切り前と同じバイト数・同じ md5 になる。

56 節でチェックリストに書いた「枝刈りは『その値を最終的な選択にしか使って
いない』ことを確かめてから入れる」を、**書いた本人が全点側で守れていなかった。**
標本側だけ直して締めていた。

あわせて `PCC_ABORT=0` で打ち切りを切れるようにした。打ち切ると `--trace` の
候補一覧が「不可: 最短を超えたので打ち切り」だらけになり、どれが落ちるかは
実行ごとに変わるので、候補を並べて見たいときに要る。

### 残った注意書き

**`pccnorm` の「決定性 バイト一致」は候補選択を検証していない。**
`main.cpp` は**選び終えた同じストリーム**で書き出しをもう一度呼ぶだけで、
選択も符号化もやり直さない。並列化や打ち切りが選択を変えていないことの
担保は、**外からスレッド数を変えて出力の md5 を比べる**ほうである
（las 15 件で `PCC_THREADS=1` / 既定 / 3 が一致することを確かめてある）。

**`CodecCtx::ensure` は排他を握ったまま表を作る。** その中で呼ぶ
`build_causal_predictors` は自分でコア数ぶんのスレッドを立てる（`attr.cpp`）。
正しさに問題は無いが、表を作る間は他の候補が止まる。属性の並列化が
コア数ぶん伸びない理由の 1 つである。

**`ctx->perm` は排他の外で読んでいる。** いまは 1 つの `encode_many` の中では
`n` が共通で、`perm` は最初の `ensure` でしか書かれないので安全である
（`ensure` の lock / unlock が happens-before を作る）。ただし `built_n != n` で
`perm.clear()` する枝があるので、**2 つの点数を並行に扱う経路を作ったら壊れる。**

**環境変数**（いずれも既定のままで動く。測定と切り分けのためにある）:

| 名前 | 既定 | 何をするか |
|---|---|---|
| `PCC_THREADS` | コア数 | 候補と掃引の並列度。1 で直列 |
| `PCC_PAR_ATTR` | 1 | 属性の候補を並列にするか |
| `PCC_ABORT` | 1 | 最短を超えた候補を打ち切るか。`--trace` で候補を並べたいときは 0 |
| `PCC_PRESELECT` / `PCC_PREKEEP` | n/8（下限 2 万） / 2 | 事前選別の標本と残す本数。0 で選別なし |
| `PCC_PRESELECT_ATTR` | 0 | 属性にも事前選別を掛けるか（54 節のとおり既定では掛けない） |
| `PCC_SPLIT_THIN` / `PCC_SPLIT_MAXFRAC` | 1.5 / 0.25 | 走査線を 2 本に分ける試みの足切り |
| `PCC_FIT_TOL` | 3e-2 | 走査線の当てはめの打ち切り |

### `--sample-select` はもう速くない

散らした標本で計画を立て、勝者と控えだけを全点で測り直す経路である。
候補を全部全点で符号化する既定より速いはずだった。全列で測ると**逆だった**
（`python/exp_sample_total.py`、標本 20 万点、las 15 件、散らす標本 25000 点）。

| | サイズ（既定比） | PCC2/LASzip |
|---|---|---|
| 既定 | — | **22.2x**（四分位 [10.9, 33.2]） |
| `--sample-select 25000` | 中央値 +0.00%、幅 −0.82〜**+2.98%** | 32.9x（四分位 [12.4, 39.7]） |

理由は 2 つある。**標本での計画に全候補を 25000 点で符号化する費用がかかる**こと、
そして**全点での測り直しは `main.cpp` が直列に回しており、打ち切りも並列化も
効かない**ことである。55・56 節で既定の経路を速くしたぶん、この経路が
相対的に重くなった。

サイズも USGS AK が +2.98%、AHN5 _20 が +1.85% 伸びる。
**速度でもサイズでも既定に負けるので、この経路を使う理由は無くなった。**
（`scripts/run_scan_batch.sh` と `notes/04_next_steps.md` がこの経路を
「10.2 倍速」として参照している。その値はもう当てはまらない。）

### 選べる設定を並べると、既定が一番小さくて一番速い

サイズと速度の取引が残っているかを確かめた
（`python/exp_tradeoff.py`、標本 20 万点、las 15 件、全列、1 つずつ順に）。

| 設定 | 対 LASzip 中央値 | LASzip より小さい | PCC2/LASzip 時間 | 四分位 |
|---|---|---|---|---|
| **既定** | **−9.9%** | **15/15** | **21.2x** | [11.3, 34.7] |
| 属性に事前選別（`PCC_PRESELECT_ATTR=1`） | −9.9% | 15/15 | 33.4x | [9.7, 76.6] |
| `--fast-attr`（属性の候補を 2 本に絞る） | −7.6% | 10/15 | 20.2x | [10.0, 33.5] |

**既定が一番小さく、しかもほぼ一番速い。取引は残っていない。**

- **属性への事前選別は、いまは遅い。** 54 節では全列の時間が 34% 縮んだが、
  それは属性を直列で回していたときの話である。55 節で並列にし 56 節で
  打ち切りを入れたので、全点で全候補を回す費用がもう小さい。標本で順位を
  付ける費用（全候補を 25000 点で符号化）のほうが上回る。
- **`--fast-attr` は 5% しか速くならないのに 15 件中 5 件が LASzip に負ける。**
  候補を減らす方向は、この構成ではもう割に合わない。

`--sample-select` も同じ理由で遅くなっている（32.9x）。
**55・56 節で既定を速くしたぶん、「候補を減らして速くする」系の設定は
すべて既定に負けるようになった。**
